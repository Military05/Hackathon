# Автоматический прогон сценариев Лии

Реализованный инструмент: `scripts/qa_run.py`. Он отправляет синтетические события серверу по CONTRACTS v1, проверяет фактические ответы и создаёт самостоятельный HTML плюс JSON. Python 3.11+, только стандартная библиотека; устанавливать pytest или запускать сервер для просмотра отчёта не требуется.

**Сервер предприятия и симулятор Гриши в текущем main ещё не реализованы.** Проверки самого QA-инструмента выполнены на HTTP test double — это не проверка готовности приложения. Недоступный сервер даёт BLOCKED и код выхода 2. Журнал TESTING заполняется после запуска против реальной версии сервера.

## Подготовка отдельного стенда

Егор С. запускает отдельную demo-базу и порт согласно RUNBOOK. Остановите фоновый симулятор на время QA-прогона: его события могут изменить проверяемые условия. Не используйте этот инструмент против рабочей базы предприятия. Он создаёт события и историю происшествий, ничего не удаляет и не закрывает операторские статусы.

Скопируйте `tests/fixtures/qa_config.example.json` в `runtime/qa/config.json`. Пример идентификаторов и координат не является конфигурацией реального сайта. Согласуйте с Егором С. и Гришей:

- `allowed_access`: существующий сотрудник с допуском в выбранное здание;
- `denied_access`: другой существующий сотрудник без допуска;
- `forbidden_zone`: машина без допуска в зону, соответствующий position sensor, точка вне всех запрещённых для этой машины зон и две точки внутри выбранной зоны;
- `heartbeat`: существующий отдельный QA-датчик и фактический порог сервера; инструмент поддерживает порог 1–30 секунд.

Сотрудники должны быть зарегистрированы в assets; датчики, здания и зоны — в `/api/site`. Инструмент проверяет их существование. Ожидаемые допуски и геометрию задаёт независимая QA-конфигурация; ожидаемый результат не выбирается по ответу тестируемого сервера.

## Запуск

Из корня после подготовки стенда и конфигурации:

```powershell
python scripts/qa_run.py --base-url http://127.0.0.1:8000 --config runtime/qa/config.json --server-sha ПОЛНЫЙ_SHA_СЕРВЕРА --allow-demo-writes
```

`--allow-demo-writes` разрешает запись тестовых событий. Без флага сетевые записи не выполняются и выбранные проверки получают BLOCKED.

Сначала можно проверить основу без остановки Ollama:

```powershell
python scripts/qa_run.py --config runtime/qa/config.json --cases Q07,Q06,Q03,Q08,Q11 --allow-demo-writes
```

Для Q27 остановите Ollama вручную **на отдельном QA-стенде** и дождитесь `agent=unavailable` в `/api/health`. Инструмент не останавливает процессы. Затем запустите Q27 или весь набор. Если агент доступен, Q27 получает BLOCKED, а не PASS.

Отчёт: `runtime/qa/report.html`; данные: `runtime/qa/report.json`. Откройте HTML в браузере. `--report` задаёт другой путь; папка создаётся автоматически. Новый запуск заменяет выбранные файлы отчёта, но события получают уникальные ID и не затирают историю сервера.

Коды выхода: 0 — выбранные проверки прошли; 1 — есть FAIL; 2 — есть BLOCKED и нет FAIL. Не выбранные сценарии имеют NOT RUN. Успех поднабора не означает прохождение всех сценариев.

## Что проверяется

| Case | Проверка |
|---|---|
| Q07 | Разрешённый проход не создаёт unauthorized_access за окно наблюдения |
| Q06 | Один unauthorized_access с правильными employee_id, building_id и evidence_event_ids |
| Q03 | Вне зоны нет тревоги; въезд создаёт один активный случай; движение внутри не дублирует его; выход снимает условие и сохраняет историю |
| Q08 | До порога после heartbeat нет новой тревоги; затем один sensor_offline; last_received_at и detected_at подтверждают порог; новый heartbeat восстанавливает связь |
| Q11 | Повтор события получает HTTP 200 и duplicate=true без нового происшествия |
| Q27 | При недоступном агенте анализ получает HTTP 503; события, правила, позиции и API карты работают |

Q27 проверяет API данных карты, а не отрисовку страницы. Семантика текста Qwen, настоящие агентные инструменты, нейросеть D4 и её метрики проверяются отдельно по TESTING.

## Данные симулятора Гриши

Пока генератор отсутствует, источник указан как `QA contract fixtures`: небольшие события с текущим временем по согласованному формату. Ожидаемые исходы фиксированы в тестах. Это QA-фикстуры, а не полный симулятор маршрутов.

Когда Гриша предоставит функцию создания событий, подключите её без изменения проверок:

```powershell
python scripts/qa_run.py --config runtime/qa/config.json --event-factory src.simulator.qa_events:make_event --allow-demo-writes
```

Путь — пример будущего адаптера, сейчас такого модуля нет. Функция получает именованные `event_id`, `event_time`, `sensor_id`, `type`, `demo`, `payload`, возвращает словарь Event и не отправляет его сама: запись выполняет QA-клиент. Она должна сохранить заданные значения, иначе проверка получает FAIL. Согласуйте экспортируемую функцию с Гришей. Модель и сервер не требуют новых API ради QA.

## Форматы ответов и время

Используются существующие `/api/health`, `/api/site`, `/api/events`, `/api/incidents`, `/api/assets` и `/api/incidents/{id}/analysis`.

Списки: JSON-массив или объект с `items` либо соответствующим именем `incidents`/`assets`. Неправильный JSON и HTTP-коды дают FAIL. Неполная выборка с `has_more`, `next_cursor`, `next` или `total` больше числа записей даёт BLOCKED. Для QA нужна полная выборка demo-стенда.

Позиции: `id`/`asset_id`, координаты на верхнем уровне или в `position`. Health: строка или объект с `status`. Offline: `threshold_seconds`, `last_received_at` в `details` или на верхнем уровне. При другом согласованном формате обновите адаптер и проверки в одном PR; CONTRACTS этим инструментом не меняется.

HTTP timeout — 3 секунды, ожидание изменения — 2 секунды, отрицательное окно наблюдения — 0,6 секунды. `--request-timeout`, `--wait`, `--observe`: >0 и <=30. Отрицательные проверки подтверждают отсутствие лишнего результата в конечном окне, а не навсегда. Threshold heartbeat и ожидание Q08 учитываются отдельно.

## Состав отчёта

ID прогона; дата UTC; адрес стенда; предоставленный SHA сервера; SHA, ветка и локальные изменения QA-инструмента; Python; источник событий и конфигурация; ожидаемый и фактический результат; PASS/FAIL/BLOCKED/NOT RUN; длительность; ID событий/происшествий и HTTP-проверки.

Версия QA не выдаётся за версию сервера. Без `--server-sha` стоит unknown. Укажите фактический SHA запускаемого сервера. HTML экранирует значения; JavaScript и внешние ресурсы не нужны. Ответы API и секреты целиком в отчёт не копируются.

## Проверка самого инструмента

```powershell
python -m unittest discover -s tests/qa -p 'test_*.py' -v
```

Тестовый HTTP-сервер создаётся внутри unittest на случайном локальном порту и останавливается после проверки. Проверяются обнаружение неверного здания, отсутствующих evidence, пропущенной тревоги, дублей, раннего offline, неверных ответов API и недостающих условий. Его успех не заносится как PASS приложения в общий журнал.
