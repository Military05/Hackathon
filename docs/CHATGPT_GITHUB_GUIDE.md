# Обычный ChatGPT + GitHub: полный алгоритм участника

> Текущая поставка ограничена задачами Егора С. и Егора М. ML, агент и сценарии разрабатываются отдельно и в эту ветку не включены. Подтверждённые этапы, команды и статусы: [DEVELOPMENT_STAGES](DEVELOPMENT_STAGES.md), [RUNTIME_QUICKSTART](RUNTIME_QUICKSTART.md), [RELEASE](RELEASE.md). Остальные разделы описывают общий целевой план команды.

Эта инструкция рассчитана на обычный чат. Work/Codex с локальным выполнением используется координатором для отдельно ограниченных задач. Командные правила: [TEAM_ROOM_PLAYBOOK](TEAM_ROOM_PLAYBOOK.md), API: [CONTRACTS](CONTRACTS.md), уточнения: [PREBUILD_FIXES](PREBUILD_FIXES.md).

## 1. Подключение и проверка контекста

1. Открыть свой обычный чат ChatGPT и выбрать доступный плагин/приложение GitHub. Если такого пункта нет, использовать свою доступную настройку Plugins/Apps; названия интерфейса могут различаться.
2. Предоставить доступ к Military05/Hackathon в настройке GitHub и подтвердить чтение конкретного файла README. Для закрытого репозитория проверить авторизацию. Публичное чтение само по себе не доказывает право создавать ветку/PR.
3. Отправить стартовый prompt ниже. Указать роль и конкретную ветку/SHA, а не только «наш проект».
4. ChatGPT должен реально получить нужные файлы. Если доступа нет, человек копирует их из GitHub или прикладывает файлы; чат явно сообщает ограничение.
5. Сверить названные участники, текущий статус и свою область. Если чат предлагает весь ThingsBoard или новую схему вместо v2, попросить перечитать UPSTREAM_REUSE и PREBUILD_FIXES.
6. В локальном клоне записать git rev-parse HEAD. GitHub-контекст и локальная папка могут быть разных версий.

Наличие GitHub-плагина не даёт автоматический терминал на вашем ноутбуке и не соединяет разговоры разных аккаунтов. Для этого проекта обычный чат выдаёт проверяемые файлы/команды, человек выполняет их и возвращает вывод. Доступные read/write действия зависят от конкретного плагина и разрешений: их надо проверить в своём чате. Официальные документы указывают, что доступ зависит от разрешений и доступные инструменты зависят от подключения: [OpenAI MCP tools](https://developers.openai.com/api/docs/guides/tools-connectors-mcp), [workspace connections](https://learn.chatgpt.com/docs/enterprise/shared-connections). Эти страницы не подтверждают локальное выполнение из обычного чата.

## 3. Какой prompt выбрать по роли

| Роль | Первая полезная просьба | К кому идти до изменения |
| --- | --- | --- |
| Егор С. | «Проверь текущий Event/idempotency/SQLite и подготовь маленькую задачу R01; покажи транзакции и expected 201/200/409» | все потребители при wire/schema изменении; Лия по кейсам |
| Егор М. | «Сделай R02: общая карта /api/site + /api/assets, дороги/маркеры/датчики и error/stale; CSS/source reuse сохранить» | Егор С. по response; Гриша по routes |
| Гаджи | «R04: подключи уже установленный локальный API, добейся настоящего вызова одного разрешённого tool, покажи trace» | Егор С. по provider/snapshot; Лия по evidence |
| Гриша | «R03/R07: воспроизводимый normal/D1–D3 из site.json, затем split episode_id перед scaler; не меняй Event» | Егор С. по ID/приёму; Егор М. по roads; Лия по expected |
| Лия | «R05: прочитай код и составь конкретные кейсы D1–D3 и boundary, команды/expected; проверяем фиксированный SHA» | автор по запуску; координатор по общему кандидату |

Чат может сформулировать инструкцию «сначала обсуди X с Гаджи». Он не должен сам считать обсуждение состоявшимся. Пользователь возвращает согласованный ответ в чат, затем работа продолжается.

## 4. Цикл «чат → код → запуск → PR»

1. Человек проверяет локальную базу, создаёт личную ветку. Не делайте git pull при незакоммиченных изменениях; сначала сохраните свою работу. Правила подробно в TEAM_WORKFLOW.
2. Чат выдаёт один небольшой комплект. Просим содержимое файла полностью, если участнику сложно применить patch; никаких «остальное очевидно».
3. Человек сохраняет указанные файлы в VS Code. Проверяет путь, кодировку UTF-8, отсутствие несуществующих import.
4. Выполняет команды в PowerShell. Если нужен второй процесс, открывает второй терминал. Не отправляет токены или секреты в чат.
5. Копирует фактическую ошибку/вывод и короткий expected. Чат чинит конкретную причину в своей области.
6. После прохождения проверки человек смотрит git diff и список изменённых файлов, затем commit/push и PR.
7. В PR указать R/T-ID, причину/поведение, SHA, команда/вход/результат, кого затрагивает. Лия проверяет один SHA.
8. Координатор или выбранный интегратор выполняет merge после review/QA. ChatGPT обычного чата не объявляет merge успешным без инструмента/ответа.

Пример команд для новой личной ветки, если рабочая папка чистая:

```powershell
git status
git fetch origin
git switch main
git pull --ff-only
git rev-parse HEAD
git switch -c codex/имя-участника-r-id
```

Префикс/точное имя можно согласовать с TEAM_WORKFLOW; команда выше — шаблон, замените имя. Для задач F1 база feature/beta1-f1 и зафиксированный beta-1, а не произвольный старый main.

Перед отправкой:

```powershell
git diff --stat
git status
git add путь-к-своему-файлу
git diff --cached
git commit -m "Кратко: конкретное поведение задачи"
git push -u origin имя-личной-ветки
git rev-parse HEAD
```

Команды с заменителями выполняются после подстановки собственных имён/путей. Не используем git add . для случайных весов, БД, venv или чужих изменений. PR через GitHub → Pull requests → New pull request; base определяет команда.

## 5. Передача контекста между чатами

```text
Репозиторий Military05/Hackathon. Роль [имя].
Issue/R-ID [идентификатор]. Ветка [имя]. Полный SHA [40символов].
Разрешённые файлы [список].
Контракт [ссылка/версия]. Согласовано с [имя]: [точное решение].
Сделано [поведение].
Проверено [команда и фактический результат].
Не проверено [что].
Ошибка/следующая задача [кратко].
Прочитай исходники именно этого SHA. Не заменяй рабочий код новой архитектурой.
```

Такая запись хранится в Issue/PR и копируется человеком в новый чат. Плагин не переносит историю автоматически и не обеспечивает тайную связь двух аккаунтов.

## 6. Если инструменты записи доступны

Перед записью чат показывает конкретные файлы/ветку/PR. Только личная ветка и согласованный allowlist. Запись через GitHub не заменяет запуск на ноутбуке: после получения ветки человек всё равно выполняет RUNBOOK и возвращает результат. Не поручайте обычному чату «merge всё»: это уничтожает границы ответственности и не доказывает совместимость.

Если tools записи отсутствуют, этого достаточно для всей человеческой разработки: чат выдаёт код, участник сохраняет/запускает/коммитит. GitHub остаётся общим источником состояния и инструкции.
