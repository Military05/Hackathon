# Архитектура мониторинга и интеллектуального анализа

## Обязательная архитектура v2 — три диспетчера

[DISPATCH_OPERATIONS](DISPATCH_OPERATIONS.md) — полная спецификация routing/ownership/transfers/presence/reminder/escalation/summary/Notifications и их API, [CONTRACTS v2](CONTRACTS.md) — единый договор. [План](TASK_03_PLAN.md) включает всё в финальную приёмку D1–D10.

Один сервер/SQLite и три секторных окна: logistics, production, coordination. Одна LLM обслуживает все профили; её очередь не ограничивает одновременные Incident. Датчики/правила/MLP создают случаи автоматически, затем сервер адресует Notification ответственному сектору. Claim/transfer/close атомарны и сохраняют revision/history/request_id. Одно продолжающееся нарушение — один Incident, не один Incident на всё предприятие.

Передача сохраняет прежнего владельца до подтверждения; отсутствие оператора не освобождает owner. Эскалация создаёт уведомление того же случая и показывает coordinator/резервным профилям. Все таймеры и история сохраняются. Аккаунты/смены/сложные права, прогноз столкновений, рация и команды оборудованию исключены.

Первыми проверяем Local-модели Bionic и доступный API; подтверждённый серверный путь — LM Studio Developer, резерв Ollama. Точные параметры в RUNBOOK; установленная версия и оборудование пока не подтверждены. Общий агент: 1 running/20 queued/120 секунд очереди/60 выполнения, кэш incident+snapshot. Вызов модели вне транзакций/приёма событий.

**Кто участвует:** пара A — Егор С. (бэкенд) и Егор М. (фронтенд); пара B — Гаджи (агент) и Гриша (симулятор и нейросеть); тестировщик — Лия. Подробности и роли: [команда](TEAM.md).

Если слово незнакомо, открой [словарь простыми словами](GLOSSARY.md). Команды и названия полей не переводим: в коде они должны остаться точными.

Проект задания №3. [План](TASK_03_PLAN.md), [контракты](CONTRACTS.md), [запуск](RUNBOOK.md), [промышленные примеры](INDUSTRY_PRACTICE.md).

## 1. Разделяем четыре задачи

| Слой | Что выполняет | Владелец |
| --- | --- | --- |
| Приём и хранение | Датчики/симулятор → валидированные события → SQLite | Егор С. (A1) |
| Точные правила | Запрещённая зона, доступ, отсутствие heartbeat | Егор С. (A1); интерфейс Егор М. (A2) |
| Небольшая нейросеть | Признаки временного окна → score (оценка модели) необычного движения | Гриша (B2) |
| Локальный агент | Выбор tools (инструменты агента) → чтение фактов → объяснение происшествия | Гаджи (B1) |

Нейросеть не собирает данные: их получает программный адаптер. LLM (большая языковая модель) не является операционной системой и не заменяет базу, сервер или геометрию.

## 4. База и события

Сущности: assets, sensors, buildings, zones, access_permissions, events, incidents (происшествия), incident_evidence, model_observations, agent_jobs, agent_analyses.

Храним raw (исходные) payload (содержимое события), event_time и received_at. Источник обозначаем demo (демонстрационные данные). Evidence (исходные события, подтверждающие вывод) происшествия — ссылки на реально сохранённые event_id. Для потери heartbeat дополнительно сохраняем detection_time и threshold_seconds; одно событие heartbeat не содержит факт будущего молчания.

Ошибочное/повторное событие не должно запускать повторную обработку. При дубле одинакового event_id и payload возвращаем idempotent ответ; при другом payload — 409.

## 5. Выполнение правил

Граница прямоугольника считается внутри. Сначала определить зону, затем проверить разрешение V1/V2/V3; наличие машины в зоне само по себе ещё не нарушение.

Событие прохода содержит employee_id и building_id; запрещённый проход становится происшествием. Информация о допуске берётся из site config/базы.

Heartbeat проверяется по received_at серверных часов. Проверка таймером раз в секунду; для demo offline_threshold=5 секунд. На одну активную потерю связи — одно открытое происшествие, не по одному каждую секунду. После возврата отмечаем восстановление; история не удаляется.

## 6. Нейросеть

Окно 10 секунд, шаг 5 секунд, минимум 6 position samples. Времена и признаки одинаковы в training (обучение) и inference. Для задержанных/неполных окон возвращаем insufficient_data, без выдуманного score.

Фиксируем feature_version=movement-v1 и семь числовых признаков в CONTRACTS. Все преобразования сохраняются вместе с MLP (небольшая многослойная нейросеть) в одном Pipeline. Не обучаем сеть на каждом HTTP-запросе; загружаем готовый артефакт один раз.

Модель обучается на синтетических эпизодах normal/anomaly. Сети не передаём готовые метки нарушения/допуска: иначе она просто повторит точное правило. Score — выход классификатора, а не доказанная вероятность опасности.

Порог выбирается на validation (проверочная часть данных для настройки) и сохраняется с версией артефакта. Training/test split (разделение данных) по episode_id, а не соседним окнам одного эпизода. Сравнение с простым baseline (простой алгоритм для сравнения) обязательно.

## 7. Агент с локальной LLM

Внешнее облако по умолчанию не используется. Проверенный локальный provider LM Studio использует /v1/chat/completions; резерв Ollama — /api/chat. Адрес и точный ID модели задаются по RUNBOOK. Наличие локального HTTP (протокол обмена с сервером) API не означает оплату внешнему поставщику.

Один запрос диспетчера создаёт agent_job. Внешний цикл:
1. Дать id происшествия и схемы разрешённых tools.
2. Модель выбирает tool (инструмент агента) и аргументы.
3. Код валидирует их и исполняет функцию.
4. Сохранить tool trace (журнал вызовов инструментов), передать результат модели.
5. Повторить в пределах бюджета или получить итог.
6. Проверить evidence итогового ответа и сохранить результат.

Бюджет MVP: один активный agent_job, максимум 3 обращения к модели, суммарно максимум 6 tool calls, общая цель времени до 60 секунд. Это проектные ограничения; фактическую скорость измеряем на demo-машине. Локальный клиент задаёт timeout (предельное время ожидания) оставшегося бюджета. Бесконечных повторов нет.

Tools читают базу и регламент. Они не выполняют произвольные команды, SQL от модели или изменения фактов. Диспетчер сам изменяет статус происшествия через обычный интерфейс.

## 8. Очереди и устойчивость

Приём данных и карта не ждут LLM. Agent_jobs принимаются с 202; интерфейс опрашивает статус. Один worker (обработчик задач) обрабатывает очередь, повторное обращение к тому же snapshot (снимок состояния данных) использует готовый результат.

Snapshot содержит incident_id, evidence ids, версии правил и модели. Новые evidence инвалидируют старый анализ; не выдаём старое объяснение за новое.

Для MVP SQLite — один writer и короткие транзакции. Вызов LLM, обучение и долгие вычисления выполняются вне DB-транзакции. Сеть/model worker не блокируют event loop (цикл обработки запросов) сервера. В MVP agent worker — одна асинхронная очередь внутри lifespan приложения; Локальный модельный runtime работает отдельным процессом; сначала проверяем Bionic/LM Studio API. CPU (процессор) inference выполняем через thread executor, обучение отдельной командой. Server scheduler (таймер фоновых проверок) стартует один раз, без нескольких uvicorn workers.

## 9. Статусы подсистем

Rules: ready. ML (машинное обучение): not_trained / ready / insufficient_data / error. Agent: unavailable / queued / running / completed / failed.

Если MLP не загружена, показываем отсутствие анализа, а не normal (обычное поведение). Если локальный модельный runtime выключен, сохраняем факты и показываем agent unavailable. Нет скрытого автоматического перехода на внешний API.

## 10. Что подтверждаем

Работу правил — тестами сценариев. Обучение — собственным артефактом и отчётом. Агентность — видимым trace (журнал действий) реальных tool calls. Независимость слоёв — отключением LLM без остановки мониторинга.

Это компактная архитектура хакатона, а не сертифицированная система управления реальным производством.

## 11. Панели участков и привязка анализа

Результат анализа привязан к incident_id и снимку данных; панель выбирается сервером по явной конфигурации места. Дороги и неизвестное место обрабатываются отдельно.
