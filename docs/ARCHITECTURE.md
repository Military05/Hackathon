# Архитектура мониторинга и интеллектуального анализа

Проект задания №3. [План](TASK_03_PLAN.md), [контракты](CONTRACTS.md), [запуск](RUNBOOK.md), [промышленные примеры](INDUSTRY_PRACTICE.md).

## 1. Разделяем четыре задачи

| Слой | Что выполняет | Владелец |
| --- | --- | --- |
| Приём и хранение | Датчики/симулятор → валидированные события → SQLite | A1 |
| Точные правила | Запрещённая зона, доступ, отсутствие heartbeat | A1; интерфейс A2 |
| Небольшая нейросеть | Признаки временного окна → score необычного движения | B2 |
| Локальный агент | Выбор tools → чтение фактов → объяснение происшествия | B1 |

Нейросеть не собирает данные: их получает программный адаптер. LLM не является операционной системой и не заменяет базу, сервер или геометрию.

## 4. База и события

Сущности: assets, sensors, buildings, zones, access_permissions, events, incidents, incident_evidence, model_observations, agent_jobs, agent_analyses.

Храним raw payload, event_time и received_at. Источник обозначаем demo. Evidence происшествия — ссылки на реально сохранённые event_id. Для потери heartbeat дополнительно сохраняем detection_time и threshold_seconds; одно событие heartbeat не содержит факт будущего молчания.

Ошибочное/повторное событие не должно запускать повторную обработку. При дубле одинакового event_id и payload возвращаем idempotent ответ; при другом payload — 409.

## 5. Выполнение правил

Граница прямоугольника считается внутри. Сначала определить зону, затем проверить разрешение V1/V2/V3; наличие машины в зоне само по себе ещё не нарушение.

Событие прохода содержит employee_id и building_id; запрещённый проход становится происшествием. Информация о допуске берётся из site config/базы.

Heartbeat проверяется по received_at серверных часов. Проверка таймером раз в секунду; для demo offline_threshold=5 секунд. На одну активную потерю связи — одно открытое происшествие, не по одному каждую секунду. После возврата отмечаем восстановление; история не удаляется.

## 6. Нейросеть

Окно 10 секунд, шаг 5 секунд, минимум 6 position samples. Времена и признаки одинаковы в training и inference. Для задержанных/неполных окон возвращаем insufficient_data, без выдуманного score.

Фиксируем feature_version=movement-v1 и семь числовых признаков в CONTRACTS. Все преобразования сохраняются вместе с MLP в одном Pipeline. Не обучаем сеть на каждом HTTP-запросе; загружаем готовый артефакт один раз.

Модель обучается на синтетических эпизодах normal/anomaly. Сети не передаём готовые метки нарушения/допуска: иначе она просто повторит точное правило. Score — выход классификатора, а не доказанная вероятность опасности.

Порог выбирается на validation и сохраняется с версией артефакта. Training/test split по episode_id, а не соседним окнам одного эпизода. Сравнение с простым baseline обязательно.

## 7. Агент с локальной LLM

Внешний API модели по умолчанию не используется. Ollama слушает локальный адрес 127.0.0.1:11434; модель вызывается через POST /api/chat. Наличие локального HTTP API не означает оплату внешнему поставщику.

Один запрос диспетчера создаёт agent_job. Внешний цикл:
1. Дать id происшествия и схемы разрешённых tools.
2. Модель выбирает tool и аргументы.
3. Код валидирует их и исполняет функцию.
4. Сохранить tool trace, передать результат модели.
5. Повторить в пределах бюджета или получить итог.
6. Проверить evidence итогового ответа и сохранить результат.

Бюджет MVP: один активный agent_job, максимум 3 обращения к модели, суммарно максимум 6 tool calls, общая цель времени до 60 секунд. Это проектные ограничения; фактическую скорость измеряем на demo-машине. Локальный клиент задаёт timeout оставшегося бюджета. Бесконечных повторов нет.

Tools читают базу и регламент. Они не выполняют произвольные команды, SQL от модели или изменения фактов. Диспетчер сам изменяет статус происшествия через обычный интерфейс.

## 8. Очереди и устойчивость

Приём данных и карта не ждут LLM. Agent_jobs принимаются с 202; интерфейс опрашивает статус. Один worker обрабатывает очередь, повторное обращение к тому же snapshot использует готовый результат.

Snapshot содержит incident_id, evidence ids, версии правил и модели. Новые evidence инвалидируют старый анализ; не выдаём старое объяснение за новое.

Для MVP SQLite — один writer и короткие транзакции. Вызов LLM, обучение и долгие вычисления выполняются вне DB-транзакции. Сеть/model worker не блокируют event loop сервера. В MVP agent worker — одна асинхронная очередь внутри lifespan приложения; Ollama работает отдельным процессом. CPU inference выполняем через thread executor, обучение отдельной командой. Server scheduler стартует один раз, без нескольких uvicorn workers.

## 9. Статусы подсистем

Rules: ready. ML: not_trained / ready / insufficient_data / error. Agent: unavailable / queued / running / completed / failed.

Если MLP не загружена, показываем отсутствие анализа, а не normal. Если Ollama выключена, сохраняем факты и показываем agent unavailable. Нет скрытого автоматического перехода на внешний API.

## 10. Что подтверждаем

Работу правил — тестами сценариев. Обучение — собственным артефактом и отчётом. Агентность — видимым trace реальных tool calls. Независимость слоёв — отключением LLM без остановки мониторинга.

Это компактная архитектура хакатона, а не сертифицированная система управления реальным производством.
