# Как передать и подключить ML/ИИ после базовой версии v6

Проверка 8 октября 2026: чтение Git и отдельных локальных файлов, без запуска
LLM, обучения, установки библиотек, загрузки весов или объединения чужого кода.
Основа этого документа: `be305a359099088dcb9cd440629b2e0913e63dbc`.
Работы Егора С./М. и независимая поставка Гриши/Гаджи остаются разными задачами.

## 2. Какие точки подключения уже есть в основном сервере

`src/core/main.py` ожидает такие интерфейсы, когда владелец реально передаст файлы:

| Модуль | Ожидаемый интерфейс | Включение |
| --- | --- | --- |
| src/simulator/run.py | DemoRunner(service), SCENARIOS; start/stop/status | DISPATCH_ENABLE_SIMULATOR=1 |
| src/ml/movement.py | MovementModel(); metadata, health(), evaluate(asset_id,events,as_of) | DISPATCH_ENABLE_ML=1 |
| src/agent/runtime.py | AgentManager(service,db_path), make_router(manager,validate_operator); start/stop/health | DISPATCH_ENABLE_AGENT=1 |

Без этих файлов включение переменной не создаёт реализацию: сервер сообщает
недоступность модуля. Базовый встроенный источник `src/core/demo_traffic.py`
работает отдельно. GET /api/health показывает отдельные состояния rules/ml/agent;
отсутствие LLM не должно отключать карту, правила и реакции диспетчеров.
Контрольный GET старого preview `127.0.0.1:8772` при подготовке документа показал
rules=ready, ml=unavailable, agent=unavailable. Этот preview не служит приёмкой v6.

Сервер уже опрашивает ML каждые 5 секунд по окну последних 10 секунд и сохраняет
результат через `Service.register_model_observation`. Нужны реальные position
и минимум 6 достаточных samples по movement-v1, а не нарисованная UI-анимация.
GET /api/model-observations возвращает сохранённые оценки; импорт модуля сам
по себе ещё не означает health=ready.

Агент должен предоставлять POST /api/incidents/{id}/analysis → 202 job и
GET /api/agent-jobs/{job_id} → queued/running/completed/failed. Без подключённого
модуля POST возвращает 503 unavailable. Его внутренние tools читают query-функции
Service: get_incident, event_history, asset_policy, sensor_health. Они не меняют
ownership, происшествия, допуски, транспорт или ворота.

## 3. Что надо исправить в найденных кандидатах до передачи

1. **Гаджи — начальная готовность.** Локальный AgentManager начинает с
   availability=False; provider.available() вызывается только в submit.
   Интерфейс отключает кнопку анализа при unavailable, поэтому первый анализ
   через UI не сможет сам включить readiness. Нужна ограниченная проверка
   реального provider при запуске/фоновом обновлении состояния, с понятной
   ошибкой и без блокирования polling. Это задача владельца агента.
2. **Гаджи — реальный runtime.** LocalModelClient использует LOCAL_MODEL_URL
   (по умолчанию http://127.0.0.1:1234/v1) и LOCAL_MODEL_ID. Разрешены только
   loopback-адреса. Клиент читает /models и вызывает /chat/completions с tools.
   Требуется настоящий tool call и проверенный JSON с evidence. Ответ /models
   и название модели ещё не подтверждают поддержку tools. Здесь LLM не запускали;
   GGUF/другие большие веса в проверенных Git-снимках не найдены.
3. **Гриша — зависимости артефакта.** Локальные requirements/metadata указывают
   scikit-learn 1.7.2, numpy 2.4.6, scipy 1.17.1, joblib 1.6.0, а requirements
   кандидата дополнительно threadpoolctl 3.7.0. Основная поставка содержит только
   FastAPI/Uvicorn/httpx/Pydantic. MovementModel проверяет версию sklearn и хеш;
   согласуйте зависимости отдельным изменением, не устанавливайте их наугад.
   Путь кандидата по умолчанию — artifacts/demo/movement-v1.joblib и соседний JSON.
4. **Гриша — актуальная карта и смена.** Старый Source содержит жёсткие координаты
   прежней карты, проходы через ACCESS-O1 и всего шесть сценариев. Он не сохраняет
   нынешний КПП ACCESS-G1 и порядок «подтверждённые люди → транспорт одной смены».
   При DISPATCH_ENABLE_SIMULATOR=1 он заменит встроенный источник целиком.
   Поэтому нельзя включать его до адаптации к актуальному site.json и проверки
   [GATE_SHIFT_V5](GATE_SHIFT_V5.md). Одновременно два источника не запускают.
5. **Гриша — HTTP-режим.** Старый CLI делает GET /api/site без сессии и
   POST /api/events без X-Source-Key. В нынешней версии это не работает.
   Нужно согласовать отдельное получение конфигурации и аутентифицированное
   чтение, а при внешней отправке — секрет DISPATCH_SOURCE_KEY. Встроенный
   Python-вызов Service не требует браузерной сессии или source key.

Агентский роутер внутри приложения получает профиль от middleware сессии;
подставленный пользователем X-Demo-Operator или URL не назначает личность.
POST анализа требует cookie, X-CSRF-Token и тот же Origin. Внешний операторский
HTTP-клиент должен отдельно войти и получить session/CSRF. X-Expected-User
необязателен для программного клиента, но защищает браузер от смены cookie в
соседней вкладке. Нельзя ради интеграции отключать авторизацию основного сервера.

## 4. Новые детерминированные происшествия и модель

`route_deviation` и `collision` относятся к правилам серверной части, а не к
результату MLP/LLM. В прочитанных удалённых AI-снимках их реализации нет.
При их передаче согласуйте поля Incident/details, evidence и состояние unknown/
restored, реакцию диспетчера и текст карты. Название collision в демонстрации
должно сопровождаться точным определением наблюдаемого условия/порога на плане;
оно не означает проверенную вероятность реальной аварии.

Модель movement-v1 оценивает необычное движение одного объекта. Её score не
подменяет детерминированное событие и не является вероятностью столкновения.
Для парного случая агенту нужны подтверждающие события обоих транспортных
объектов. Найденный кандидат materialize_history ограничивает историю основным
entity_id; проверить второй объект/evidence должен Гаджи. ИИ не может закрыть
или переименовать подтверждённое правило лишь потому, что score оказался низким.
Проверка нового случая с отключённым ML/LLM обязательна.

## 5. Что попросить у второго исполнителя

Передайте Грише и Гаджи такой запрос:

> Подготовьте поставку от актуального main с авторизацией, КПП и текущим site.json.
> Пришлите ветку/PR и полный SHA кода, список разрешённых файлов, команды проверок
> с фактическими результатами, список зависимостей, артефакт+metadata+SHA256 и
> способ передачи локальных весов отдельно от Git. Для агента — runtime/model ID,
> реальный tool_trace/evidence, ограниченную очередь и поведение при недоступной
> модели. Сохраните cookie/CSRF/source key, один источник событий и semantics смены.
> Укажите NOT RUN для неподтверждённых устройств, TLS и полного совместного показа.

Гриша передаёт source/ML/артефакт и отчёт; Гаджи — runtime, tools, очередь и
подтверждённый ответ модели; Егор С. интегрирует точки подключения; Егор М.
проверяет job/UI; Лия проверяет три клиента и общий SHA. Крупные веса не кладут
на диск C: или в Git; владельцы отдельно выбирают место и проверяют свободное
место/RAM/VRAM. Наличие RTX в названии ветки не является замером устройства.

Если владельцы используют найденные файлы Integration, каждый создаёт чистую
личную ветку от актуального main и переносит только свою согласованную поставку:

- Гаджи: src/agent/runtime.py, src/agent/__init__.py и свои новые тесты.
- Гриша: src/ml/movement.py, src/ml/train.py, src/ml/__init__.py, небольшой
  artifacts/demo/movement-v1.joblib, соседний movement-v1.json и ML_REPORT.json/.md,
  собственные тесты. Проверенный SHA256 артефакта фиксируется в передаче.
- src/simulator/run.py передаётся отдельно после исправления карты/КПП/авторизации.
  requirements.txt и main.py меняются только согласованно с Егором С.

Владелец просматривает `git diff --cached --name-only` и коммитит перечисленные
файлы своей роли. Не используйте `git add .` в грязной Integration: там лежат
чужие сервер, карта, site.json и инструкции. GitHub должен получить собственный
commit/PR с фактическими файлами и тестами; только его SHA передаётся интегратору.
Коммит одного имени ветки или README не является передачей этих локальных модулей.

## 6. Порядок последующей интеграции координатором

1. Получите поставку с SHA, проверьте diff разрешённых файлов относительно
   актуального main. Создайте отдельную ветку проверки; не копируйте весь старый
   main.py/site.json из Integration и не объединяйте неподготовленный каркас.
2. Сначала передайте только ML и согласованный артефакт. Проверьте реальные
   observations, недостаточные данные, hash/version mismatch, обычные маршруты
   новой карты и ложные тревоги. Обучение в работающем HTTP-сервере не запускайте.
3. Затем подключите агента к уже доступному проверенному runtime. Проверьте
   первый запрос из UI, tools/evidence, очередь/timeout/restart и отказ модели.
4. Внешний симулятор включайте отдельно после совместимости карты/КПП/смены;
   встроенную демонстрацию сохраняйте до подтверждённой замены.
5. Лия проверяет общий SHA, три аутентифицированных клиента, правила без ИИ,
   новые типы, доступы/CSRF и нагрузку на целевом ноутбуке. Только затем
   координатор объединяет согласованную поставку в main.

Команды чтения снимка, когда владелец назвал фактическую ветку:

```powershell
git fetch origin
git rev-parse origin/codex/rtx4060-ai-runtime
git diff --name-status main...origin/codex/rtx4060-ai-runtime
git ls-tree -r --name-only origin/codex/rtx4060-ai-runtime src/agent src/ml src/simulator artifacts
```

После передачи и проверки модулей, в отдельной интеграционной среде:

```powershell
$env:DISPATCH_ENABLE_ML='1'
$env:DISPATCH_ENABLE_AGENT='1'
$env:LOCAL_MODEL_URL='http://127.0.0.1:1234/v1'
$env:LOCAL_MODEL_ID='ID, который реально отдаёт ваш runtime'
powershell -ExecutionPolicy Bypass -File scripts/start.ps1
```

Это шаблон включения поставленных модулей, **не команда установки/загрузки модели**.
Сейчас подтверждены только чтение файлов, ссылки Git и хеш локального артефакта.
LLM/tool-call, совместный inference с v6, целевые ноутбуки и remote TLS — NOT RUN
в этой проверке. Аккаунты и общий сервер описаны в [REMOTE_CLIENT_V6](REMOTE_CLIENT_V6.md).
