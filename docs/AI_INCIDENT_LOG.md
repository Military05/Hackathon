> В текущем дашборде v7 используется «Очистить все» с архивированием через POST /api/incidents/clear. Этот старый административный API удаления не связан с кнопкой новой страницы. Events и ModelObservation сохраняются. См. [ADMIN_WORKSPACES_V7](ADMIN_WORKSPACES_V7.md).

Изменения подготовлены только в `codex/ai-readable-analysis`, от исходного
коммита `4c5ae771b39e584995542d4614a82126d64b629a`. Рабочий сервер не обновлялся.

## Поведение

Карточка анализа показывает прежние проверенные выводы, похожие случаи и записи
диспетчера. Qwen читает всё через `get_incident` из одного сохранённого SQLite-среза.
Похожие случаи: тот же тип, объект (включая второй объект/датчик) и место,
последние 30 календарных дней UTC; текущий случай не включается. Загружаются
последние 20 случаев, до пяти последних записей человека; в карточке до трёх
заметок. Сравнение ограничено сохранённым журналом и не доказывает рост/снижение.
Полный текст и источники сохраняются в технических данных.

«Сохранить заметку» использует существующее авторизованное `record_response`
с `response_code=checked`, ревизией и уникальным request_id. Действие доступно
ответственному за незавершённый случай. Заметка — сообщение человека, а не
подтверждение аварии, причины или прекращения нарушения. Инструкции внутри
заметки не должны выполняться моделью. Строгое совпадение ID/поля/значения
дополнено источниками `incident_history` и `dispatcher_note`; свободные объяснения
Qwen по-прежнему не становятся подтверждёнными фактами.

«Повторяемость случаев» запускает анализ выбранного случая (или первого
доступного). При пустом журнале показывается предупреждение без обращения к ИИ.
Это резюме похожих случаев, а не прогноз общей динамики предприятия.

## Очистка, включая активные происшествия

Кнопка «Очистить журнал» доступна администратору. GET
`/api/admin/incident-log/preview` возвращает количество, предупреждение и токен
состава журнала. Только после подтверждения браузер отправляет POST
`/api/admin/incident-log/clear` с `confirmation=DELETE_INCIDENT_LOG` и токеном.
Сессия, CSRF и Expected-User сохраняются. При изменении набора происшествий
подтверждение нужно повторить; обновление измерений существующего случая само
по себе не мешает подтвердить очистку.

Одна транзакция удаляет **все активные и завершённые происшествия**, связанные
заметки, историю обработки, передачи, уведомления, ответы повторных команд и
сохранённые задания/результаты ИИ. Это удаление записей SQLite, а не фильтр UI.
Аккаунты, сессии, файл SQLite и исходные события датчиков сохраняются.
Интерфейсное восстановление удалённого журнала невозможно; анализ удалённых
случаев недоступен. При продолжающемся нарушении новые сигналы могут создать
новое происшествие. Уже существующие внешние резервные копии не изменяются.

Очистка блокируется при queued/running-анализе. Счётчик поколения журнала
предотвращает постановку старого среза в очередь после очистки. Запоздалые
ответы UI до удаления отбрасываются. Для журнала свыше 2000 случаев очистка
отклоняется и требует отдельного обслуживания, без частичного удаления.

## Установка

До отдельного подтверждения не устанавливать на сервер 8000 и не объединять
с main. После подтверждения: свежая SQLite-копия через Connection.backup(),
перенос согласованного кода с проверкой рабочего SHA, проверки, согласованный
перезапуск с прежним абсолютным DISPATCH_DB. Саму очистку при установке не выполнять.
