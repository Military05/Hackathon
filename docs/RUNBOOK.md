# Запуск и повторение демо

Если слово незнакомо, открой [словарь простыми словами](GLOSSARY.md). Команды и названия полей не переводим: в коде они должны остаться точными.

**Мониторинг пока содержит структуру и инструкции; QA-инструмент уже реализован.** requirements.txt, перечисленные ниже серверные .py, данные и обученный артефакт ещё должны создать владельцы. Команды серверного запуска ниже — целевой интерфейс: автор реализует его либо меняет этот файл в том же PR (запрос на объединение изменений). Нельзя ставить «проверено» до повторения другим участником.

## Автоматическая проверка для Лии

Python 3.11+, дополнительных библиотек для QA не нужно:

~~~powershell
python -m unittest discover -s tests/qa -p 'test_*.py' -v
python scripts/qa_run.py --report runtime/qa/report.html
~~~

Первая команда проверяет QA-инструмент на тестовом HTTP-сервере. Вторая без разрешения записи сохраняет BLOCKED и возвращает код 2. Для настоящего прогона подготовьте отдельный QA-стенд и конфигурацию, затем используйте `--allow-demo-writes`: [полная инструкция](QA_AUTORUN.md). Результат — HTML и JSON рядом; отсутствие сервера не считается успешной проверкой.

## Целевой базовый запуск — Егор С. (A1)

Егор С. (A1) создаёт и проверяет requirements.txt с закреплёнными совместимыми версиями fastapi,uvicorn,httpx,numpy,scikit-learn,joblib,pytest. Не пишем выдуманные версии. Не добавляем Node/Docker без необходимости.

~~~powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m src.core.main --init-demo
.\.venv\Scripts\python.exe -m uvicorn src.core.main:app --host 127.0.0.1 --port 8000
~~~

--init-demo создаёт runtime базу из site.json, повторный запуск не удаляет историю. Отдельный явно описанный --reset-demo допускается только для demo-базы; Лия (QA — тестировщик) проверяет его область. Сервер один worker (обработчик задач), scheduler (таймер фоновых проверок) запускается один раз. Не нужен PowerShell Activate: вызываем venv Python напрямую.

Открыть http://127.0.0.1:8000, проверить /api/health. Остановка Ctrl+C. Состояние сохраняется в runtime/demo.sqlite, путь документирует Егор С. (A1).

## Целевой симулятор — Гриша (B2), второе окно терминала

~~~powershell
.\.venv\Scripts\python.exe -m src.simulator.run --scenario normal --seed 42 --base-url http://127.0.0.1:8000
~~~

Сценарии: normal (обычное поведение),forbidden-zone,unauthorized-access,sensor-offline,unusual-movement. Каждый имеет seed (начальное число для повторяемой генерации), уникальные event ids и печатает краткие ожидаемые изменения. Повторный run получает новый run_id, чтобы не столкнуться с event-idempotency. Отдельный режим replay (повтор заранее сохранённых данных) сохраняет id для проверки дублей. Сценарий offline сначала посылает heartbeat, затем замолкает. Все события demo (демонстрационные данные)=true.

## Целевое обучение и оценка — Гриша (B2)

~~~powershell
.\.venv\Scripts\python.exe -m src.ml.generate --seed 42 --output data/generated
.\.venv\Scripts\python.exe -m src.ml.train --input data/generated --output artifacts/local
.\.venv\Scripts\python.exe -m src.ml.evaluate --input data/generated --model artifacts/local/movement.joblib
~~~

Файлы split (разделение данных) metadata и test (итоговая тестовая часть данных) report сохраняются; README и ML_REPORT фиксируют фактические параметры. Обучение отдельной командой, не во время обработки событий. Если CLI (запуск и управление командами в терминале) отличается, Гриша (B2) обновляет эту страницу до передачи Лия (QA — тестировщик).

Артефакт joblib загружаем только от своей команды. Для повторяемости фиксируем hash (контрольный отпечаток файла) и версии библиотек; не загружаем случайные чужие pickle/joblib файлы. Сервер после перезапуска читает согласованный путь артефакта.

## Локальная LLM — Гаджи (B1), сначала Bionic/LM Studio

Локальный агент обязателен в финальной версии; мониторинг и координация продолжаются при его недоступности. Установленную версию Bionic и характеристики ноутбука пока не подтвердили. Сначала используем имеющиеся веса; большие файлы на машине владельца храним на E:.

1. Для LM Studio Bionic: Settings → Local Models → Library; выбрать скачанную Local-модель в сессии. Не Cloud/Remote для автономного показа на одном ноутбуке. [Официальная библиотека](https://lmstudio.ai/docs/bionic/models/download-local-models).
2. Подтвердить API именно установленной версии. Bionic — отдельное приложение: нельзя переносить в него названия экранов LM Studio без проверки. [Различие](https://lmstudio.ai/docs/bionic).
3. Подтверждённый серверный путь LM Studio: Developer → загрузить подходящую модель → Start server. Записать фактический base URL/порт/авторизацию. [Server](https://lmstudio.ai/docs/developer/core/server).
4. Проверить GET /v1/models и POST /v1/chat/completions с tools; получить структурированный tool_calls, выполнить нашу функцию, вернуть результат, получить ответ. [Tools](https://lmstudio.ai/docs/developer/openai-compat/tools). Ответ в обычном чате не подтверждает агентность.

Пример проверки только если сервер действительно показывает 127.0.0.1:1234 и не требует авторизации:

```powershell
Invoke-RestMethod -Uri "http://127.0.0.1:1234/v1/models"
```

Целевые переменные приложения (ещё реализовать): LOCAL_LLM_PROVIDER=openai_compatible, LOCAL_LLM_BASE_URL=http://127.0.0.1:1234/v1, LOCAL_LLM_MODEL=<точный ID из /v1/models>, LOCAL_LLM_API_KEY=<только если требует сервер>. Ключ не писать в Git. Гаджи добавляет .env.example без секретов и документирует фактический способ загрузки конфига; наличие файла .env само по себе не означает чтения приложением.

Резерв после проверки совместимости: provider=ollama, base URL=http://127.0.0.1:11434, модель по фактическому ollama list. Для Ollama API /api/chat, а не /v1/chat/completions; адаптер нормализует tools/ответ. Кандидат qwen3:4b не гарантия скорости. По официальной [FAQ](https://docs.ollama.com/faq) веса можно разместить через OLLAMA_MODELS на E:; OLLAMA_NO_CLOUD=1. Не устанавливать второй runtime и не скачивать веса повторно без необходимости.

TEAM: модель/квантование/runtime/API/CPU/RAM/GPU/VRAM/свободное место/версии/реальный tool call/время. Очередь: 1 running, 20 queued, 120 сек ожидания, 60 выполнения, max 3 запросов/6 инструментов. Превышение — понятная ошибка, не остановка тревог. Автоматического облачного переключения нет.

## Целевые проверки — Лия (QA — тестировщик) и авторы

~~~powershell
.\.venv\Scripts\python.exe -m pytest
~~~

Лия (QA — тестировщик) также выполняет ручные сценарии из TESTING, проверяет отключение локального модельного сервера, неизвестную модель, отсутствие trained artifact и сетевую ошибку. Отчёт всегда привязан к git rev-parse HEAD (ветка или версия с предлагаемыми изменениями).

## Ошибки

- Module not found / отсутствует requirements: сначала проверить реализован ли соответствующий PR; это руководство не установило приложение.
- Порт занят: остановить предыдущий свой сервер или согласовать новый порт и base-url симулятора.
- Пустая карта: /api/site, /api/assets, network ошибки; проверить одинаковые id.
- Агент unavailable: проверить выбранный runtime, модель и реальный API (способ обмена данными с сервером); мониторинг не должен останавливаться.
- ML (машинное обучение) not_trained: выполнить обучение, проверить путь и версии; не подменять отсутствие модели значением normal.
- SQLite locked: убрать второй сервер/writer и длинные транзакции; не удалять базу как универсальное «исправление».

## Три рабочих места и координация — целевой запуск

После реализации открыть три окна с адресами http://127.0.0.1:8000/?operator=dispatcher-1, http://127.0.0.1:8000/?operator=dispatcher-2 и http://127.0.0.1:8000/?operator=dispatcher-3. Параметр operator — согласованный целевой UI-интерфейс; пока страницу ещё должен создать Егор М.

Три окна используют одну runtime/demo.sqlite. Каждый клиент выбирает свой профиль, отправляет X-Demo-Operator и presence; не запускаем три серверных процесса на общей базе. Критерий: D5 → свои случаи на трёх экранах; D6 → один победитель; D7 → передача подтверждена; D8 → deadline/escalation; D9 → новая тревога видна; D10 → restart/offline. Все точные пороги и действия в DISPATCH_OPERATIONS.

Сценарии, которые Гриша должен добавить к CLI: simultaneous-incidents, same-sector-burst, unknown-area. D6/D7/D8/D10 выполняют QA-клиенты через операции координации, а не события датчика. Команды публикуются автором вместе с реализацией; сейчас не выдаём их за готовые.

Для трёх компьютеров в доверенной локальной demo-сети: Егор С. настраивает один сервер --host 0.0.0.0, фиксирует LAN IPv4 через ipconfig и доступ Windows Firewall только для нужной частной сети/порта. Клиенты используют http://<IPv4-сервера>:8000; localhost на другом компьютере означает его самого. Интернет не нужен, локальное соединение нужно. LLM можно оставить на loopback сервера. Внешний интернет-доступ серверу не открываем.

## Подготовить автономный ноутбук заранее

1. Проверить Python/совместимые версии, runtime и CPU/RAM/GPU/VRAM; веса локальной модели должны помещаться и реально вызывать tools.
2. Установить зависимости пока интернет есть. Для повторной offline установки Егор С. на целевой Windows/Python готовит runtime/wheelhouse через python -m pip download -r requirements.txt -d runtime/wheelhouse, проверяет install --no-index --find-links runtime/wheelhouse -r requirements.txt. Wheels должны совпадать с ОС/архитектурой/Python; отсутствие готового wheel фиксируется до защиты.
3. Гриша переносит artifacts/local/movement.joblib и метаданные/порог/версии/hash. Собственное обучение на ПК, применение на ноутбуке; train dataset не нужен для inference, но simulator/fixtures нужны для демо.
4. Гаджи переносит проверенные веса и конфигурацию runtime, проверяет загрузку на ноутбуке, не предполагает совместимость одного формата весов со всеми runtime.
5. Егор М. убирает CDN/внешние шрифты/JS/иконки. Старый docs/ui HTML не считается автономным финальным интерфейсом.
6. Лия отключает интернет, перезапускает сервер/runtime и проходит D1–D10 + настоящий агент. Отключение интернета не равно выключению локальной сети между demo-компьютерами.

Большие веса/venv/wheelhouse/runtime не коммитим в Git. Инструкция и hash/версии в репозитории; артефакты передаются отдельным комплектом. Установка/запуск считаются подтверждёнными только после независимого повторения.
