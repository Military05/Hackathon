# Ошибка AI-анализа запрещённой зоны

Ветка: codex/ai-server-launch. Исходный коммит:
`9e16af8f4ba31d1cc0c81fdafca885e154df04b5`.
Работающий сервер и рабочие происшествия не перезапускались и не изменялись
проверочными запросами. Срез рабочего задания читался из checkpoint SQLite
без записи; наличие WAL на момент чтения не обнаружено. Проверочные задания
сохранялись только в новых отдельных SQLite-базах.

## Диагностика

Сохранённое задание `aj-f9db5e7ca2fe41789612467fc38d14fc`:
type forbidden_zone, asset V1, status failed,
code model_reply_invalid, details.reason invalid_json.
Это происшествие независимого правила запрещённой зоны, не model_anomaly MLP.
Связанная последняя оценка MLP может присутствовать в срезе как дополнительные
данные; её статус не отменяет запрет зоны.

Сырой ответ исходного рабочего запроса не сохранялся приложением. На том же
сохранённом срезе повтор с прежним кодом воспроизвёл причину: первый запрос
выполнил get_incident; второй и третий ответы имели finish_reason=length,
1009 символов content и обрывались внутри event ID. Лимит max_tokens=450
не соответствовал потенциально длинному ответу (до 20 facts и свободные тексты).
Провайдеру подавалась схема, но она не предотвращает обрыв по лимиту.
Клиент терял finish_reason; обрезанный JSON доходил до json.loads, которое
возвращало invalid_json. Добавлять скобки или дополнять ID было бы неверно.

ModelAnswer требует facts, hypotheses, recommendations, запрещает лишние поля.
Каждый факт содержит source, id, field, value; разрешённые source:
event, policy, sensor_health, model_observation. Последующая проверка требует
точного совпадения ID/поля/JSON-значения с реально выполненными tools.
Эти проверки и требование status/score/threshold для MLP не ослаблены.

stale вычисляется независимо от ошибки: текущий snapshot_id или execution
отличается от сохранённого. Срез включает ограниченную историю событий,
последнюю MLP observation, состояние происшествия, политики и здоровье источника.
В диагностике исходный срез as_of 07:11:26.270Z содержал последнее событие
07:11:25.465Z и observation mo-5496be3ef1d2b85df8701cb3; последующий checkpoint
содержал событие 07:18:15.467Z и observation mo-4c461832bd080a07bab18db4.
Одно движение/новая MLP observation может изменить analytical hash. Поэтому
stale не означает ошибку JSON и не снимает требование проверки фактов.

## Исправление

- model_client.py распознаёт finish_reason/done_reason length и отклоняет
  незавершённый ответ отдельно; structured final имеет максимум 1024 токена,
  вызовы tools — прежние 450. Общие бюджеты 60 секунд/3 запроса/6 tools сохранены.
- loop.py ограничивает финал тремя фактами, одной короткой гипотезой и двумя
  короткими рекомендациями; свободный ответ не публикуется, финал генерируется
  по схеме. Для обычных происшествий кандидаты фактов — только буквальные
  значения прочитанных tools, не произвольные ID и значения.
- Некоторые движки схем считают 25 и 25.0 взаимозаменяемыми. Строгая проверка
  JSON-типов сохраняется: целочисленные float-кандидаты не предлагаются в общей
  enum-схеме. Значения не округляются и не исправляются после генерации.
- result.py содержит понятные русские ошибки формата; json.loads/Pydantic и
  независимая проверка фактов остаются обязательными.
- app.js для failed/queued/running пишет «Данные изменились после начала
  запроса»; «УСТАРЕЛ» остаётся для completed результата. stale не скрывается.
- replay_agent_snapshot.py воспроизводит сохранённый срез через настоящие
  queue/worker/JobStore/Qwen в новой тестовой базе; существующие базы запрещены.
- Автотесты проверяют length даже при синтаксически корректном content, bounded
  retry, отклонение ложных значений, буквальные кандидаты/JSON-типы и надпись stale.

Во время подготовки первый повтор в тестовой очереди выявил несовпадение
значения; он был отклонён и не объявлялся успешным. После ограничения точных
кандидатов и исключения неоднозначных float повтор стал completed:
`zone-fix-test-job-20261008-d.db`, 3 проверенных факта, stale=false,
15.094 секунды, production_database_accessed=false.
Подробные срезы и ответы находятся в artifacts/local и не коммитятся.
Отдельный live HTTP сценарий MLP D4 после изменения: PASS, 19.687 секунды,
проверены обязательные status/score/threshold. Node-набор: 72 PASS;
AI/ML: 72 PASS; QA: 18 PASS. Полный runtime набор после обновления ожиданий
лимита и обязательной structured final фазы: 121 PASS. Всего 283 теста PASS.
В процессе расширения схемы обнаружены и исправлены несовместимые ожидания
тестовых провайдеров и доступ к прежним properties в sensor_offline;
итоговые наборы повторены успешно. Проверки ложных фактов не отменялись.

Применение Python-исправления к уже работающему процессу требует отдельного
согласованного штатного перезапуска; автоматически он не выполнялся.
До переключения сделать свежий backup API, подтвердить точный код/DB/PID.
Запустить эту ветку тем же единым скриптом с явным прежним Database; не
восстанавливать старую резервную копию поверх живой базы. После переключения
войти существующим аккаунтом и запросить новый анализ. Старое failed-задание
остаётся в истории; prompt_version изменён, прежний результат не используется
как новый. Объединение main в эту подготовку не входит.
