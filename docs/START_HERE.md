## 3. Первые 30 минут

- Принять приглашение GitHub и клонировать проект.
- Убедиться, что origin — Military05/Hackathon.
- Вписать готовность в TEAM через свою docs-ветку и PR.
- Получить назначенную Issue: один результат, личная ветка, файлы, проверка.
- Согласовать контракт v1: часы, координаты, поля событий, ошибки.
- Проверить у организаторов, можно ли использовать условное предприятие и симулятор.
- B1 начинает проверку локальной LLM; B2 готовит простые нормальные события для первого запуска.

## 4. Как понимать текущие документы

Стек ниже — принятое предложение для старта, а не уже реализованный код:
Python 3.11+, FastAPI, SQLite, HTML/CSS/JS/SVG; scikit-learn для маленькой MLP; Ollama для локальной языковой модели.

Приложение пока не реализовано. В RUNBOOK команды помечены как целевые и начинают работать после создания перечисленных файлов. Не считайте существующие README в src готовыми модулями.

## 5. Главные границы

- Сбор показаний и проверка формата — обычный код.
- Геометрия зон, допуски и потеря связи — точные правила.
- Собственная MLP — оценка необычного движения, на обученных примерах.
- Локальная LLM — чтение истории через инструменты, объяснение и рекомендации.
- Один агент достаточен для двух дней. Разные обычные модули не называем отдельными ИИ-агентами.
- Карта показывает факты отдельно от предположений модели.

## 6. Ветки

A1/A2 сначала направляют личные PR в main. После короткой проверки beta-1 координатор B1 создаёт feature/beta1-f1. B1 и B2 создают личные ветки от неё и направляют PR в неё.

QA сразу проверяет beta-1 на фиксированном SHA; полная проверка не задерживает старт обеих пар. Команды веток есть в инструкции каждой роли.

## 7. Что писать при передаче

«Issue ..., PR ..., base ..., head ..., SHA ..., что проверить ..., ожидается ...».
Блокировка: конкретная ошибка, файл, кому нужен ответ. Незавершённый PR — Draft.

Основной результат: воспроизводимый совместный main, который показывает правила, нейросеть и локального агента с отдельными источниками доказательств.
