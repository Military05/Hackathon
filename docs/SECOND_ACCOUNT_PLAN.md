# Два аккаунта ChatGPT: что поручить второму помощнику

## Актуальные границы помощников v2

Цель B1 — общий локальный агент для трёх рабочих мест; [DISPATCH_OPERATIONS](DISPATCH_OPERATIONS.md). Первый помощник: проверенный Bionic/LM Studio API, loop/jobs. Второй: tools/schemas/provider/evidence; отдельные клоны и файлы. Ollama резерв, не обязательная установка. Общая очередь 1 running/2 queued/120 секунд ожидания/60 выполнения. Demo-профиль автора анализа не назначает owner.

Передача, присутствие и эскалация обязательны в продукте, но принадлежат Егору С./Егору М.; помощники Гаджи не переписывают их модули. Старые задания ниже читаются вместе с CONTRACTS v2, не расширяют полномочия модели. Никакой автоматической связи двух аккаунтов не обещаем.

План для Гаджи: задание №3, команда из пяти человек. Это два помощника разработчика на одном участке, а не два новых участника команды и не два агента внутри продукта.

## 1. Что сейчас есть

На момент подготовки плана main содержит инструкции и README каталогов. Python-модули, сервер, модель и тесты приложения ещё не написаны. Перед началом второй помощник заново проверяет текущую ветку и файлы: команда могла уже добавить код.

Не запускай команду приложения, если соответствующего файла ещё нет. Не проси помощника «сразу сделать всё».

## 2. Как подключить второй аккаунт

1. В отдельном профиле браузера войди во второй аккаунт ChatGPT. Отдельный профиль помогает различать аккаунты.
2. Открой установленный плагин GitHub или установи его из доступного каталога. Выполни предложенное подключение и авторизацию GitHub.
3. Выбери доступ к Military05/Hackathon в предлагаемом процессе настройки.
4. В новом чате попроси прочитать docs/TEAM.md и назвать участников, затем показать последний коммит main.
5. В первом аккаунте тоже проверь чтение. Совместная привязка двух ChatGPT к одному GitHub-логину не подтверждена явно в найденной документации; этот шаг проверяет фактическую работу вашей конфигурации.
6. Если нужны изменения, отдельно убедись, что плагин разрешает запись/ветки/PR. Одно чтение публичного файла не доказывает авторизацию и право изменять проект.

Если оба подключения не работают одновременно, для Codex с локальным окружением можно работать с отдельными клонами: GitHub-плагин для изменения локального кода не обязателен. Вход ChatGPT, доступ к локальным файлам и Git-авторизация — разные настройки. Применимость зависит от выбранного клиента.

Не запускай двух помощников в одной локальной папке: переключение ветки одним изменит файлы другого. Используй отдельные клоны, например Hackathon-primary и Hackathon-secondary. Удалённая работа через плагин тоже идёт в разных ветках.

## 3. Рекомендуемое разделение

| Кто | Работа | Файлы |
| --- | --- | --- |
| Гаджи + первый помощник | Bionic/LM Studio API, реальный вызов инструментов, затем ограниченный цикл агента | src/agent/model_client.py, orchestrator.py, jobs.py |
| Гаджи + второй помощник | Список инструментов, проверка параметров, проверка ссылок на события | src/agent/tools.py, schemas.py, providers.py, evidence.py; tests/agent/ |
| Егор С. | API, SQLite, правила и подключение общих маршрутов | src/core/, src/storage/, requirements.txt |
| Егор М. | Основная карта и интерфейс | src/interface/web/ |
| Гриша | Симулятор, признаки и нейросеть | src/simulator/, src/ml/ |
| Лия | Сценарии, журнал и проверка результата | docs/TESTING.md и согласованные тесты |

Первый и второй помощники не редактируют одни и те же файлы. Гаджи отвечает за обе работы, проверяет результат и передаёт Лии. Задачи других разработчиков не берём без договорённости.

Сейчас не нужен второй автономный диспетчер внутри продукта. Достаточно одного локального агента с ограниченным набором инструментов.

## 4. Что можно сделать сегодня

Сначала подтвердите допустимость заранее написанного кода по регламенту. Если его нельзя готовить до старта, сегодня только подключение, чтение, согласование и план; код пишете после официального начала.

### Шаг 1 — самостоятельный модуль инструментов

Второй помощник создаёт:
- явный список четырёх разрешённых функций;
- схемы параметров;
- проверку типов, обязательных полей, неизвестных параметров, идентификаторов, дат и limit;
- вызов переданного поставщика данных;
- контролируемые ошибки, без произвольного SQL, команд или URL.

Функции из CONTRACTS:
1. get_incident(incident_id) — карточка происшествия.
2. get_event_history(asset_id,since,until,limit) — история, максимум 100 событий.
3. get_asset_policy(asset_id) — допуски и policy_version.
4. get_sensor_health(sensor_id) — состояние датчика.

Поставщик данных — небольшой интерфейс к функциям чтения. На первом этапе тесты дают заранее заданные примеры; позже Егор С. подключит реальные query-функции базы. Не создаём вторую независимую базу и не меняем сервер.

Согласуйте интерфейс поставщика с Егором С. до интеграции. Тестовые данные явно названы тестовыми, а не подключением настоящего предприятия.

### Шаг 2 — проверка исходных событий

После готовности инструментов второй помощник добавляет проверку:
- event_id из ответа присутствует среди событий, полученных разрешёнными инструментами;
- для фактов о допуске получена указанная версия разрешений;
- отсутствующие и выдуманные ссылки отклоняются;
- снимок данных и версии совпадают с анализируемым происшествием.

Проверка ссылок не доказывает, что любой текст модели логически верен. Совпадение фактов и корректность выводов дополнительно проверяют Гаджи и Лия.

### Шаг 3 — реальные проверки модуля

Минимум:
- допустимый вызов каждого инструмента;
- неизвестный инструмент и объект;
- неверная дата, since>until, limit<=0 и limit>100;
- лишний параметр;
- настоящий и выдуманный event_id;
- неизвестная версия разрешений;
- отсутствие побочных записей у чтения.

Для первой автономной задачи можно использовать unittest из стандартной библиотеки Python: не менять общий requirements.txt ради тестов. Команду автор проверяет в доступном окружении. Если выполнен только просмотр кода, так и написать.

Тесты должны проверять поведение на границах, а не просто повторять строки реализации.

## 5. Ветки до и после beta-1

Сегодня, если разработка разрешена: одна личная ветка второго помощника prototype/agent-tools от свежего main. Это временный прототип, не готовая первая бета.

Первый помощник использует отдельную prototype/agent-runtime. Не отправляйте прототипы напрямую в main. Можно публиковать личные ветки; объединение — после согласования с командой.

После beta-1 Гаджи создаёт feature/beta1-f1 по общей инструкции. Во втором клоне, находясь в prototype/agent-tools:
1. Получить изменения: git fetch origin.
2. Убедиться, что нет незакоммиченных файлов.
3. Включить основу: git merge origin/feature/beta1-f1.
4. Решить конфликты вместе с владельцами файлов.
5. Повторить проверки и отправить свою ветку.
6. Открыть PR: base=feature/beta1-f1, compare=prototype/agent-tools.

Обычная рабочая ветка Гаджи feature/f1-agent и ветка второго помощника — обе личные; они направляют PR в одну общую feature/beta1-f1. Первый прототип переносится после просмотра изменений: в клоне первого помощника выполнить git fetch origin, перейти в feature/f1-agent (после её создания от общей ветки) и выполнить git merge origin/prototype/agent-runtime. Затем проверить и направить PR feature/f1-agent → feature/beta1-f1. Один оператор выполняет конкретное объединение.

Не делайте merge чужой незавершённой ветки без передачи результата. Git-команды и разбор конфликтов: [TEAM_WORKFLOW](../TEAM_WORKFLOW.md).

## 6. Готовый первый запрос второму помощнику

Скопируй целиком в новый чат с подключённым GitHub. Он разрешает работу в указанной ветке, но не слияние в main.

~~~text
Работаем в репозитории Military05/Hackathon, задание №3.
Я Гаджи, отвечаю за локального агента. Ты мой второй помощник.
Прочитай docs/SECOND_ACCOUNT_PLAN.md, docs/CONTRACTS.md,
docs/roles/FULLSTACK_AGENT.md и CODEX_USAGE.md.
Проверь актуальный main и перечисли уже существующий код.
Зафиксируй стартовый SHA. Не перезаписывай чужие изменения.

Твоя первая задача — только модуль четырёх read-only инструментов
и проверки их параметров. Создай личную ветку prototype/agent-tools
от актуального main; если она уже существует, сначала изучи её.
Никаких прямых коммитов в main и никаких слияний без моего поручения.

Разрешённые файлы: src/agent/tools.py, src/agent/schemas.py,
src/agent/providers.py, tests/agent/test_tools.py и небольшие
тестовые данные внутри tests/agent/.
Не меняй core, storage, interface, ml, simulator, общие зависимости
и контракт. Не пиши клиента локальной модели, orchestrator или jobs —
это делает первый помощник в других файлах.

Реализуй get_incident, get_event_history, get_asset_policy,
get_sensor_health строго по контракту. Реальные данные позднее
подключит Егор С.; сейчас используй передаваемый интерфейс
поставщика данных и отдельный тестовый поставщик.

Проверь неизвестный инструмент/id, неверные даты, since>until,
limit<=0, limit>100, лишние параметры и успешные вызовы.
Без произвольного SQL, shell, URL и записи в базу.
Не устанавливай Ollama и не скачивай веса модели.

Опубликуй только свою ветку и покажи изменённые файлы,
команду проверки, фактический результат, итоговый SHA
и ограничения. Если окружение не позволяет запускать тесты,
сообщи это прямо. Не выдавай тестовый поставщик за интеграцию.
~~~

Если регламент ещё не разрешает код, замени поручение реализацией на: «Только изучи контракт, предложи интерфейс и проверки, не изменяй репозиторий».

Вторая задача — evidence.py и её проверки; выдавай её отдельным запросом после просмотра первой работы.

## 7. План на завтра

| Момент | Первый помощник / Гаджи | Второй помощник |
| --- | --- | --- |
| Начало | Подтвердить контракт с Егором С., проверить Bionic/LM Studio API и tools | Реализовать/уточнить автономные инструменты |
| Пока пишется основа | Реальный запрос модели → вызов функции → ответ | Проверить ошибки и исходные ссылки |
| После beta-1 | Создать общую ветку и подключить ограниченный цикл | Включить общую основу, PR инструментов в общую ветку |
| Первая интеграция | Подключить настоящие query-функции с Егором С. | Повторить свои проверки на реальных данных |
| Проверка Лии | Живой показ, таймауты, отключение локального модельного сервера | Исправить только свой проверяемый дефект |
| Перед freeze | Запуск, инструкция и совместная версия | Проверка конкретного запроса/исправления |

План по зависимостям, а не обещание, что всё займёт фиксированное число минут. Если инструменты нужны прямо сейчас первому помощнику, заранее согласуйте короткий интерфейс, но не выдавайте временные примеры за работающую систему.

## 8. Как передавать работу между аккаунтами

Второй чат не знает историю первого. Передай:
- репозиторий и ветку;
- задачу и разрешённые файлы;
- текущий контракт;
- SHA и ссылку на изменения;
- выполненные проверки;
- что ещё не подключено.

Шаблон:
~~~text
Готово: ...
Ветка: ...
SHA: ...
Файлы: ...
Проверка: команда / результат.
Ограничения: ...
Нужное подключение: ...
~~~

Не рассчитывай на автоматическую синхронизацию чатов или локальных незапушенных файлов. Общая память проекта — документы, коммиты и PR.

## 9. Источник и границы

[Официальная документация OpenAI об авторизации плагинов](https://developers.openai.com/plugins/build/auth): вызовы используют авторизацию и права выбранного подключения. Эта страница не подтверждает явно одновременную привязку двух аккаунтов ChatGPT к одному GitHub-логину. Доступность плагина, записи и локального исполнения проверяем на ваших аккаунтах отдельно.

Сам факт второго аккаунта не создаёт автоматически задачу и не запускает работу. Нужно открыть чат, подключить доступ и отправить конкретное поручение.
