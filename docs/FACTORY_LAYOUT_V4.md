# Площадка автомобильного завода v4

Исходная версия: `main`, `73e9bbc2adcd6c6f3b89fff71238d2b3893302ad`.
План: `data/demo/site.json`, `layout_version=site-v4-automotive-campus`.
Это схема демонстрационного завода, координаты 0..100 в условных единицах,
ось y направлена вниз; GPS, реальные метры и скорость в км/ч не используются.

## Что находится на карте

18 зданий занимают западную, восточную и центральную части территории.
Главный офис O1 и КПП G1 находятся рядом с юго-западным въездом.
Склады сырья W1, комплектующих W3 и инструмента W4 находятся на северо-западе,
склад готовых автомобилей W2 — на юго-западе.
На востоке расположены прессовый P1, сварочный P3 и сборочный P2 цеха,
окраска P4 и окончательный контроль качества P5. В центре — сборка двигателей
P6, инженерный корпус P7, столовая C1, энергоцентр E1, насосная E2 и медпункт M1.
Пожарный пост F1 расположен у склада готовых автомобилей.

Размеры зданий различаются. Полное `name` используется в карточках;
`short_name` помогает поместить название внутри прямоугольника при уменьшении
карты. `category` и `color` задают визуальную категорию, но не права доступа.

## Дороги и движения

Заводские магистрали, межцеховые проезды, внешние объезды и въезд образуют
одну связанную сеть. Места соединения имеют одинаковые координаты в массиве
`roads[].points`. Скруглённые углы уже представлены набором точек в данных:
транспорт и карта используют одну геометрию. Дорожная разметка не требуется.
Ширина каждого проезда учитывается при проверке расстояния до зданий.

`routes.V1`, `routes.V2`, `routes.V3` — замкнутые последовательности `[x,y]`:

| Транспорт | Основной маршрут |
| --- | --- |
| V1, погрузчик | Сырьё и комплектующие → складской проезд → готовые автомобили |
| V2, погрузчик | Прессово-сварочное производство → сборочный цех → производственный объезд |
| V3, служебная машина | КПП → центральные магистрали → КПП |

Нормальные маршруты не проходят внутри зданий или закрытых зон. Поля
`route_stops` задают предложенные точки остановки на настоящих проездах,
целевое здание и длительность в demo-секундах. Исполнитель движения может
использовать эти точки или рассчитывать ближайшее место к `destination`.

Встроенный демонстрационный источник использует ближайшую точку маршрута к
текущему `destination`; посещение всех перечисленных остановок пока не обещается.
Его режимы, запуск и ограничения описаны в [FACTORY_TRAFFIC_V4](FACTORY_TRAFFIC_V4.md).

Для сценария контролируемого нарушения добавлен отдельный реальный подъезд:
`demo_fault_routes.V1 = {zone_id: "Z1", points: [[25,60],[25,50]]}`.
Первая точка находится на нормальном маршруте V1, последняя — внутри Z1.
При сценарии нарушения машина должна пройти этот отрезок туда и обратно,
затем продолжить нормальный маршрут с той же точки. Мгновенный перенос
координат между зданиями или анимация без серверных Event не нужны.

## Согласование с источником событий

1. Получать план из того же `site.json`, который загружает сервер. Не держать
   прежние координаты зданий и проездов в отдельной копии симулятора.
2. Отправлять настоящие demo position/heartbeat/access Event через общий
   сервис. В JSON события используются прежние asset/sensor/building ID.
3. Нормальный транспорт идёт по `routes`; intentional forbidden-zone проходит
   по `demo_fault_routes`. Скорость вычисляется по длине пути, а не по количеству
   sampled точек: на скруглении не должно быть скачка скорости.
4. Обычная остановка погрузчика не означает потерю датчика. Heartbeat продолжает
   приходить, при необходимости позиция подтверждается повторно.
5. Датчик отключается только в явном сценарии потери связи. Факт восстановления
   подтверждается новым событием, а не зелёной подсветкой интерфейса.
6. Запуск, остановка и выбранный сценарий принадлежат общему серверу, поэтому
   несколько браузерных вкладок не создают несколько источников движения.

Новые здания сами по себе не добавляют новых физических датчиков. Существуют
прежние POS-V1/2/3, ACCESS-O1 и HB-QA; неподтверждённые исправные каналы не
создаются. ACCESS-O1 перенесён к главному офису, HB-QA — к сборочному цеху.
Права сотрудников и транспорта, прямоугольники Z1/Z2 и прежние ID сохранены.
Новые здания требуют отдельного согласования допусков, если команда захочет
проводить через их двери дополнительные access-сценарии.

## Проверка этой геометрии

```powershell
python -m unittest tests.runtime.test_site_layout -v
python -m unittest tests.runtime.test_backend tests.runtime.test_backend_regressions -v
```

На локальном Python 3.11 проверены: 12 тестов плана и 29 backend/regression
тестов — PASS. Проверяются связность сети общими узлами, ширина дорог вне
зданий, путь на оси дорог, отсутствие пересечения нормальных маршрутов с
закрытыми зонами, соседство офиса с КПП, размещение датчиков и отсутствие
пересечения внутренних областей разных диспетчерских секторов.
Эти проверки подтверждают геометрию и совместимость правил. Запуск движения
в браузере, три клиента и измерение производительности целевого ноутбука
проверяются отдельно при общей приёмке.

Прежнюю базу демонстрации не удалять. Для нового показа следует выбрать новый
путь `DISPATCH_DB`, чтобы старые происшествия с прежними координатами не
смешивались с новой площадкой.
