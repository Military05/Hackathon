# Архитектура мониторинга предприятия и ИИ-диспетчера

Предложение для MVP хакатона, 6 октября 2026. Основа: существующие ARCHITECTURE.md и CONTRACTS.md репозитория Military05/Hackathon. Это проект архитектуры, а не отчёт о реализованной системе. Дополнения к контрактам перечислены отдельно.

## Назначение

Оператор видит офис, склады, цеха, КПП и дороги с контрольными зонами. Система получает события датчиков, проверяет точные правила, оценивает необычное движение и показывает происшествия на соответствующих участках. По запросу оператора ИИ объясняет выбранное происшествие, используя сохранённые факты и разрешённые инструменты.

## Интерфейс

[Пример панелей и инструкция просмотра](ui/README.md). Панели используют демонстрационные данные и заранее написанные объяснения.

Главный экран: SVG-план предприятия, карточки участков, общий журнал происшествий. Карточка участка содержит название, число открытых происшествий и состояние датчиков. Отсутствие данных и неисправность датчика отображаются отдельно от отсутствия тревог.

Выбор участка открывает его события, датчики и происшествия. Выбор происшествия открывает факты, доказательства, время обнаружения, состояние условия и операторский статус. В этой же карточке находится анализ ассистента: факты, гипотезы, рекомендации и ссылки на исходные события. Несколько происшествий одного склада имеют отдельные анализы.

Цвет приоритета всегда сопровождается текстом. Статус open/acknowledged/closed изменяет оператор. Возврат машины из зоны или восстановление датчика снимает активность условия, но сохраняет историю. Закрытие карточки оператором не означает физического устранения нарушения.

## Состав системы

| Компонент | Ответственность | Размещение |
|---|---|---|
| Симулятор или адаптер датчиков | Привести данные источника к согласованному Event | Отдельный процесс или внешний источник |
| FastAPI | Приём событий, проверки, запросы интерфейса, управление заданиями анализа | Ноутбук |
| SQLite | События, допуски, происшествия, результаты и версии | Ноутбук |
| Модуль правил | Допуски, геометрия зон, таймер heartbeat | В приложении |
| Маленькая MLP | Оценка необычного движения | CPU, обучение отдельной командой |
| Обработчик агента | Очередь, вызов модели, исполнение инструментов, проверка результата | В приложении, вне обработки событий |
| Qwen3:4b через Ollama | Выбор инструментов и объяснение происшествия | Отдельный процесс на ноутбуке |
| Адаптер Яндекс API, опционально | Другой поставщик модели для того же агента | Серверный клиент внешнего API |
| Интерфейс HTML/CSS/JS/SVG | План, панели участков, журнал, карточка анализа | Браузер |

Для MVP один процесс FastAPI, один таймер и один обработчик очереди агента. Неблокирующие вызовы Ollama выполняются с тайм-аутом; вычисления MLP выносятся из цикла обработки запросов. SQLite использует короткие транзакции и сериализованную запись. Длительные вычисления и вызовы модели выполняются вне транзакций.

## Поток событий

1. Источник отправляет Event: уникальный ID, время, датчик, тип, payload, demo.
2. Сервер проверяет структуру, существование объектов, соответствие датчика объекту и временные ограничения.
3. Сохраняет событие и received_at. Повтор того же события не вызывает повторную тревогу. Несовместимое содержимое того же ID даёт конфликт.
4. Правила анализируют проход, координаты или heartbeat. Отдельный таймер обнаруживает отсутствие heartbeat.
5. При нарушении создаётся или обновляется Incident со ссылками на исходные события и версией правила.
6. Окна позиций отдельно поступают в MLP. Недостаточные данные отмечаются явно; результат модели хранится с версией и исходными событиями.
7. Интерфейс опрашивает сервер раз в секунду и обновляет журнал, план и карточки.

На один продолжающийся въезд в запрещённую зону создаётся одно происшествие. Новый въезд после выхода создаёт новый случай. Каждое отдельное наблюдение прохода без допуска является отдельным происшествием.

## Привязка к участку

Event и Incident — источник истины; интерфейс не угадывает место по тексту модели.

- Проход: участок определяется по building_id.
- Въезд: zone_id связывается с ответственным участком в конфигурации.
- Стационарный датчик: участок определяется по конфигурации датчика.
- Движущийся датчик: используются известные координаты и привязка зоны; при отсутствии достоверного места событие попадает в «Место не определено».
- Дороги и общие зоны имеют собственную панель, без искусственного назначения ближайшему зданию.

Рекомендуемое дополнение: единый site_area_id для участка отображения. building_id и zone_id остаются предметными идентификаторами. Конфигурация содержит site_areas и явные связи зданий, зон и датчиков. На момент обнаружения участок сохраняется в Incident: движение машины и будущая правка геометрии не меняют историю происшествия.

## Работа ИИ-диспетчера

Один общий агент обслуживает все участки. Отдельный экземпляр Qwen для каждого здания не требуется.

1. Оператор выбирает происшествие и нажимает «Проанализировать».
2. Сервер создаёт AgentJob и отвечает 202 с job_id; экран остаётся доступным.
3. Задание содержит incident_id и снимок версий, доказательств и применимой политики.
4. Агент передаёт модели инструкцию, ID происшествия и описания разрешённых инструментов.
5. Модель выбирает инструмент; код проверяет аргументы и читает данные.
6. Результат возвращается модели. Цикл ограничен тремя обращениями к модели, шестью инструментами и общим бюджетом 60 секунд.
7. Код проверяет структуру ответа и существование ссылок на доказательства. Это проверка происхождения данных, а не гарантия истинности каждого утверждения модели.
8. Ответ сохраняется по incident_id и снимку. Панель получает job/result от сервера и отображает анализ у нужного происшествия.

Инструменты из текущего контракта: get_incident, get_event_history, get_asset_policy, get_sensor_health. Они вызывают обычные функции чтения базы; публикация базы в интернет не требуется. Никаких команд ОС, SQL от модели и управления оборудованием.

Системная инструкция требует прочитать факты, проверить применимые разрешения, разделять доказанные события и гипотезы, не придумывать причины и ссылаться на полученные данные. Инструкция и описания функций передаются при обращении; дообучение Qwen для первой версии не предусмотрено.

Полученные документы и payload датчиков рассматриваются как данные, а не как инструкции для агента.

## Очередь и повторные запросы

Для ноутбука максимум одно выполняющееся задание анализа. Остальные ожидают. Повторное нажатие для того же снимка возвращает существующее задание или готовый результат. Новые доказательства или изменение применимой политики делают анализ устаревшим. Старый ответ помечается явно; новый результат сохраняется отдельной версией.

Задания и результаты хранятся в SQLite. После перезапуска незавершённые running переводятся в failed с объяснением; queued можно восстановить в памяти. Готовые результаты сохраняются. Очередь ограничивается настройкой; переполнение даёт понятную ошибку без остановки мониторинга. Для MVP ручной запуск анализа предпочтителен. Автоматический запуск позже можно добавить только на новое происшествие, с дедупликацией и лимитом очереди.

## Данные

| Сущность | Основные поля/связи |
|---|---|
| SiteArea | ID, название, тип участка |
| Building / Zone | Геометрия, связь с SiteArea |
| Asset | Машина или сотрудник |
| Sensor | Тип, объект, привязка участка при наличии |
| Permission | Объект, разрешённые здания/зоны, версия политики |
| Event | Время источника и сервера, датчик, payload, неизменяемая запись |
| Incident | Тип, объект, участок, active condition, status, доказательства, версии |
| ModelObservation | Окно позиций, оценка, порог, версия модели |
| AgentJob | Происшествие, snapshot, статус, ошибка, время |
| AgentAnalysis | Факты, гипотезы, рекомендации, доказательства, trace, модель, snapshot |
| IncidentStatusHistory | Кто и когда подтвердил/закрыл происшествие |

Точное изменение существующих полей согласуется в CONTRACTS.md до реализации.

## API

Используем существующие операции /api/site, /api/events, /api/assets, /api/sensors, /api/incidents, /api/incidents/{id}, /api/incidents/{id}/analysis и /api/agent-jobs/{job_id}.

Предлагаемые дополнения: фильтр site_area_id в журнале происшествий и датчиков; агрегированные сводки участков в GET /api/site-areas/summary. Сервер считает количества по базе и возвращает время актуальности сводки. Коды ошибок и формат ответов едины. PATCH карточки изменяет только операторский статус.

## Локальная модель и внешний API

Агент зависит от внутреннего интерфейса поставщика модели: запрос сообщений/инструментов → нормализованные tool calls или итоговый ответ. Ollama и Яндекс имеют отдельные адаптеры; совместимость конкретной модели и API проверяется реальным вызовом инструмента. Смена поставщика не меняет приём датчиков, правила или интерфейс происшествий.

По умолчанию для автономного демо — локальная Qwen3:4b после проверки качества и времени. Яндекс — явно выбранный режим при разрешённом облаке и интернете. Автоматического скрытого переключения с локальной обработки на передачу данных в облако нет. Ключ внешнего API хранится на сервере и не попадает в браузер, репозиторий или журналы.

## Обучаемая модель движения

Сохраняем текущий план: семь признаков movement-v1, StandardScaler и MLPClassifier со слоями 16 и 8. Обучение отдельно на эпизодах, разделённых на train/validation/test. Преобразования, порог и версии сохраняются вместе с артефактом. На запросах датчиков веса не переобучаются.

Оценка этой модели — сигнал о необычном движении, не доказательство нарушения и не вероятность аварии. Проход без допуска и запрещённый въезд определяются точными правилами.

## Структура кода

```text
src/
  core/           # FastAPI, приём событий, правила, таймер
  storage/        # SQLite, схема, миграции и функции чтения
  simulator/      # Сценарии событий
  ml/             # Признаки, обучение, оценка, применение
  agent/
    worker.py     # Очередь и ограниченный цикл
    tools.py      # Разрешённые функции
    validation.py # Структура и доказательства результата
    providers/    # Ollama, опционально Яндекс
  interface/web/  # План, панели, журнал и анализ
data/demo/        # Конфигурация предприятия
artifacts/local/  # Обученная маленькая модель
runtime/          # Рабочая база
tests/            # Проверки сценариев и интеграции
```

## Границы MVP и готовность

Сначала готовим базовую цепочку событие → правило → происшествие → правильная панель. Затем обученную MLP и анализ Qwen. Функции панели подтверждения/закрытия работают независимо от модели.

Проверка готовности: проход без допуска попадает в офис; запрещённый въезд — на ответственный участок; общая дорога — в панель дороги; два случая одного склада имеют отдельные ответы; повтор события не дублирует тревогу; устаревший ответ маркируется; неизвестное место не выдумывается; отключение Ollama сохраняет мониторинг; реальный tool calling и анализ укладываются в бюджет; второй участник повторяет запуск на чистом клоне.

Для двух дней отдельные микросервисы, брокер сообщений, многопользовательские права и промышленная отказоустойчивость выходят за MVP. При переходе к реальному предприятию отдельно проектируются аутентификация, права, резервирование, аудит, реальные адаптеры и проверка качества на реальных данных.
