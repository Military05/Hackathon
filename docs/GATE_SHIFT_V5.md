# КПП и единый сценарий начала смены

Обновление 7 октября 2026, исходная версия `3a751e9a30b2e1436b9e7ec7b1a3b9830aee887f`.
Модуль `src/core/operations.py` принадлежит серверной части Егора С.; построенный
на событиях интерфейс — Егору М. Внешние симулятор, ML и ИИ-агент не меняются.
Это синтетические события `demo=true`, не управление физическим КПП.

## Проход людей

На плане нужен датчик `ACCESS-G1`, `type=access`, `building_id=G1` и участок
`checkpoint`. U1/U2/U3 имеют допуск G1; U4 — зарегистрированный сотрудник без
этого допуска. Датчик ACCESS-O1 остаётся на офисе и посылает heartbeat отдельно.

Внешний Event сохраняет прежние точные поля. Пример подтверждённого прохода:

```json
{
  "event_id": "gate-example-001",
  "event_time": "2026-10-07T10:00:00.000Z",
  "sensor_id": "ACCESS-G1",
  "type": "access",
  "demo": true,
  "payload": {
    "employee_id": "U1",
    "building_id": "G1",
    "direction": "in",
    "access_kind": "passage_confirmed"
  }
}
```

`direction` допускает `in/out`; `access_kind` можно опустить, сервер нормализует
его в `passage_confirmed`. Событие означает фактически подтверждённый проход.
Отклонённая карта, при которой человек остался снаружи, сюда не записывается.

Разрешённый проход сохраняется без Incident. Подтверждённый вход U4 создаёт один
`unauthorized_access`, назначенный сектору КПП. Повтор того же event_id и тела
возвращает duplicate и не удваивает журнал, Incident или проверку смены.
Другой body под тем же ID отклоняется. Выход остаётся отдельным обычным проходом.

Сценарии `unauthorized-access` и `simultaneous` теперь посылают U4 через G1:
вход на 6-й секунде, выход на 13-й. В офисе не появляются выдуманные проходы.
Обычный сценарий не генерирует людей только ради наполнения журнала.

## Смена: сначала люди, потом транспорт

`shift` создаёт запись смены и ожидает U1/U2/U3; необязательный
`site.shift_employees` может задавать зарегистрированных сотрудников с допуском
G1. Три стандартных подтверждённых прохода происходят через 1, 3 и 5 секунд.

До получения всех разрешённых событий машины стоят на исходных координатах.
Позиции и heartbeat продолжают приходить каждую секунду: ожидание людей не
выдаётся за потерю связи. Статус машины — `awaiting_gate_checks`.

После фактического сохранения всех проверок сервер переводит фазу в `transport`,
фиксирует `transport_started_at`, начинает движение с той же исходной точки.
Нет телепортации или движения только по таймеру интерфейса. Все последующие
position этого запуска относятся к той же shift_id; heartbeat не считается
проверкой сотрудника или транспортным этапом.

Если приём прохода заканчивается ошибкой, транспорт не начинает движение,
источник сообщает `error`; смена завершена с фазой `error`. Остановка и смена
сценария закрывают прежнюю смену с фазой `stopped`. Незавершённая запись после
перезапуска сервера становится `interrupted`: транспорт не продолжает чужую
смену автоматически. Сохранённые проходы и их корреляция доступны после restart.

Корреляция хранится в отдельных `ops_shifts`/`ops_shift_events`. Для внутреннего
генератора `Service.ingest_event(event, shift_id=...)` сохраняет Event, правило
и связь в одной транзакции. Публичный JSON Event не содержит shift_id; внешние
источники и ИИ не должны добавлять новые поля или назначать себе смену.

## Контракт Operations для интегратора

Создать `operations = Operations(service)` один раз при построении приложения.
Повторный экземпляр на том же Service безопасен; прежняя смена прерывается
только при первом запуске Operations после настоящего создания нового Service.
Генератор также создаёт Operations, если его ещё не подключил интегратор.

```python
operations.journal(q=None, direction=None, permission=None,
                   since=None, until=None, limit=50, offset=0)
operations.checkpoint_csv(**same_filters)  # bytes, по умолчанию limit=200
operations.current_shift()                # последняя смена или None
operations.dispatch_activity(operator_id)
operations.dispatch_history_csv(operator_id=None, limit=1000)
```

Интегратор добавляет маршруты `/api/checkpoint/journal`,
`/api/checkpoint/export.csv`, `/api/shifts/current`, `/api/operator-activity` и
`/api/dispatch-history/export.csv` и проверяет авторизацию до вызова этих методов.
Методы сами не принимают HTTP cookie и не определяют администратора.

Журнал возвращает `{items,total,limit,offset,as_of,occupancy}`. Строка содержит
event_id, event_time, received_at, employee_id, employee_name, building_id,
direction, permission (`allowed/violation`), shift_id/scenario (null для события
вне смены). Допуск отражает реальное решение правила при приёме: последующее
редактирование текущей политики не превращает историческую тревогу в законный
вход. Выход считается разрешённым событием выхода.

`q` — буквальный поиск ID/имени/ID события, до 100 символов. `%`/`_` не работают
как пользовательские шаблоны SQL. Фильтры — направление, допуск, UTC since/until;
since не может быть позднее until. Сортировка от последних event_time/event_id.
Размер страницы 1..200, offset 0..100000; запросы параметризованы.

`occupancy.observed_inside_count` — сотрудники, у которых последний полученный
проход является входом. Это не число всех реально находящихся на заводе людей:
`initial_state_known=false`, `certainty=observed_only`. Есть время последнего
прохода и состояние источника G1. Потерянные события/неизвестная начальная смена
не компенсируются придуманными данными. Фильтр журнала не меняет эту сводку.

Смена содержит expected_employee_ids, checked_employee_ids, expected_gate_count,
gate_count (уникальные проверенные сотрудники), gate_event_count,
transport_events_count, transport_asset_ids, recent_transport_events (не более
12 последних реальных position с event_id/asset_id/x/y), cleared, phase,
started_at/ended_at/transport_started_at/error. Статус DemoRunner имеет поле
`shift` с этой сводкой только для соответствующего запуска.

Сводка диспетчера возвращает operator_id, claimed, transferred, closed, responses,
as_of. Считает историю успешных операций: claim, завершённые исходящие передачи
accept_transfer, close и record_response. Неудачные запросы не считаются;
созданная, но не принятая передача не становится завершённой.

Dispatcher-3 отвечает за КПП. Он не может принять необращённое происшествие
чужого сектора только по своему номеру. Согласованные уведомления/эскалации для
резервного оператора по-прежнему дают право принятия.

CSV кодируется UTF-8 с BOM; csv.writer сохраняет запятые, кавычки и переносы.
Текст с начальными `=`, `+`, `-`, `@`, TAB/CR/LF экранируется апострофом для
табличных редакторов. CSV КПП экспортирует запрошенную страницу, максимум 200:
интерфейс должен явно назвать это ограничение. CSV работы диспетчера содержит
последние до 1000 его действий, максимум 2000; глобальный экспорт с
operator_id=None разрешает только администратор на уровне HTTP.

## Нагрузка и проверки

С ACCESS-G1 обычная передача — 3 position + 3 heartbeat в секунду. Во время
проходов добавляется один access. Один источник, один FastAPI worker и SQLite;
дополнительных служб, GPU, обучения или запросов к модели нет. Журнал и история
сохраняются на диске; при многочасовой непрерывной работе база растёт.

```powershell
python -m unittest discover -s tests/runtime -p 'test_operations.py' -v
python -m unittest discover -s tests/runtime -p 'test_demo_traffic.py' -v
python -m unittest discover -s tests/runtime -p 'test_backend.py' -v
```

В изолированной поставке: 12 Operations, 13 traffic и 17 существующих backend
tests — PASS. Покрываются реальный SQLite, законные/незаконные проходы, повторы,
поиск/пагинация/время, CSV-инъекции, атомарный rollback, сохранение корреляции после
restart, настоящее неподвижное ожидание транспорта, продолжение после людей и
ошибка источника КПП. Браузер, HTTP-авторизацию, общую новую карту, ML/ИИ и замеры
на целевых устройствах проверяет интегратор; эти проверки здесь NOT RUN.
