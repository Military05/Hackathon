# Работа пятером в одной комнате: 7–8 октября

> Текущая поставка ограничена задачами Егора С. и Егора М. ML, агент и сценарии разрабатываются отдельно и в эту ветку не включены. Подтверждённые этапы, команды и статусы: [DEVELOPMENT_STAGES](DEVELOPMENT_STAGES.md), [RUNTIME_QUICKSTART](RUNTIME_QUICKSTART.md), [RELEASE](RELEASE.md). Остальные разделы описывают общий целевой план команды.

Этот документ даёт порядок работы над общей версией. Технические форматы определены в [CONTRACTS](CONTRACTS.md), [DISPATCH_OPERATIONS](DISPATCH_OPERATIONS.md) и [PREBUILD_FIXES](PREBUILD_FIXES.md). Команды текущего приложения — в [RUNBOOK](RUNBOOK.md), фактические результаты — в [RELEASE](RELEASE.md). Старые инструкции со статусом «ещё нет кода» и очередью 20 читаются с актуальными уточнениями: очередь максимум 2, наличие функций проверяется по текущему SHA и RELEASE.

## 1. Кто отвечает

| Человек | Приоритет | Свои файлы | С кем обсуждает подключение |
| --- | --- | --- | --- |
| Егор С. | API, SQLite, правила, dispatch, общий сервер | src/core, src/storage; main entrypoint, схема, зависимости и site.json | все потребители; QA Лия |
| Егор М. | карта предприятия и 3 диспетчерских | src/interface/web | Егор С. по API, Гриша по координатам, Гаджи по панели анализа |

| Гриша | сценарии, признаки, MLP | src/simulator, src/ml | Егор С. по событиям/inference, Егор М. по маршрутам, Лия по split/кейсам |
| Лия | независимая проверка и повтор запуска | tests/QA, отчёты и инструкции проверки | автор каждой функции; координатор по готовности |

Владелец проекта координирует срок, приоритеты, объединение и два Work-агента. Это организационная ответственность; она не меняет владельцев модулей. Если один из пяти одновременно координатор, сохраняются те же границы.

GitHub-плагин в чате помогает прочитать проект и подготовить алгоритм. Каждый участник сам сохраняет код, запускает PowerShell, проверяет результат и отправляет личную ветку, если его чат не имеет соответствующих инструментов. Работа ChatGPT не снимает ответственность автора. [Точный порядок](CHATGPT_GITHUB_GUIDE.md).

## 2. Первые 30 минут, начиная с 14:00 7 октября

1. Координатор сообщает ссылку репозитория и общий проверяемый commit SHA. Все записывают одну базу. Ветки с непроверенной работой Егора остаются отдельно; из них ничего не копируют автоматически.
2. Каждый в своём клоне проверяет git status, текущую ветку и SHA. Два человека не используют одну папку. Пятеро могут пользоваться одним сервером демо, но не одним рабочим checkout.
3. Все запускают текущую общую версию по [RUNTIME_QUICKSTART](RUNTIME_QUICKSTART.md) и RUNBOOK. Лия фиксирует первый результат и перечисляет конкретные пробелы; наличие документа не означает наличие функции.
4. Егор С. показывает site.json: O1, W1/W2, P1/P2, G1, Z1/Z2, V1–V3/U1–U3, sensor IDs, дороги, секторы, профили, пороги. Егор М. и Гриша подтверждают одинаковую геометрию. Гаджи подтверждает provider и snapshot. Лия — тесты ID и границ.
5. Егор С./Егор М. выбирают пример одного Event и одного Incident: ключи, response, ошибка, expected_revision/request_id. Это короткое решение C0, без перестройки всей архитектуры.
6. Гаджи проверяет уже установленный локальный runtime и доступную модель. Полноценный tools-вызов проверяется сразу, а не последним вечером. Если runtime несовместим, фиксирует ошибку и согласует совместимый вариант.
7. Каждый берёт одну небольшую задачу, указывает разрешённые файлы, нужного соседа и ожидаемый результат.

Не нужно тратить первую встречу на установку полного ThingsBoard или Home Assistant: библиотека карты и source-порты уже подготовлены в лёгком приложении. [Заимствования](UPSTREAM_REUSE.md).

Команды из корня своего клона:

```powershell
.\scripts\setup.ps1
.\scripts\start.ps1
```

Открыть http://127.0.0.1:8000 и запустить сценарий кнопкой интерфейса. Для нескольких компьютеров комнаты сервер запускается командой `.\scripts\start.ps1 -Lan`; доступ и локальный адрес описаны в RUNTIME_QUICKSTART. Только один человек запускает общий demo server и одну симуляцию. Если нужен отдельный CLI-прогон, сначала остановить встроенную симуляцию:

```powershell
.\.venv\Scripts\python.exe -m src.simulator.run --scenario normal --seed 42 --base-url http://127.0.0.1:8000 --duration 120
.\.venv\Scripts\python.exe -m unittest discover -s tests/runtime -p 'test_*.py' -v
```

Повторное обучение выполняет Гриша отдельно от сервера:

```powershell
.\.venv\Scripts\python.exe -m src.ml.train --output artifacts/demo --episodes 600 --seed 20261007
```

Артефакты: artifacts/demo/movement-v1.joblib, movement-v1.json и ML_REPORT.json/md. До изменения обучения прочитать текущий отчёт и сверить hash. Настройка агента: LOCAL_MODEL_URL по умолчанию http://127.0.0.1:1234/v1; LOCAL_MODEL_ID можно задать ID уже загруженной модели. Без доступного совместимого локального runtime анализ сообщает 503 unavailable; это не успешно работающий LLM. На target ноутбуке измерения фиксируем в [PERFORMANCE](PERFORMANCE.md).

## 3. Обязательные обсуждения перед изменением

| Собираюсь изменить | Обсудить до кода | Что согласовать | Что можно делать пока ждём |
| --- | --- | --- | --- |
| Event/API/ID/ошибку | Егор С. + потребитель + Лия | один request/response, миграция, совместимость | свою функцию на согласованном fixture |
| site.json, здания/зоны/дороги | Егор С. + Егор М. + Гриша | границы, точка происхождения, route, допуск, сектор | визуальный стиль или генератор эпизодов без новых ID |
| SQLite/schema/main/dependency | Егор С. | транзакция, версия схемы, порт подключения | изолированный модуль с публичной функцией |
| карту/общий UI entrypoint | Егор М. + Егор С. | формат и state, refresh/error behavior | компоненты/подписи в своих файлах |
| sensor heartbeat/timeout/recovery | Егор С. + Гриша + Лия | received_at, never_started, grace, 2 свежих выхода | генератор с текущими порогами |
| ML features/порог/сохранение | Гриша + Егор С. + Лия | movement-v1, артефакт, статус not_trained, метрики | автономная train/evaluate процедура |
| tools/snapshot/анализ/jobs | Гаджи + Егор С. | freeze as_of, лимиты, trace, errors | клиент модели или evidence-validator на fixture |
| UI анализа/индикация stale | Гаджи + Егор М. | queued/running/error, evidence links, snapshot | отдельный компонент результата |
| claim/transfer/close/presence | Егор С. + Егор М. + Лия | одна revision, идемпотентность, atomic operation | тест сценария/кнопка на fixture |
| итоговый merge/новый scope | координатор + владелец + Лия | проверенный SHA, границы, состояние обязательных кейсов | исправления своего модуля |

Фраза для обсуждения: «В задаче X хочу изменить поле/функцию Y. Сейчас Z; предлагаю W. Это затронет A/B. Проверим таким входом и получим такой ответ». Устное решение записывается в Issue/PR или коротком решении docs. ChatGPT не должен выдумывать, что сосед уже согласовал.

Не делать до обсуждения: менять названия ID, порядок признаков, lifecycle, порог, схему БД; переносить чужую незавершённую ветку; добавлять новый runtime/сервис; заменять API mock-данными; увеличивать очередь или число модельных вызовов.

## 4. Карта: общая договорённость

O1 — центральный офис и диспетчерская. G1 — КПП. W1/W2 размещены у складских подъездов, P1/P2 — у производственных проездов. Центральная дорога связывает КПП, офис и ответвления к складам/цехам. Карта рисуется из site.json, а не отдельно каждым автором.

Показываем здания, проезды/площадки, подписи, текущие позиции и короткий след движения, датчики, зоны ограничения и возраст данных. Маркеры не пересекают стены. Шкала 0..100 условная, GPS не используется. Leaflet CRS.Simple обеспечивает перемещение и масштабирование; все ресурсы локальные.

Гриша использует те же waypoint-маршруты. Нормальная остановка на погрузке допустима. Запрещённый въезд — сценарий пересечения Z1/Z2 по подъезду. Доступ сотрудника — отдельное access-событие, а не придуманная координата работника. Потеря heartbeat не означает, что исчезнувшая машина телепортировалась или вышла из зоны.

На планшете датчиков обозначены online/offline/unknown, время последнего приёма, asset/sensor ID. Одновременные нарушения остаются разными карточками. Секторы logistics/production/coordination закреплены за профилями, не выбираются LLM.

## 5. Небольшие задачи: первая половина дня 1

Если нужная функция уже присутствует в опубликованном SHA, задача становится её проверкой/исправлением. Не переписываем работающий модуль ради повторения инструкции.

| ID | Кто | До 1–3 часов | Что считаем готовым |
| --- | --- | --- | --- |
| R01 | Егор С. | запустить общий API и проверить Event/idempotency | 201 новый, 200 duplicate, 409 конфликт, 422 invalid, SQLite сохраняет событие |
| R02 | Егор М. | подключить карту к /api/site и /api/assets | здания/дороги/маркеры совпадают; 3 клиента видят одну симуляцию |
| R03 | Гриша | normal + D1/D2/D3 на общем site | seed/run_id/demo, воспроизводимая последовательность, правильные sensor IDs |
| R04 | Гаджи | первый реальный tool roundtrip | модель запросила разрешённую функцию, код выполнил её, trace содержит результат |
| R05 | Лия | короткий D1–D3 и проверка геометрии | точный SHA, вход/expected/actual, отсутствие дублей и четыре края/углы зоны |
| R06 | Егор С. + Егор М. | проверить routing/claim/3 профиля | у каждого свой сектор; конкуренция даёт одного владельца |

C1: запуск → normal → D1–D3 → три рабочих места → claim. Лия проверяет общий SHA, координатор фиксирует beta-1 только после этого. Функции beta-2 и F1 не объявляются готовыми по C1.

## 6. Вторая половина дня 1: три потока

Поток A: Егор С./Егор М. продолжают main к beta-2. Поток B: Гаджи/Гриша создают личные ветки от проверенного beta-1 и собирают F1. Поток Q: Лия отдельно проверяет зафиксированный beta-1 и принимает маленькие PR. [Существующая схема Git](../TEAM_WORKFLOW.md) сохраняется.

| ID | Кто | Задача 1–3 часа | Приёмка |
| --- | --- | --- | --- |
| R09 | Егор С. | request/accept/cancel/expire transfer | прежний owner до accept; один pending; deadline не продлевается restart |
| R10 | Егор М. | claim/transfer/presence UI + incoming | принимает серверный ответ; показывает ошибку; адресованная передача видна вне своего сектора |

## 7. День 2: объединение, ноутбук, защита

1. Включить проверенный beta-2/main в F1 без force push; каждый владелец решает конфликт своих данных/поведения. Не объединять оставленную отдельно ветку Егора.
2. Егор С. подключает ML/agent в общий сервер по публичным интерфейсам. Егор М. проверяет UI. Лия получает один SHA и проходит D1–D10 плюс PREBUILD_FIXES A1–A12.
3. Перенести Pipeline, локальные JS/CSS и проверенные веса/runtime. В Git только инструкции/версии/hash и малые артефакты по правилам проекта; крупные веса/venv не коммитить.
4. На целевом ноутбуке запустить 3 браузера, симуляцию, точные правила, MLP и одну модельную задачу. Аппаратура: Ryzen 7 8845HS/32 GB/Radeon 780M/Windows 11 x64. Записать реально измеренные CPU/RAM и задержки.
5. Второй человек повторяет RUNBOOK из чистого клона. Затем внешний интернет отключается, LAN при показе на нескольких компьютерах остаётся. Холодный restart и сохранение инцидентов/ownership/notification проходят отдельно.
6. За 3 часа до официальной сдачи freeze: новых функций не добавляем, исправляем обязательную цепочку. Координатор фиксирует фактический deadline.
7. За 2 часа выполняем полный показ на ноутбуке. За последний час оформляем RELEASE и backup-видео, репетируем роли. Финальный тег ставится после проверенного merge и smoke main.

Два дня — рабочий бюджет и порядок, а не гарантия отсутствия всех ошибок. Невыполненная проверка имеет статус NOT RUN; дефект имеет владельца и шаг воспроизведения. Не закрывать её словом «готово».

## 8. Дневной ритм комнаты

Каждые 60–90 минут короткая синхронизация до 5 минут: «что работает; SHA; что блокирует; кого нужно; следующий малый результат». Координатор ведёт общую доску TODO/IN PROGRESS/REVIEW/QA/DONE. DONE означает объединено и проверено в общей версии; локально выполнено — REVIEW.

Задача передаётся с пятью пунктами:

```text
R-ID / Issue:
Ветка + полный SHA:
Разрешённые и изменённые файлы:
Команда + вход + expected:
Нужный reviewer / что согласовано:
```

Если сосед занят, пишем в Issue и устно сообщаем; продолжаем независимую часть. Не создаём параллельную БД, вторую симуляцию или новое имя API.

## 9. Как показать жюри за 7–10 минут

1. Объяснить: это автономная модель предприятия, синтетические датчики demo=true; план создан командой, карта не GPS.
2. Normal: машины едут по дорогам, датчики передают данные; три рабочих места смотрят один сервер.
3. D1/D2/D3: точные правила обнаруживают вход/проход/потерю связи автоматически; показать исходные evidence.
4. D5/D6: несколько событий; два оператора одновременно claim, побеждает один; ответственное лицо видно всем.
5. D7/D8: передача с подтверждением; до acceptance owner прежний; отсутствие реакции даёт уведомление/эскалацию.
6. D4: собственная MLP с версиями, baseline и test; необычное движение отделено от точного нарушения.
7. Агент: отдельный анализ, реальный tool_trace, факты с источниками, гипотезы отдельно. Интернет выключен.
8. Сохранение/restart и измерения ноутбука. Назвать готовые библиотеки и собственные модули по UPSTREAM_REUSE.

Не обещаем промышленную сертификацию, прогноз аварии, реальное управление оборудованием или идеальную точность ML. Проверяем допустимость заранее подготовленного кода и симуляции по фактическому регламенту организаторов.
