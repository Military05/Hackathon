# Два Work-агента: что поручает координатор

> Текущая поставка ограничена задачами Егора С. и Егора М. ML, агент и сценарии разрабатываются отдельно и в эту ветку не включены. Подтверждённые этапы, команды и статусы: [DEVELOPMENT_STAGES](DEVELOPMENT_STAGES.md), [RUNTIME_QUICKSTART](RUNTIME_QUICKSTART.md), [RELEASE](RELEASE.md). Остальные разделы описывают общий целевой план команды.

Это отдельная помощь разработчикам, а не два диспетчера продукта и не обязательное требование для остальных участников. Пятеро выполняют свои задачи обычным ChatGPT. Координатор даёт двум агентам узкие задания, собирает результат и согласует его с владельцем модуля. [Общий порядок](TEAM_ROOM_PLAYBOOK.md), [чат команды](CHATGPT_GITHUB_GUIDE.md).

## 1. Общие условия до старта

1. Взять проверенный commit SHA общей базы. Обоим дать один SHA и ссылку на CONTRACTS/PREBUILD_FIXES.
2. Создать отдельные worktree/клоны и ветки. Не запускать двух агентов в одной папке и не менять одновременно общую main.py/schema/site.json.
3. Для каждого задания указать allowlist файлов, запреты, вход/ожидаемый результат, интерфейс соседней работы, timeout и критерий готовности.
4. Сначала согласовать с человеком-владельцем публичный интерфейс функции. Агент не меняет чужой контракт «для удобства».
5. Один агент пишет ограниченный модуль, второй проверяет независимые ошибки/кейсы или соседний модуль с другим allowlist.
6. Каждый возвращает ветку, полный SHA, diff, команду и фактическую проверку. Невыполненные проверки перечисляет.
7. Координатор сравнивает результаты, владелец делает review, Лия проверяет общий SHA. Итоговый merge выполняет человек.
8. Передача между аккаунтами — через Issue/PR и сообщение координатора; автоматическая связь не предполагается.

Крупные веса не скачивать на C: и не добавлять в Git. Сначала использовать имеющийся локальный runtime, а не менять стек параллельно с задачей.

## 2. Самая полезная пара: агент и проверка evidence

Владелец: Гаджи. До запуска обсуждение с Егором С.: provider query, materialized snapshot/as_of, сохранение jobs; с Егором М.: форма job/result/error.

| Агент | Ограниченная работа | Пример allowlist | Не менять |
| --- | --- | --- | --- |
| A | исправление адаптера локальной модели, bounded loop/очереди или evidence по одному дефекту | src/agent/runtime.py | backend, UI, schema, requirements без review; не переписывать весь runtime |
| B | независимые tools/args/evidence/queue проверки | отдельный tests/runtime/test_agent_review.py и отдельный QA-отчёт | src/agent/runtime.py, backend, UI; только читать код A |

Отдельный агент планируется в src/agent/runtime.py; он не входит в текущую поставку Егора С./М. Поэтому A и B не редактируют одновременно разные куски этого одного файла: A меняет runtime, B только отдельные проверки. Если Гаджи решит разделить модуль на model_client/orchestrator/jobs и tools/schemas/providers/evidence, это сначала один согласованный отдельный PR; только после него можно дать двум авторам разные файлы. Не создавать параллельный второй loop рядом с уже работающим. Цель 1–3 часа: одна законченная часть и проверяемый интерфейс; не «весь продукт».

Приёмка A: настоящий tools roundtrip локальной модели; max3 model requests/max6 tools; общий running budget60s, queue budget120s; 1 running/до2queued; кэш одного snapshot; timeout/restart=failed без зависания карты.

Приёмка B: неизвестное tool/поля/ID/date/limit отклоняются; SQL/shell не доступны; evidence только из реальных результатов tools; sensor-health/policy имеют отдельные типизированные ссылки; hallucinated evidence не публикуется; snapshot одинаковый.

Что A получает от B: воспроизводимый fixture и конкретный дефект с expected/actual. Что B получает от A: полный SHA runtime, schema вызова и структура результата. Прежде чем соединять, Гаджи фиксирует один wire fixture. Тест с контролируемым ответом модели доказывает поведение клиента/validator, но не реальный tool calling установленной Local-модели: этот прогон Гаджи выполняет отдельно.

## 3. Вторая полезная пара: MLP и независимая оценка

Владелец: Гриша. Согласование с Егором С.: public predict/window status/model metadata; с Лией: независимый test и expected.

| Агент | Работа | Разрешённые файлы | Запрет |
| --- | --- | --- | --- |
| A | extractor movement-v1 + train/save Pipeline | src/ml/movement.py, src/ml/train.py | сервер, site.json, оценочный test другого агента |
| B | оценка leakage/baseline/latency и отчёт | отдельный tests/runtime/test_ml_review.py и QA-отчёт | менять train/extractor/threshold, подгонять test |

Первое задание A: проверить текущий единый extractor семи features и сохранение scaler+MLP с metadata; исправить один подтверждённый дефект. Команда: `.\.venv\Scripts\python.exe -m src.ml.train --output artifacts/demo --episodes 600 --seed 20261007`. В текущей поставке артефакт artifacts/demo/movement-v1.joblib и отчёт рядом уже могут присутствовать; не заменять их непроверенным экспериментом. B на фиксированном SHA A проверяет split episode_id до scaler, порог только validation, разные seed, false incidents/episode и baseline. Независимую проверку нельзя проводить до получения полного SHA A и dataset manifest.

Параллельно B может подготовить тесты и критерии на fixtures. Обучение не выполняется в HTTP request; pickle/joblib из неизвестного внешнего источника не используется. Модель из своего train сохраняется с hash, версиями и порядком признаков.

## 4. Третья полезная пара: диспетчерская конкуренция

Владелец: Егор С.; review UI — Егор М.; QA — Лия.

A получает один ограниченный backend-модуль claim/transfer и собственную ветку. B читает fixed SHA и пишет отдельный black-box regression runner: два claim одновременно, replay request_id, revision conflict, accept/expire boundary, restart, ownership. B не исправляет backend в тех же файлах; возвращает воспроизводимый дефект.

Эта пара нужна после появления backend интерфейсов. Одновременное «A переписывает весь server, B переписывает весь UI» не даёт проверяемого результата и нарушает ownership.

## 5. Четвёртая полезная пара: карта и геометрическая проверка

Владелец: Егор М. вместе с Гришей по routes.

A улучшает карту только в src/interface/web на текущем API: own plan, Leaflet CRS.Simple, дороги, labels, sensor states, stale/error. B готовит проверку /api/site + simulator routes: waypoint не внутри зданий, граница зоны включена, x/y трансформация одинаковая, 3 браузера видят одну симуляцию, новые alerts не теряются. B пишет отдельный runner/отчёт, не правит UI A.

Не брать архитектуру 3D, генератор GPS-тайлов или редизайн всего продукта. Нужно ясное демонстрационное движение и измеримая корректность данных.

## 8. Порядок использования за два дня

Первым берём агента/tools evidence: самый рискованный интеграционный участок и легко разделяемые файлы. Затем MLP/evaluation. Конкурентные dispatch-тесты и геометрия идут по мере готовности серверной основы. Не нужно запускать все пары сразу: два агента обслуживают текущую блокировку.

Через 90 минут координатор проверяет, получен ли маленький runnable результат. При расширении scope обрезает задачу до исходного контракта. После 3 часов нужен завершённый модуль или точный блокер; красивый план без исходников/прогона не считается поставкой. Финальный результат проверяется человеком на общем SHA и целевом ноутбуке.
