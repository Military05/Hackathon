# План реализации задания №6 — экологическая карта города

План для команды из пяти человек на два дня. Это вариант реализации задания №6 для обсуждения; окончательный выбор темы команда подтверждает отдельно.

## 1. Короткое объяснение проекта

Мы создаём веб-приложение, которое объединяет опросы жителей, сообщения об экологических проблемах и показания датчиков воздуха и воды.

На Яндекс Картах пользователь выбирает район, видит обратную связь жителей и последние измерения. Система помогает находить места, требующие внимания, и смотреть изменения во времени.

Главный сценарий демонстрации: житель отправляет сообщение → оно появляется на карте → приходит измерение датчика → пользователь видит оба источника и историю района.

## 2. Что должно войти в готовый результат

| Часть задания | Наша реализация |
| --- | --- |
| Опросы | Короткая анкета по району: запах, дым, состояние воды, общая оценка |
| Обратная связь | Сообщение с категорией, описанием и точкой на карте |
| Датчики воздуха | Приём измерений через API, последние значения и история |
| Датчики водных ресурсов | Такой же механизм приёма, отдельные показатели и единицы |
| Привязка к Яндекс Картам | Метки сообщений и датчиков, выбор района, карточки объектов |

Отзывы и измерения показываем раздельно. Жалоба жителя сама по себе не подтверждает превышение загрязнения. Если данных по району нет, показываем «нет данных», а не «всё хорошо».

## 3. Что делает пользователь

1. Открывает карту города.
2. Выбирает район или точку.
3. Проходит короткий опрос.
4. При необходимости отправляет отдельное сообщение о проблеме.
5. Смотрит сообщения, результаты опросов и измерения датчиков.
6. Выбирает период и просматривает историю.

Для первой версии достаточно одного города и нескольких подготовленных районов. Не пытаемся охватить всю страну за два дня.

## 4. Как устроена система

~~~text
Опросы и сообщения жителей ─┐
                           ├→ сервер → база данных → карта и статистика
Датчики воздуха и воды ────┘
~~~

- Интерфейс: карта, анкета, форма сообщения, карточка района.
- Сервер: проверка входных данных, сохранение, выдача данных интерфейсу.
- База: районы, опросы, ответы, сообщения, датчики, измерения.
- Симулятор: отдельный скрипт, отправляющий тестовые измерения в тот же API, что и будущие реальные датчики.

Стек выбираем по навыкам команды. Для этого объёма достаточно одного сервера, одной базы и одного веб-интерфейса. Отдельные микросервисы и брокер сообщений не обязательны.

## 5. Какие данные храним

| Сущность | Минимальные поля |
| --- | --- |
| Район | id, название, координаты или границы |
| Ответ на опрос | id, район, ответы, время |
| Сообщение | id, район, координаты, категория, описание, время |
| Датчик | id, тип: воздух/вода, координаты, район, источник |
| Измерение | id датчика, время измерения, показатель, значение, единица |

Для измерения сохраняем и время приёма. Отмечаем тестовые источники, устаревшие показания и отсутствие данных. Показатели с разными единицами не объединяем в одну числовую шкалу без обоснованного правила.

## 6. Контракт API до параллельной работы

Пример минимальных маршрутов; точный формат фиксируем в docs/CONTRACTS.md.

| Маршрут | Назначение |
| --- | --- |
| GET /api/districts | Районы и краткая сводка |
| POST /api/survey-responses | Сохранить ответ на опрос |
| GET /api/districts/{id}/summary | Результаты опросов и статистика района |
| POST /api/reports | Сохранить сообщение о проблеме |
| GET /api/reports | Получить сообщения с фильтром по району/периоду |
| POST /api/measurements | Принять измерение датчика |
| GET /api/sensors | Получить датчики и последние измерения |
| GET /api/sensors/{id}/measurements | Получить историю датчика |

Согласуем обязательные поля, ошибки, координаты и единицы. Для разных датчиков используем один понятный формат измерения. Для точки фиксируем именованные latitude/longitude, а преобразование в порядок координат карты делает интерфейс.

Приём показаний предусматривает проверку идентификатора датчика, значения, времени и единицы. Для внешнего подключения согласуем простой механизм доступа; реальные секреты не включаем в репозиторий.

## 7. Как показать датчики без оборудования

Делаем симулятор отдельно от основного приложения:

1. Есть тестовый датчик воздуха и тестовый датчик воды.
2. Скрипт отправляет измерения через POST /api/measurements.
3. Сервер сохраняет их.
4. Карта и карточка датчика обновляются.
5. В демонстрационном сценарии показатель выходит за настроенный порог.
6. Появляется предупреждение.

На карте и защите явно обозначаем: данные симулированные. Возможность приёма внешних измерений остаётся реальной: физический датчик сможет отправлять данные по тому же контракту.

Демонстрационные пороги не выдаём за официальные санитарные нормы. Для реального применения потребуются проверенные источники нормативов и корректные единицы.

## 8. Распределение пяти участников

| Роль | Работа |
| --- | --- |
| Разработчик бэкэнда | API опросов/сообщений, база, валидация, общий контракт |
| Разработчик фронтэнда | Яндекс Карты, формы, карточка района, фильтры |
| Full-stack №1 | Приём измерений, симулятор, сохранение и проверка данных датчиков |
| Full-stack №2 | Показ датчиков на карте, история/график, предупреждения |
| QA | Проверка основных функций первой беты, затем датчиков и объединённой версии |

Оба full-stack могут менять логику и интерфейс. Такое разделение — распределение конкретных задач, а не жёсткая специализация.

Перед началом согласуем, кто меняет общий router, модели базы и общий entrypoint карты. Каждый работает в личной ветке; PR пары функций идут в их общую ветку.

## 9. Беты и параллельная работа

### Бета №1

Минимум: Яндекс Карта → опрос/сообщение → сохранение → просмотр результата. Проверяем один реальный сценарий целиком и фиксируем beta-1.

С этого момента одновременно:

- Пара основы улучшает формы, результаты опросов и фильтры к beta-2.
- Два full-stack в feature/beta1-f1 добавляют датчики и их отображение по заранее согласованному контракту.
- QA на фиксированном SHA beta-1 проверяет основные функции, оформляет баги и перепроверяет исправления.

Full-stack пара до готовности скелета согласует контракт измерений, готовит примеры и симулятор. Не ждёт без полезной работы.

### Совместная версия

Включаем актуальный main в ветку функции, адаптируем контракты и проверяем опросы, сообщения, датчики воздуха и воды вместе. После успеха объединяем функцию через PR в main и повторно проверяем общий результат.

Полные команды Git находятся в TEAM_WORKFLOW.md; схема трёх потоков — в PROCESS_IMPROVEMENTS.md.

## 10. План на два дня

| Период | Результат |
| --- | --- |
| День 1, начало | Проверить доступ к карте, выбрать стек, согласовать API и данные |
| День 1, первая половина | Собрать и проверить beta-1: карта + опрос + сообщение |
| День 1, вторая половина | Параллельно beta-2, датчики/симулятор, проверка beta-1 |
| День 2, первая половина | Объединить датчики и карту, проверить совместные сценарии |
| День 2, вторая половина | Исправления, чистый запуск, документация и репетиция |

За 2–3 часа до сдачи прекращаем новые функции. Если времени мало, оставляем один опрос, форму сообщения, карту и оба типа датчиков; дополнительные графики и сложную аналитику сокращаем первыми.

## 11. Что проверяет QA

- Опрос сохраняется и попадает в сводку правильного района.
- Сообщение появляется в правильной точке.
- Пустой ввод, неверные координаты и неправильные значения не ломают приложение.
- Данные сохраняются после перезапуска.
- Измерения воздуха и воды приходят через API и отображаются корректно.
- Показатель, единица, время и источник не перепутаны.
- Тестовые измерения обозначены как тестовые.
- Отсутствие/устаревание данных видно пользователю.
- Фильтры и история соответствуют выбранному периоду.
- Основные функции и датчики работают в одной версии.

Результаты привязываем к точному SHA. Сценарии и журнал — в docs/TESTING.md.

## 12. Что показать на защите

1. Житель проходит опрос и отправляет сообщение о проблеме.
2. На карте появляется сообщение, в районе обновляется сводка.
3. Симулятор отправляет измерения воздуха и воды через API.
4. Видны новые значения, источник и время.
5. Один тестовый показатель пересекает демонстрационный порог: появляется предупреждение.
6. Открываем историю района/датчика и объясняем различие отзывов и измерений.

Основной эффект проекта: обратная связь и измерения доступны в одном месте, при этом происхождение данных прозрачно.

## 13. Первое техническое действие

Сразу проверить подключение Яндекс Карт на локальной странице: API-ключ, доступный тариф/условия, разрешённый адрес приложения. Для JS API v3 требуется настроенное ограничение HTTP Referer.

[Официальный быстрый старт Яндекс Карт](https://yandex.ru/maps-api/docs/js-api/common/quickstart.html).

Не оставляем получение ключа и первый запуск карты на последний день. Карта прямо предусмотрена заданием; её подключение — ранняя контрольная точка.
