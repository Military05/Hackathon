# Проверки задания №3 и журнал Лия (QA — тестировщик)

Если слово незнакомо, открой [словарь простыми словами](GLOSSARY.md). Команды и названия полей не переводим: в коде они должны остаться точными.

Тестировщик начинает с [своей инструкции](roles/QA.md). План и форматы: [TASK_03_PLAN](TASK_03_PLAN.md), [CONTRACTS](CONTRACTS.md), команды: [RUNBOOK](RUNBOOK.md).

## Приоритеты и проходы

P0: не запускается, потеря данных/неконтролируемая запись. P1: обязательное поведение неверно, интеграция ломает демо. P2: неудобство с обходом. P3: оформление.

1. До beta-1: уточняем кейсы, отдельные PR (запрос на объединение изменений) авторов, smoke (короткая проверка запуска и основного сценария) скелета.
2. Сразу после beta-1: полная регрессия зафиксированного SHA (идентификатор конкретной версии кода) одновременно с работой обеих пар.
3. Во время F1: отдельная проверка MLP (небольшая многослойная нейросеть) и агента по готовности.
4. После main → F1: совместный фиксированный SHA; при любом изменении head (ветка или версия с предлагаемыми изменениями) повторить затронутые проверки.
5. После F1 → main: короткий smoke, чистый клон, финальные кейсы.

Не запускаем два тестовых сервера на одной demo-базе. Для независимой проверки выделяем отдельную папку runtime и порт; конкретные параметры запуска фиксирует Егор С. (A1) в RUNBOOK. Лия (QA — тестировщик) не изменяет модельные метрики ради прохода.

## Проверка нейросети

Лия (QA — тестировщик) получает dataset metadata, версии, seed (начальное число для повторяемой генерации), split (разделение данных) manifest, hash (контрольный отпечаток файла) артефакта, baseline (простой алгоритм для сравнения) и ML_REPORT. Проверяет отсутствие leakage: готовый класс не подан в features; эпизоды не пересеклись; test не использован для выбора порога. Метрики на синтетике подписаны как синтетические.

Если модель не обнаружила D4, записываем фактический результат; не редактируем evidence или отображение, чтобы показать успех. Для новой настройки нужен независимый итоговый test.

## Проверка производительности

На согласованной demo-машине: число событий/сек, длительность прогона, ошибки приёма, задержка карты, время MLP и p50/p95 agent latency (время ожидания ответа) при достаточном количестве запросов. Для единичного запроса пишем его время, не «статистический p95». Сравниваем мониторинг с LLM (большая языковая модель) и без; если показатели ухудшились, проверяем очередь и блокировки.

Это измерение нашего прогона, не доказательство масштаба настоящего завода.

Поля: branch + полный SHA, версии/команда запуска, fixture/seed, шаги, expected, actual, evidence/log, затронутые main/F1, исполнитель. Секреты и персональные данные исключаем из публичного Issue (задача или сообщение об ошибке).

## Release gate

Нет P0/P1 обязательного пути; пройден совместный кандидат; актуальны RUNBOOK и ML_REPORT; модель/агент заявлены только по фактическому показу; второй участник повторил запуск. Итоговое решение о сокращении объёма руководитель фиксирует в RELEASE.
