## A1 / T28: порядок реакции и запись действия

Incident получает `response_plan: {contact, steps}`. Оба значения — короткие тексты из общего регламента конфигурации; UI имеет явные демонстрационные тексты по умолчанию, пока сервер не готов. Контакт — роль, а не выдуманный телефон. LLM не должна менять утверждённую первую реакцию. Действует общий цикл: обнаружение → назначение владельца → реакция → проверка наблюдений → завершение разбора.

PATCH `action=record_response` содержит стандартные expected_revision/request_id и `response_code=contacted|inspection_requested|checked`, `reason` 1–500 символов. Только текущий владелец незавершённого рабочего случая. Создаёт запись DispatchHistory; Incident возвращает `response_history` (последние записи: response_code,reason,actor_operator_id,created_at). Само по себе не меняет condition_active, не закрывает случай и не доказывает физическое выполнение команды. Идемпотентность/транзакция такие же, как claim. Полная история сохраняется на сервере; карточка может показывать последние пять действий.

Владелец: Егор С.; отображение Егор М.; агент Гаджи; проверка Лия. Карточка/операция уже доступны в mock, API provider отправляет эту операцию. Серверной реализации ещё нет.

## A2 / T29: актуальность и отсутствие первого пакета

`condition_state=active|restored|unknown` описывает актуальное знание детектора. `condition_active` сохраняет последнее известное логическое условие, когда текущее неизвестно; unknown не является восстановлением. `last_seen` объекта относится к position, не к любому heartbeat. `last_received_at` датчика — контакт с каналом, `last_measurement_at` — свежесть измерения. Старое доставленное измерение может подтвердить контакт канала, но не актуальное положение.

Порог `position_stale_seconds=5` — конфигурируемый demo-порог. На карте последняя позиция остаётся, возраст и неизвестное текущее место обозначены текстом. В UI время сверяется с серверным `as_of` сводки; точные измерения задержек между компьютерами требуют согласованных часов. Future tolerance demo — 2 секунды; события сверх него 422. Поздние позиции сохраняются без отката текущего положения и без восстановления текущего условия на основании старой точки.

Ожидаемые датчики заданы конфигурацией. До первого пакета unknown в пределах `startup_sensor_grace_seconds=10`; затем sensor_offline с `details.cause=never_started`, last_received_at=null, временем начала ожидания и порогом. После первого heartbeat обычный offline threshold=5. Никакого выдуманного исходного heartbeat: evidence_event_ids может быть пустым для отсутствия первого сигнала; факт подтверждается сохранённым состоянием здоровья и конфигурацией. История source_not_started сохраняется, повторный restart не порождает новый идентичный эпизод. Сенсор считается восстановленным по действительно актуальному сигналу.

Владелец: Егор С. + Гриша, UI Егор М., проверка Лия. В интерфейсе реализованы возраст и unknown; транспортные таймеры — задача backend.

## A3 / T30: access означает подтверждённый проход

В MVP `type=access`, employee_id/building_id/direction означает **наблюдённый проход**, access_kind=passage_confirmed при наличии поля. Старый допустимый payload без access_kind сохраняет этот же смысл. Сценарий unauthorized-access не является отказом карточки. Переназвать QA fixture denied_access или пояснить, что это проход без допуска, не событие deny контроллера. Обычное разрешение открыть дверь также не доказывает проход.

Реальные access_attempt/granted/denied/door_forced потребуют отдельного адаптера и типов; не превращать их в confirmed passage. При неизвестном человеке не подставлять выдуманный employee_id. Расширение реальной СКУД не является обязательной интеграцией за два дня.

Владелец: Егор С. + Гриша + Лия; Гаджи проверяет соответствие текста факту. В mock есть отдельная явная подпись подтверждённого прохода.

## A4 / T31: гистерезис зоны и геометрия

Вход: первое свежее position внутри включённой границы запрещённой зоны. Восстановление: `zone_exit_confirm_samples=2` последовательных свежих, упорядоченных position снаружи. При точке внутри счётчик выхода сбрасывается; при пропуске данных условие unknown и подтверждение выхода не накапливается. Один эпизод остаётся одним Incident. После подтверждённого выхода настоящий новый вход даёт новый случай. Два измерения могут добавить задержку: её замеряет Лия.

Данные в условных единицах 0..100, не метры и не км/ч. Обнаружение по полученным точкам не обещает зарегистрировать пересечение между редкими измерениями. Достаточная частота demo согласуется с Гришей; реальные требования к датчикам — отдельный пилот.

Владелец: Егор С.; сценарии Гриша; Лия проверяет шум, потерю точки и повторный вход. Frontend сам не исполняет производственные правила геозон.

## A5 / T32: связь клиента и заявленная готовность

POST /api/operator-presence: `{session_id, availability:"ready"|"away"}`. Availability — заявление этой вкладки; server session last_seen хранится отдельно. `client_online` профиля = есть свежая сессия, `operator_ready` = есть свежая сессия с availability=ready. Для совместимости `operator_online` в summary означает client_online и не доказывает человеческое внимание. Если открыты две сессии одного профиля, ready любой свежей сессии делает профиль готовым: переключатель одной вкладки не завершает другую.

Связь проверяется по серверному времени, presence heartbeat=3, timeout=15 demo секунд. Порог не объявляется нормой предприятия. При restart `startup_operator_grace_seconds=5`: клиенты восстанавливают сессии, затем возобновляется проверка недоступности; исходные deadlines/ownership не обнуляются. При смене профиля клиент посылает прежней сессии away и переключает provider/курсоры; при сбое прежняя сессия истекает по timeout. У профилей независимые session_id.

Не освобождать владельца из-за скрытой страницы. Проверить background throttling на используемом браузере; операторское отсутствие не выводить из visibilityState. UI явно показывает ошибку сервера и последнюю известную позицию. Не использовать браузерный polling как доказательство гарантированной задержки.

Владелец: Егор С. + Егор М.; Лия. Отправка presence и переключатель подготовлены в API provider; server lease/readiness ещё не реализованы.

## A6 / T33: резерв координатора

Порядок резервов для недоступного владельца: dispatcher-1 → [dispatcher-3, dispatcher-2]; dispatcher-2 → [dispatcher-3, dispatcher-1]; dispatcher-3 → [dispatcher-1, dispatcher-2]. Готовность учитывает свежий клиент и ready. Текущий owner сохраняется до успешного восстановления ответственности.

`reassign_unavailable` разрешён первому доступному готовому резерву в этом списке после непрерывной недоступности владельца не менее 15 секунд и после startup grace. to_operator_id — другой готовый профиль. Причина обязательна. Revision/idempotency, смена owner и DispatchHistory — одна транзакция. При существующей pending transfer её отмена с причиной recovery выполняется в той же транзакции; прежний pending не может затем принять случай. Два резерва с одинаковой revision дают одного победителя.

Если все отсутствуют — задача остаётся явно необработанной. Никаких фиктивных владельцев. Эскалация адресует уведомление, но не доказывает физическую реакцию людей. Это фиксированная demo-политика, не аккаунты/смены/сложная матрица прав.

Владелец: Егор С. + Егор М.; проверка Лия. В mock server recovery/transfer не имитируются как подтверждённо готовые.

## A7 / T34: нагрузка, приоритет и звук

Обязателен same-sector-burst: три случая на складе, один выбран/принят, остальные видны; помощь адресуется резерву по серверным правилам. Отдельно проверить три сектора, coordination перегрузку и отсутствие всех рабочих мест. Три оператора — пример конфигурации; численность настоящего предприятия определяется его задачами и нагрузкой.

Приоритет задаётся `severity` из конфигурации правила/места/типа события. Штатные события не требуют тревоги. Для confirmed прохода в опасное место и запрещённой зоны demo critical, для потери наблюдения/ML warning; для будущих denied событий приоритет отдельно, не автоматически critical. Разделять физическую важность, просрочку реакции, актуальность данных и статус обработки.

Звук только после разрешения, максимум один короткий сигнал за цикл и не чаще одного раза в 5 секунд (не на каждое сообщение); журнал не скрывается. На первой загрузке/смене профиля история не озвучивается. seq монотонный и сохранённый; server next_seq — cursor после последней возвращённой записи, не пропуск непрочитанных страниц. Нельзя в первой ограниченной странице вернуть глобальный максимум и потерять оставшиеся записи.

Владелец: Егор С. + Егор М., сценарии Гриша, Лия. В mock уже есть burst и сортировка; реальные уведомления требует сервер.

## A8 / T37: очередь модели

Начальные пределы: 1 running, максимум **2 queued**, FIFO, queued budget 120 секунд, running budget 60 секунд на всё задание (не на каждый из трёх запросов модели), max 3 model requests/6 tools. До помещения в очередь оценка ожидания должна быть **строго меньше** оставшегося queue budget. Для консервативной оценки взять остаток 60-секундного running бюджета и по 60 секунд на предыдущие queued. Если места по времени нет, 429 queue_busy/queue_full с понятной причиной; не принимать заведомо истекающее задание. После измерений ноутбука параметры можно согласованно изменить.

Повтор активного задания/готового успешного анализа одного snapshot объединяется. failed остаётся в истории, повторный осознанный запрос может создать новое задание. Интерфейс показывает queued/running/result/error, мониторинг продолжает работу. Модель вне транзакций SQLite и блокирующего обработчика событий. На restart running=failed interrupted, queued сохраняют исходный бюджет; deadline не продлевается.

Владелец: Гаджи + Егор С.; проверка Лия. Здесь адаптирован API UI; jobs/runtime отсутствуют.

## A9 / T36: согласованный срез и доказуемость

Задание содержит сохранённый `as_of`, ограниченный набор событий/наблюдений, версии rule/policy/model и snapshot_id. Tools читают этот срез, не произвольную текущую смесь. БД не удерживается в открытой транзакции на 60 секунд: коротко материализовать разрешённые данные, затем вызвать модель. Новые данные обновляют карту; прежний анализ отмечается stale. Назначение оператора не меняет аналитический snapshot.

AgentResult дополнительно может содержать `evidence_refs` для типизированных подтверждений `{kind:"event"|"sensor_health"|"policy", id, as_of, version}`. Только реально возвращённые разрешёнными tools ссылки, не ids от модели. Event-факт ссылается на Event; отсутствие heartbeat на сохранённый sensor-health snapshot с threshold/last_received_at/временем проверки; разрешение на policy_version. Для never_started нет выдуманного event. `evidence_event_ids` остаётся списком только настоящих событий.

Измеренные поля карточки выводит программа. Правильная ссылка не делает верным неподтверждённый текст: проверять идентификаторы, время, место, значения и политику. Гипотезы отдельно; никаких заявлений о звонке, команды машине или вероятности аварии без основания. Tool trace подтверждает реально исполненные функции.

Владелец: Гаджи + Егор С.; Лия. Backend/agent не реализованы интерфейсом.

## A10 / T35: исход модельного подозрения

PATCH `action=dismiss_model`, reason 1–500, standard revision/request_id. Только владелец рабочего `model_anomaly`, без pending transfer; нельзя применить к зоне, доступу или потере датчика. Сохраняет `disposition=rejected_model_signal`, disposition_reason, reviewed_at и историю. Raw score/ModelObservation и condition_active не подделываются. Этот модельный эпизод не считается рабочей задачей/активным подозрением и не создаётся заново на каждое окно, пока детектор не подтвердит завершение эпизода. Он доступен в истории с явной подписью. Новый подтверждённый эпизод после восстановления — новый Incident.

`close` точных нарушений по-прежнему требует owner, condition_active=false, condition_state!=unknown и отсутствия pending transfer. Диспетчер не может скрыть продолжающееся точное нарушение через dismiss. Сводка считает active условия отдельно от unclaimed рабочих задач; отклонённые модельные подозрения исключает, raw результат виден в истории. escalated_count учитывает только текущие незавершённые рабочие задачи с escalation_level>0, не весь исторический журнал.

Владелец: Егор С. + Гриша + Егор М.; Лия. Действие/история уже реализованы в mock и подготовлены в API provider.

## A11 / T38: MLP и смысл транспорта

Нормальные эпизоды включают погрузку, ожидание, остановки, повороты и различия транспорта. Аномалия описана как необычный паттерн движения, не риск столкновения. Split по episode_id до обучения scaler, threshold по validation, независимый test с другими seed/вариациями sampling и шума; baseline рядом с MLP. Указать число ложных происшествий/эпизодов и latency, не только перекрывающиеся окна. Если модель не превосходит baseline — честно объяснить ограничения.

В карточке тип транспорта и destination полезны как контекст. Допуск к W1/W2 не определяет текущую цель поездки. Автоматическое destination_mismatch не добавляется незаметно: это следующий отдельный сценарий, если понадобится. Движение demo по проездам, без прохождения сквозь здания. Координаты условные.

## Форматы provider и статус поставки

GET operator-profiles возвращает массив `{operator_id,sector_id,name}`. Read lists assets/incidents/sensors возвращают массивы; provider также принимает явные wrappers assets/incidents/sensors/operator_profiles для совместимости. /dispatch-summary — `{as_of,sectors:[{sector_id,active_count,unclaimed_count,escalated_count,operator_online,operator_ready}],unknown_count}`. /dispatch-notifications — `{notifications:[...],next_seq}`. /site может иметь sectors.map_bounds и roads для отображения; это не источник допусков и не правило детекции.

Frontend не меняет ownership оптимистически в API: сначала ответ сервера, затем перечитывание; ошибки показываются, fallback на mock отсутствует. Старый PATCH status убран. Единственный Node runner проверяет UI policy/provider/mock; серверная атомарность, межклиентная синхронизация и финальный offline показ пока не пройдены.
