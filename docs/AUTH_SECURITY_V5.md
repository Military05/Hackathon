Область: Егор С. — сервер и аккаунты; Егор М. — формы входа и административный
интерфейс; Лия — общая приёмка. Исходная версия: main
`3a751e9a30b2e1436b9e7ec7b1a3b9830aee887f`. Старые указания «без аккаунтов» и
«переключать оператора через URL» заменены новым прямым поручением координатора.
Модули `src/agent`, `src/ml`, `src/simulator` не изменяются.

## Первый запуск

Авторизация включена по умолчанию. Готовых паролей, аккаунта admin/admin и
автоматического назначения прав через регистрацию нет. Перед рабочим запуском
создайте администратора на компьютере сервера:

```powershell
.\.venv\Scripts\python.exe scripts/manage_users.py create-admin
powershell -ExecutionPolicy Bypass -File scripts/start.ps1
```

CLI спрашивает логин, имя и дважды пароль через getpass: пароль не находится в
командной строке или истории PowerShell. Для локального создания проверенного
диспетчера есть `create-dispatcher`; список аккаунтов — `list`.
Параметр `--db` или переменная `DISPATCH_DB` должны указывать ту же SQLite, что
использует сервер. Не создавайте аккаунты в другой базе по ошибке.

Регистрация на странице создаёт заявку `pending`. Администратор подтверждает её
и назначает профиль. Пользователь не может сам передать role или operator_id.
Три профиля: dispatcher-1 — логистика/склады; dispatcher-2 — производство;
dispatcher-3 — КПП. Администратор имеет отдельную роль и использует dispatcher-3
для существующих операторских API; четвёртый сектор не создаётся. Расширенные
операции передачи/резерва продолжают проверяться правилами Service.

## API для интерфейса

| Метод/адрес | Вход | Ответ |
| --- | --- | --- |
| GET /api/auth/status | без входа | enabled, configured: есть активный администратор |
| POST /api/auth/register | username, name, password | 201: user, status=pending |
| POST /api/auth/login | username, password | user, csrf_token, expires_at; cookie сессии |
| GET /api/auth/me | cookie | user, csrf_token, expires_at |
| POST /api/auth/logout | cookie + X-CSRF-Token | status=logged_out; отзыв сессии |
| GET /api/admin/users | роль admin | users: массив аккаунтов |
| PATCH /api/admin/users/{id} | status и/или operator_id + X-CSRF-Token | user |
| GET /api/admin/audit | роль admin | items: до 100 последних записей |

`user`: id, username, name, role, status, operator_id, created_at. Хеш пароля,
сырой session token и ключ источника в JSON не возвращаются. csrf_token хранится
в памяти страницы и отправляется как X-CSRF-Token на POST/PATCH/DELETE. Cookie
выдаётся браузеру автоматически; JavaScript не читает его из-за HttpOnly.
После перезагрузки страницы токен CSRF получают из /api/auth/me.

Вкладки одного профиля браузера разделяют cookie. Для трёх одновременных разных
аккаунтов используйте отдельные браузерные профили, браузеры или компьютеры.
Интерфейс отправляет `X-Expected-User` с id аккаунта, который он показывает.
При смене cookie в другой вкладке несовпадение даёт 409 session_identity_changed
до чтения, записи или выхода: рабочее место нужно обновить. Это дополнительная
проверка соответствия экрана текущей сессии, а не источник полномочий. Заголовок
необязателен для программных клиентов; сервер всё равно определяет личность
по настоящей сессии. Публичные вход и регистрация игнорируют этот заголовок.

После 401 показывайте форму входа и прекращайте старые polling запросы. 403
admin_required — недостаточные полномочия; csrf_required — нужен токен текущей
сессии; account_pending/account_blocked — заявка ожидает решения/аккаунт заблокирован.
429 auth_rate_limited — не повторять вход автоматически: подождать минуту.
Остальные ошибки имеют общий code/message/details.

`?operator=dispatcher-3` и X-Demo-Operator перестают быть источником личности:
middleware всегда подставляет профиль текущей сессии. Это распространяется и на
роутеры подключаемого агента без изменения его реализации. Программные клиенты
операторских API должны отдельно войти и отправлять сессию/CSRF; owner модулей
согласует это при интеграции. Внутренние Python-вызовы Service остаются прежними.

## Что защищено

- Пароли: PBKDF2-HMAC-SHA256, 600 000 итераций, случайная 16-байтная соль; 8–128
  символов. Хеширование выполняется вне event loop, в синхронных FastAPI endpoints
  и CLI. Хеширование увеличивает время входа, но не вычисляется при polling.
- Сессии: случайный 256-битный токен, в SQLite только SHA256 токена; срок 8 часов,
  отзыв после выхода, блокировки и смены профиля. До 10 активных сессий на аккаунт.
- Cookie: HttpOnly, SameSite=Strict, Secure при HTTPS. Проверяется CSRF-токен и
  соответствие Origin; cross-site запросы отклоняются. Прямые CLI-клиенты без
  Origin должны предъявить реальные cookie/CSRF.
- Ограничение входа по аккаунту и адресу: максимум 5 попыток за минуту. Регистрация
  ограничена 5 запросами за минуту с адреса. Память ограничителя — до 2048 ключей.
  Счётчик одного процесса обнуляется при перезапуске; это демо-уровень защиты.
- Журнал: создание/изменение аккаунтов, успешный/неуспешный вход, выход. Пароли,
  cookie и CSRF в журнал не записываются. Действия диспетчеров отдельно сохраняет
  существующий dispatch_history. Audit не является защищённым от администратора
  файловым хранилищем и не заменяет профессиональный мониторинг безопасности.
- HTTP: nosniff, запрет встраивания страницы, CSP только локальных скриптов;
  Leaflet разрешены inline стили, JS inline запрещён; API Cache-Control=no-store.

Существующие бизнес-проверки владельца, revision и передачи сохраняются. Последний
активный администратор не может заблокировать сам себя. Роль admin назначается
только локальным CLI, а не PATCH формы.

## Источники событий

POST /api/events (и POST /api/model-observations, если такой роутер подключён)
использует отдельный `X-Source-Key`. Задайте секрет `DISPATCH_SOURCE_KEY` длиной
не меньше 24 символов, сгенерированный случайно, на сервере и у внешнего источника.
Ключ не включается в frontend, site.json, Git, скриншоты или документы.
Без настроенного ключа внешний POST возвращает 503 source_key_unconfigured;
без правильного ключа — 401 source_authentication_required. Авторизация диспетчера
не даёт права подделывать телеметрию через этот адрес.

Встроенный demo_traffic и правила вызывают Service напрямую: им ключ не нужен,
и включение авторизации не останавливает движение. Внешний источник должен
обновить HTTP-адаптер отдельно у своего владельца; его файлы здесь не меняются.

## Доступ с другого компьютера

Передача логина и cookie по обычному удалённому HTTP отклоняется с 403
encrypted_transport_required. Localhost можно использовать без сертификата.
Стартовый скрипт при -Lan требует сертификат/ключ либо явно подтверждённый
защищённый сетевой туннель. Это не открывает порты маршрутизатора и не изменяет
Windows Firewall.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start.ps1 -Lan -TlsCert 'E:\certs\factory.crt' -TlsKey 'E:\certs\factory.key'
```

Используйте сертификат, которому доверяют браузеры всех участников и который
содержит нужное имя сервера/IP. Самоподписанный недоверенный сертификат создаёт
ошибки браузера; отключение проверки сертификата не является приёмкой.
Приватный ключ не коммитится. При ручном запуске используйте один worker и
`--no-proxy-headers`: forwarded заголовки не должны назначать защищённую схему.

Альтернатива: владелец отдельно проверяет, что все подключения проходят только
через реально шифрующий VPN/туннель и обычный порт недоступен из других сетей;
только после этого задаёт `DISPATCH_TRUST_ENCRYPTED_TUNNEL=1`. Эта переменная сама
не шифрует ничего и не устанавливает VPN. Если браузер видит HTTP внутри VPN,
cookie не имеет Secure, а безопасность канала обеспечивается проверенным туннелем.
Для HTTPS cookie имеет Secure и сервер отдаёт HSTS. Прямую публикацию порта
приложения в интернет текущая поставка не настраивает.

## Минимальная демонстрация для жюри

1. Без входа GET /api/assets и операторская запись получают 401.
2. Новая регистрация получает pending; войти ещё нельзя. Администратор назначает
   нужный из трёх профилей, после этого вход разрешён.
3. Диспетчер открывает админ-API — 403. Меняет operator в URL/заголовке — сервер
   продолжает действовать от его настоящего профиля.
4. Запись без CSRF/с чужого сайта — 403; обычная операторская запись с токеном
   работает. После выхода старая сессия получает 401.
5. Без правильного source key нельзя отправить телеметрию; встроенная демонстрация
   продолжает двигаться. В журнале видны вход/выход/решение по регистрации.

Автоматическая проверка: `python -m unittest tests.runtime.test_auth -v`.
Старые тесты бизнес-контрактов запускают create_app(enable_auth=False), чтобы
независимо проверять правила; проверка защиты использует реальное включённое
значение по умолчанию. `DISPATCH_ENABLE_AUTH=0` предназначен только для локальных
тестов, никогда для LAN. Полная приёмка трёх браузеров, доверенного TLS и целевых
ноутбуков выполняется отдельно; unit tests не доказывают её.
