## Этап 1 — вход и базовая защита / Егор С. + Егор М.

Сервер: PBKDF2, заявки pending, локальный bootstrap администратора, сессии/CSRF,
проверка полномочий, ограничения входа, журнал входов, отдельный ключ источника.
Интерфейс: вход/регистрация, назначенный сектор, выход и минимальная админ-панель.
Оператор определяется сессией; URL и demo-заголовок не дают новую личность.
Подробности: [AUTH_SECURITY_V5](AUTH_SECURITY_V5.md).

## Этап 2 — КПП и начало смены / Егор С. + Егор М.

ACCESS-G1 фиксирует подтверждённые входы/выходы. U1/U2/U3 имеют допуск; U4
демонстрирует проход без допуска. Сначала три разрешённых входа в сценарии shift,
потом транспорт; одна shift_id связывает сохранённые проходы и position.
Сигналы продолжаются во время ожидания, при ошибке проверки транспорт не стартует.
Журнал: поиск, направление, допуск, период, страницы и CSV. Отдельная сводка
считает реальные успешные действия диспетчера. [GATE_SHIFT_V5](GATE_SHIFT_V5.md).

## Этап 3 — зоны, дороги, камера / Егор М. и общий site.json

18 объектов сохранены; дорожные оси не повторяются, края не перекрывают поверхность
на узлах. Z1/Z2 — оранжевые зоны по допуску, Z3 — красная запретная со штриховкой.
Секторы обозначены без заливки; голубой заливки нет. «Мой сектор» приближает
западные склады, основные цеха или КПП. Время сигналов видно у объектов/датчиков.
Мигает выбранное происшествие, обычные обновления не перемещают камеру.
[MAP_V5](MAP_V5.md).

## Этап 4 — плотная страница и удобства / Егор М.

Карта, журнал и КПП размещаются в основных колонках; пустая карточка компактна,
сценарии/диагностика сворачиваются. Сводка работы и ограниченные CSV доступны
без лишних служб. Существенные этапы показываются в правой панели приложения
во время разработки; это индикатор поставки, а не рабочая функция диспетчера.

## Этап 5 — общая приёмка и main / координатор + Лия

Сначала объединяются узкие проверенные ветки и текущий main с сохранением чужих
изменений. Проверяется один фиксированный SHA: три входа в разных профилях
браузера, права, люди→транспорт, передача, камера, CSV, восстановление/перезапуск.
Результаты публикуются в [RELEASE](RELEASE.md) с PASS/FAIL/NOT RUN.
Проверенную базовую поставку координатор объединяет в main по поручению пользователя;
force push не применяется. Полный продукт с ML/ИИ требует отдельного общего gate.

## Передача отдельным владельцам

Гриша получает общий site.json, неизменённый JSON Event, новый ACCESS-G1 и
условие внешнего HTTP `X-Source-Key`. Гаджи получает API с сессией/CSRF и реальные
query функции. Их каталоги не переписываются ради новой интерфейсной задачи.
Долгие модельные вычисления остаются вне SQLite-транзакций и приёма событий.
Включение env-флага не устанавливает модуль или модель и не подтверждает работу.

Новую локальную задачу начинают после сохранения собственных изменений:

```powershell
git switch main
git pull --ff-only origin main
git rev-parse HEAD
git switch -c codex/your-small-task
```

В handoff указывают ветку, полный SHA, разрешённые файлы, контракты, реальные
команды проверок и незавершённость. Не редактируют чужой грязный checkout.

## Нагрузка

Базовый путь — 6 источников на 1 Гц, не более 15 кадров/с карты, один FastAPI
worker и SQLite; без GPU/Docker и новых тяжёлых установок. История растёт на диске.
Три клиента, подключённая ML/LLM, целевые ноутбуки и доверенный удалённый TLS
измеряются отдельно. Результаты изолированных модулей не заменяют этот gate.
