# Чёткий план реализации задания №3 — три диспетчера

Обновлено 7 октября 2026. Это полный согласованный целевой объём на два дня. Реализация ещё не подтверждена. [Контракт v2](CONTRACTS.md), [поведение диспетчерских](DISPATCH_OPERATIONS.md), [конкретные задачи](BACKLOG.md).

## 1. Результат

Один локальный сервер получает данные модельного предприятия, хранит их, автоматически обнаруживает нарушения и распределяет происшествия на три рабочих места. Люди одновременно реагируют, принимают и передают случаи; система напоминает и эскалирует непринятые/зависшие случаи. Обученная маленькая MLP ищет необычное движение, общий локальный агент объясняет выбранный случай доказательствами. Без интернета работают все эти части после предварительной установки.

Обязательны: карта и позиции; доступ и состояние датчиков; D1–D3; одновременные тревоги без дублей; три секторных профиля; общий обзор; атомарное принятие; передача с подтверждением/тайм-аутом; напоминания/эскалация; D4 с MLP и отчётом; живые tools агента; сохранение/перезапуск; перенос и показ на ноутбуке.

Исключены: аккаунты, пароли, смены, сложные права; прогноз столкновений; рация; команды оборудованию. Возможность связаться с водителем — действие человека, не скрытая функция ИИ.

## 2. Модель предприятия

W1/W2 — склады, P1/P2 — цеха, O1 — офис, G1 — КПП; три машины V1–V3, сотрудники U1–U3, position/access/heartbeat датчики. Координаты 0..100, прямоугольные зоны, граница включена. site.json — единственный источник геометрии и привязок.

logistics → dispatcher-1, production → dispatcher-2, coordination → dispatcher-3. Участков отображения больше трёх; каждый относится к одному сектору. Общие дороги и unknown обслуживает coordination. Три профиля — UI для людей, одна LLM для всех.

## 3. Демонстрационные сценарии и критерии

| ID | Сценарий | Что должно быть доказано |
| --- | --- | --- |
| D1 | запрещённый въезд | тревога появилась автоматически, evidence, нет дублей |
| D2 | проход без допуска | таблица допусков, адресованный сектор, исходный access event |
| D3 | потеря/возврат heartbeat | offline после первого heartbeat, восстановление, история |
| D4 | необычное движение | реально обученная MLP, версия, порог, независимые метрики |
| D5 | три одновременных нарушения | три сектора получают случаи, чужая карточка/LLM не блокируют показ |
| D6 | два оператора принимают один случай | один assigned_operator_id, второй получает 409 |
| D7 | передача с подтверждением | прежний отвечает до acceptance, новый затем, история одна |
| D8 | ожидание/исчезновение/истечение передачи | напоминание и эскалация того же incident_id, нет потока дублей |
| D9 | новые тревоги и неизвестное место | постоянная панель, incoming transfer виден вне своего сектора, unknown у координатора |
| D10 | restart, повтор команд, интернет выключен | данные, ownership и уведомления сохранены, весь локальный показ работает |

## 4. Поэтапная реализация

Этап C0: согласовать CONTRACTS v2, геометрию/ID, интерфейсы query и модельный API. Все готовят свои тестовые данные независимо. Гаджи не ждёт сервер, Гриша не ждёт агента.

Этап C1 / beta-1: реальная цепочка симулятор → API → SQLite → правила → три простых секторных экрана. D1–D3, базовый routing, принятие одним оператором, журнал и карточка. Тег только после короткой проверки. Это промежуточный результат, не сокращение финальной цели.

После C1 три параллельных потока: Егор С./Егор М. делают обязательную beta-2 (передача, присутствие, напоминания, эскалация, общая сводка, звук); Гаджи/Гриша делают ML и агента в feature/beta1-f1; Лия проверяет фиксированный beta-1 и принимает маленькие готовые задачи.

Этап C2: beta-2 и отдельные ML/agent готовы к объединению. Гаджи включает актуальный main в общую F1; владельцы решают конфликты поведения и форматов. Лия проверяет один совместный SHA.

Этап C3: D1–D10, все обязательные операции и локальная модель на ноутбуке. Чистый клон, отключённый интернет, финальный показ. Один интегратор-человек объединяет PR и ставит тег после проверки.

## 5. Расписание относительно старта

| Время | Егор С. / Егор М. | Гаджи / Гриша | Лия / контроль |
| --- | --- | --- | --- |
| первые 30 минут | v2, site.json, секторные поля | API кандидата, события normal | критерии, окружение, D1–D10 |
| до 2 часов | один случай полностью: API/БД/карта | настоящий tool call; генератор эпизодов | проверить совпадение ID и данных |
| первая половина дня 1 | D1–D3, routing, claim, три профиля | tools/loop; обучение отдельно | smoke C1, beta-1 |
| вторая половина дня 1 | transfer/presence/escalation/summary | очередь/evidence; MLP и отчёт | регрессия beta-1 + готовые модули |
| конец дня 1 | конкурентные операции и новые экраны | первые живые интеграции | совместный кандидат или точные блокировки |
| первая половина дня 2 | fixes и beta-2 | main → F1, ноутбук/модель | D1–D10 на совместном SHA |
| за 3 часа до сдачи | никаких новых требований | исправления обязательного пути | freeze функций |
| за 2 часа | чистая установка и offline показ | веса/артефакт/ресурсы готовы | независимый повтор |
| последний час | репетиция, команды, финальный PR | живой анализ и метрики | RELEASE по фактическому результату |

Часы ориентировочные, не гарантированные сроки. Если C1 задерживается, оба full-stack помогают основной цепочке. Если API модели не работает за первые 1–2 часа, Гаджи фиксирует конкретную ошибку и проверяет другой совместимый локальный runtime/модель; не тратит весь день на красивый чат.

Каждая блокировка: причина, владельцы, следующий проверяемый шаг, время; не «ждём весь backend». Общий main.py/schema/requirements меняет Егор С. или согласованный маленький PR. Общий UI entrypoint — Егор М.

## 7. Проверки и полнота

Каждая задача закрывается кодом, примером и фактической проверкой. Синтетические метрики подписываем; inference не называется прогнозом аварии. Принятие не равно восстановлению condition; очередь анализа не очередь тревог. Передача/эскалация обязательны, их нельзя молча отложить. Если дедлайн наступил до выполнения части, RELEASE честно описывает незавершённость; согласованная цель не объявляется достигнутой.

Codex получает одну конкретную задачу, ветку, разрешённые файлы, v2 и критерий. Проверять поведение и соединять части начинаем в первый день, не перед сдачей. [Git](../TEAM_WORKFLOW.md), [помощь Codex](../CODEX_USAGE.md).
