# План реализации задания №3

Если слово незнакомо, открой [словарь простыми словами](GLOSSARY.md). Команды и названия полей не переводим: в коде они должны остаться точными.

## 1. Что требуется и что показываем

Задание требует мониторинг и контроль предприятия со складскими, офисными и производственными зданиями. Вход — события датчиков транспорта и доступа; визуализация на карте желательна.

Наш пользователь — диспетчер. Он видит транспорт, доступ в здания, здоровье датчиков и происшествия. Собственная небольшая нейросеть оценивает необычное движение. Локальный агент объясняет выбранное происшествие по данным системы.

Уточняем у организаторов допустимость модельного предприятия и симулятора. Если дадут реальные данные, сохраняем контракт и добавляем адаптер их формата.

## 2. Демонстрационное предприятие

План — прямоугольник с локальными координатами 0..100, единица: условная единица схемы, не метр.

Здания: склад сырья W1, склад готовой продукции W2, цех P1, цех P2, офис O1, КПП G1. Есть дороги и две контрольные зоны Z1/Z2. В версии на два дня зоны — прямоугольники, граница включена.

Объекты: три транспортных средства V1–V3, три сотрудника U1–U3, датчики позиций, доступа и heartbeat. Конкретные id и допуски определяет файл data/demo/site.json, который создаёт A1 при разработке.

## 3. Четыре демонстрационных сценария

| ID | Сценарий | Основа результата |
| --- | --- | --- |
| D1 | Транспорт входит в запрещённую для него зону | Геометрия + допуски, точное правило |
| D2 | Сотрудник совершает проход без допуска | Событие доступа + таблица разрешений |
| D3 | Датчик не передавал heartbeat более 5 секунд | Время приёма на сервере, точное правило |
| D4 | Необычные остановки/изменения движения | Собственная MLP (небольшая многослойная нейросеть) на окнах событий; отдельная оценка модели |

После любого выбранного происшествия D1–D4 диспетчер запускает локального агента. Он читает факты через инструменты, выводит краткое объяснение и ссылки на evidence (исходные события, подтверждающие вывод). Основной мониторинг работает без LLM (большая языковая модель).

## 4. Минимум и расширение

Обязательный минимум beta-1: реальные API (способ обмена данными с сервером) и SQLite, план территории, нормальные события, D1–D3, журнал, карточка происшествия, инструкция запуска.

Целевая F1: D4 с сохранённой собственной MLP и отчётом проверки + локальный агент с вызовом инструментов и evidence. Это главный дополнительный результат full-stack (разработчик и серверной части, и интерфейса) пары.

Резерв, если часть ИИ не проходит проверку: сохранить честный статус «модель не готова/агент недоступен» и работающий мониторинг. Цель не считать достигнутой, пока neural/agent не показаны; на защите описать фактически реализованный объём.

Не берём за два дня: обучение большой LLM с нуля, управление реальными воротами/машинами, несколько автономных агентов, Kubernetes, видеоаналитику, сложный роутинг транспорта, GIS и десятки сервисов.

## 5. Стек

Основной сервер: Python 3.11+, FastAPI; база: SQLite. Интерфейс: HTML/CSS/JS и собственная SVG-схема, которую отдаёт тот же сервер. Для MVP один процесс сервера и одна точка записи SQLite; фронт опрашивает API раз в секунду.

Нейросеть: scikit-learn Pipeline(StandardScaler, MLPClassifier), скрытые слои 16 и 8, бинарная задача normal/anomaly, CPU (процессор). Это собственное обучение небольшой сети, а не собственная большая языковая модель.

Агент: Ollama на отдельном процессе того же компьютера либо компьютере B1. Кандидат для ранней проверки — qwen3:4b с поддержкой tools (инструменты агента). Скорость и качество ещё не проверены на оборудовании команды; точное имя и результат фиксируем в TEAM.

## 6. Два дня

| Время относительно начала | Что делаем | Проверка |
| --- | --- | --- |
| 0–30 мин | Роли, регламент, контракт v1, Issues (задачи и сообщения об ошибках) | Все получили доступ |
| 30–60 мин | A1 — схема/модели; A2 — карта; B2 — normal (обычное поведение) simulator; B1 — проверка локальной LLM; QA (тестировщик) — сценарии | Контракт и события совпали |
| 1–3 ч | A1/A2 собирают обязательный скелет; B1/B2 выполняют независимые приготовления | Один сценарий целиком, затем D1–D3 |
| После smoke (короткая проверка запуска и основного сценария) beta-1 | Пара A — beta-2; пара B — F1; QA — полная проверка beta-1 | Три потока одновременно |
| До конца дня 1 | Маленькие PR (запрос на объединение изменений), фиксы, первая синхронизация main → F1 | Есть совместный кандидат либо точный список блокировок |
| День 2, первая половина | Нейросеть, агент, интеграция и проверка | Все D1–D4 и evidence |
| За 3 ч до сдачи | Стоп новым функциям | Только обязательные баги и демо |
| За 2 ч | Чистый клон, запуск, резервный показ | Повторение без автора |
| Последний час | Репетиция, журнал SHA (идентификатор конкретной версии кода), финальный тег | Продукт соответствует показанным функциям |

План ориентировочный, точные часы определяют организаторы. Если скелет задерживается, оба full-stack помогают его закончить.

## 7. Как проверяем пользу ИИ

Правила: нарушения D1–D3 обнаруживаются, нормальные события не создают ложных случаев.

MLP: отдельный набор эпизодов, confusion matrix (таблица верных и ошибочных предсказаний), precision/recall/F1, число false positives (ложные тревоги), время inference (применение обученной модели). Порог выбран на validation (проверочная часть данных для настройки), финальный test (итоговая тестовая часть данных) не участвует в подборе.

Агент: выбирает разрешённые tools, не выдумывает id/измерения, отличает факты от предположений, завершает работу в пределах бюджета. Проверяем реальные запросы; заранее сохранённый текст не считается живым ответом.

Нагрузка: меряем наш демонстрационный поток, не утверждаем промышленную производительность без теста.

## 8. Показ на защите

Нормальное движение → нарушение зоны → доступ без допуска → потеря heartbeat → необычный эпизод MLP → запрос «почему это происшествие?» → агент запрашивает историю и объясняет evidence.

Коротко покажите независимость мониторинга: остановка LLM не останавливает события/правила/карту. Все данные симулятора отмечены demo (демонстрационные данные); качество на симуляции не переносим автоматически на настоящий завод.
