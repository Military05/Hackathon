## 2. Почему не ставим четыре сервера

ha-floorplan зависит от среды Home Assistant. ThingsBoard содержит собственные Java-сервисы, хранилище, правила, API и большой интерфейс. Traccar — самостоятельная GPS-платформа с протоколами реальных трекеров. Их API, идентификаторы, пользователи и состояния не совпадают с нашим v2.

Запустить все платформы одновременно, затем согласовать четыре модели данных и добавить наши диспетчерские операции — отдельная большая интеграция. За два дня полезнее готовая библиотека карты и перенос маленьких независимых частей. Поэтому рабочая цепочка одна:

```text
один симулятор → FastAPI → SQLite → правила / MLP
                                   ↓
                       три браузерных диспетчерских
                                   ↓ отдельный запрос
                        одна очередь локального агента
```

Нет Docker, Kafka, MQTT-брокера, Home Assistant, Java-сервера ThingsBoard, Java-сервера Traccar, 3D-движка или картографических тайлов. Дополнительные процессы не нужны для модели предприятия. Если позже появится физическое оборудование, адаптер события подключается перед тем же POST /api/events.

## 3. Leaflet: свой план вместо карты Земли

Наши координаты — условные единицы, диапазон x/y 0..100. В Leaflet используется CRS.Simple. Порядок Leaflet — [y,x]; нельзя передать [x,y] и затем вручную менять только часть объектов. Здания, зоны и дорога берутся из одного data/demo/site.json.

Для SVG с началом координат сверху слева отображение может преобразовать y в 100-y. Преобразование применяется в одном адаптере ко всем точкам. Серверные правила и исходные события всегда используют исходные x/y. Подпись карты прямо говорит, что это план модельного предприятия.

Сцена: O1 — центральный офис; W1/W2 — склады; P1/P2 — цеха; G1 — КПП. От КПП и центрального проезда отходят дороги к офису, складам и производству. Маршруты проходят по проездам и площадкам погрузки, а не сквозь здания. Зоны Z1/Z2 — ограничения доступа, не спутниковые снимки и не случайные цветные прямоугольники.

Геометрия, допуски и текущая цель поездки — разные данные. Возможность посетить склад не означает, что транспорт сейчас направляется туда. Красная зона — правило допуска. Синий/зелёный участок — контекст сектора. Движущийся маркер — последняя телеметрическая позиция.

## 4. ha-floorplan: точный исходник и адаптация

Исходный файл: [home.css](https://github.com/ExperienceLovelace/ha-floorplan/blob/56b969418215e99081650534194990d061cdf35a/docs/_docs/floorplan/examples/home/home.css). Git blob: 437f41cb2b4a774e1f70a39616e18cf400074755.

Скопированы CSS-правила .binary-sensor-on, .binary-sensor-off и vector-effect: non-scaling-stroke. В нашей легенде значение цвета подписывается рядом с датчиком. on/off не подменяет трёхзначный серверный health: online/offline/unknown. Unknown получает отдельное оформление. Offline определяется сервером по heartbeat, а не по цвету SVG или отсутствию анимации.

Полный floorplan-element и его вычисляемые конфигурации не подключаются. Это позволяет обойти зависимость от Home Assistant и сохранить обычный HTML/JS.

## 5. ThingsBoard: состояние тревоги

Исходники:

- [AlarmStatus.java](https://github.com/thingsboard/thingsboard/blob/258298131ca811fd50008636e08dc384867936ce/common/data/src/main/java/org/thingsboard/server/common/data/alarm/AlarmStatus.java), blob bb445875d2696b8999df974f0f926f4ae2eed87a.
- [AlarmSeverity.java](https://github.com/thingsboard/thingsboard/blob/258298131ca811fd50008636e08dc384867936ce/common/data/src/main/java/org/thingsboard/server/common/data/alarm/AlarmSeverity.java), blob ddfd0544a5011fbe2194b09f0aa19bed27d85bd3.

Четыре комбинации ACTIVE_UNACK, ACTIVE_ACK, CLEARED_UNACK, CLEARED_ACK пригодны для объяснения двух независимых вещей: продолжается ли условие и принял ли его человек. У нас основной wire-контракт сохраняет status=open/acknowledged/closed и condition_active. Дополнительное вычисляемое представление не заменяет status и не освобождает owner.

| Наше состояние | Представление ThingsBoard | Смысл |
| --- | --- | --- |
| condition_active=true, status=open | ACTIVE_UNACK | нарушение продолжается, никто не принял |
| condition_active=true, status=acknowledged | ACTIVE_ACK | нарушение продолжается, есть ответственный |
| condition_active=false, status=open | CLEARED_UNACK | условие восстановилось, случай ещё требует обработки |
| condition_active=false, status=acknowledged/closed | CLEARED_ACK | условие восстановилось и случай принят/обработан |

При condition_state=unknown нельзя утверждать CLEARED: потеря датчика не доказывает выход из зоны. Для такого случая наше приложение сохраняет неопределённость отдельно. Бинарное представление ThingsBoard не должно скрывать неизвестное состояние.

Severity нашего проекта info/warning/critical не заменяется пятизначным enum ThingsBoard. AlarmSeverity сохранён для изучения, а не как обязательный runtime enum. Не копируем правила создания доступа/зоны из платформы: они должны использовать нашу геометрию, допуски, evidence и пороги.

## 6. Traccar: геозона без GPS

Исходник: [GeofencePolygon.java](https://github.com/traccar/traccar/blob/b89a69251bded7036488c765ec17499cb5e88346/src/main/java/org/traccar/geofence/GeofencePolygon.java), blob 13f6658ef17adff3a885cb61f9730522adeaa3ec. Сохранён и [исходный тест](https://github.com/traccar/traccar/blob/b89a69251bded7036488c765ec17499cb5e88346/src/test/java/org/traccar/geofence/GeofencePolygonTest.java).

Методы preCalculate и containsPoint реализуют проверку пересечений луча с рёбрами полигона. В порте на Python остаётся эта проверка; координаты переводятся в обычную плоскость x/y. WKT-парсер, площадь Земли, Spatial4j, Java, километры и нормализация линии перемены дат для нашего плана не нужны.

Наше существенное изменение: точка на ребре или углу находится внутри зоны. Перед подсчётом пересечений проверяется принадлежность отрезку. Лия проверяет внутреннюю точку, внешнюю, четыре края и углы прямоугольника. Использование алгоритма без проверки границы нарушило бы CONTRACTS.

## 7. Что означает «работа датчиков»

В этой версии датчики — зарегистрированные источники событий, симулятор формирует их показания. Position даёт координаты машины; access фиксирует подтверждённый проход сотрудника; heartbeat показывает связь с конкретным источником.

Это не драйвер физического датчика и не доказательство промышленной точности. Заимствование визуализации или геозоны не создаёт источник реальных измерений. Весь демо-поток помечен demo=true. Сервер проверяет ID, тип, координаты, время и повторы; сохраняет исходное Event; правила создают Incident с evidence_event_ids.

Точное обнаружение зоны/доступа/отсутствия heartbeat выполняется без LLM. MLP оценивает необычное движение. Агент объясняет уже зарегистрированные факты через разрешённые tools. Эти три механизма нельзя выдавать за один большой «ИИ, который всё определяет».

## 9. Ресурсы целевого ноутбука

Из повторно просмотренного скриншота характеристик: AMD Ryzen 7 8845HS, 32 GB RAM, встроенная AMD Radeon 780M, Windows 11 x64. Это описание оборудования, а не результат нагрузочного прогона приложения. Личные идентификаторы устройства в проект не добавляются.

Стартовая нагрузка: 3 машины, U1–U3, небольшой фиксированный набор position/access/heartbeat-датчиков, 3 рабочих места браузера. Один серверный worker, одна SQLite; одна симуляция для всех клиентов. Каждый браузер не создаёт свои машины и не обучает свою модель.

LLM: одна running job, до 2 queued с проверкой оставшегося времени, runtime-модель настраивается на контекст 4096 tokens, ответ max_tokens=450. Текущий клиент также ограничивает объём сериализованного разговора 6000 символами; это грубый предел размера, а не точный токенизатор. Модель загружается в локальном runtime один раз. MLP загружается один раз, обучение выполняется отдельно. Большие модели/venv/runtime размещаются на E:, не в Git. Встроенная графика использует общую RAM, поэтому размер модели выбирается после замера доступной памяти и скорости.

До заявления «работает на ноутбуке» Лия проводит 15-минутный прогон 3 браузеров + симуляции + одной аналитической задачи, затем перезапуск без внешнего интернета. Фиксирует CPU/RAM, частоту событий, received→incident→UI, inference, полный agent latency и состояние интерфейса в [PERFORMANCE](PERFORMANCE.md). Измерения на другой машине не засчитываются как PASS ноутбука.

При недостаточной скорости сперва уменьшаем размер/квантование локальной модели и контекст в допустимом диапазоне, затем согласованно корректируем частоту демо. Не отключаем точные правила или передачу, чтобы скрыть перегрузку. Если LLM недоступна, карта/правила/диспетчерская продолжают работать с явным статусом unavailable; это отказоустойчивость, а не успешная проверка агента.
