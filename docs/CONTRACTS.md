# Контракт ядра, интерфейса и функций

Тема и стек ещё не выбраны. Это заполняемый договор команды, а не API уже реализованного приложения.

## Принцип

Интерфейс получает ввод пользователя → вызывает сценарий ядра → показывает результат. Хранилище вызывается через согласованную точку. Для CLI это обычные функции/классы в одном процессе; HTTP, JSON и отдельный сервер не обязательны.

До начала параллельной работы A1 и A2 заполняют контракт v1, оба full-stack просматривают его. Заглушки используют тот же формат. Изменение общего формата фиксируем до изменения потребителей.

## Для каждой операции

Скопируйте этот блок и заполните конкретно.

| Поле | Описание |
| --- | --- |
| Название и назначение | что пользователь получает |
| Сигнатура / точка вызова | функция/метод; для API — метод + путь |
| Вход | поля/типы, обязательность, допустимый диапазон |
| Успешный выход | тип/поля и смысл каждого значения |
| Ошибки | категории/коды, текст для пользователя, способ передачи |
| Побочные эффекты | что сохраняется/изменяется, либо «нет» |
| Пустой ввод | что произойдёт |
| Повтор операции | создаёт дубль, заменяет, возвращает то же или ошибку |
| Пример нормального вызова | вход → ожидаемый выход |
| Пример ошибочного вызова | вход → конкретная ошибка |
| Кто реализует / кто потребляет | A1/A2/B1/B2 |
| Проверка | сценарий / тест / Issue |

## Данные и хранение

Согласовать только то, что нужно заданию:

- Имена, типы и идентификаторы общих сущностей.
- Формат чисел, дат, кодировки текста, сортировка при необходимости.
- Где данные живут и что сохраняется после перезапуска.
- Кто владеет записью и как обрабатывается недоступное хранилище.
- Версия формата файла/таблицы, если формат может измениться.
- Воспроизводимый маленький набор fixtures.

## Интерфейс

Для CLI: команды/пункты меню, аргументы, ввод, формат вывода, неправильный ввод, выход и коды возврата. Для web/desktop: действия, состояния ожидания/ошибки и результат. Не фиксируем конкретный вариант до выбора формата.

Главное ядро не должно требовать интерактивного input/отрисовки для обычного теста. Исключения, если они нужны выбранному стеку, явно обсуждаем.

## Изменение контракта

1. Issue с причиной и примером до/после.
2. Просмотр другой пары.
3. Решение: совместимое расширение, адаптер или согласованная замена.
4. Обновление версии/таблицы.
5. PR производителей и потребителей.
6. Проверка старого обязательного сценария плюс нового поведения.
