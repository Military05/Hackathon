# A1 — разработчик бэкэнда и основы

## Твой результат

Один сервер принимает события, сохраняет факты, применяет точные правила и отдаёт данные карте. После каждого PR main запускается. Ты предварительный интегратор main; остальные разработчики помогают в ревью и конфликтах.

Общее чтение: [старт](../START_HERE.md), [план](../TASK_03_PLAN.md), [контракты](../CONTRACTS.md), [архитектура](../ARCHITECTURE.md). Своё имя и часы впиши в [TEAM](../TEAM.md).

## Первые действия

1. Подтверди с A2/B1/B2 контракт v1, coordinate bounds, event ids и UTC.
2. Создай requirements.txt с нужными пакетами и после проверки зафиксируй версии.
3. Создай FastAPI entrypoint src/core/main.py и единый доступ к SQLite.
4. Создай data/demo/site.json: шесть зданий, зоны, объекты и допуски.
5. Дай A2 реальный GET /api/site, затем POST /api/events.
6. Получи normal events B2. Не блокируйся: минимальное событие из CONTRACTS достаточно для первой ручной проверки.

## Твои файлы

src/core/, src/storage/, requirements.txt, data/demo/site.json. Ты координатор общего router/entrypoint и схемы БД.

Не меняй модули агент/ML без автора. Для них заранее сделай согласованные точки подключения. Подключение новых routes выполняется одним небольшим PR, чтобы B1/B2 не переписывали main.py одновременно.

## Минимум beta-1

- FastAPI раздаёт web-интерфейс с того же адреса.
- POST events валидирует schema, ids, время и координаты.
- SQLite хранит события и evidence.
- GET assets возвращает последнюю позицию; старое событие не откатывает текущую позицию.
- Правила forbidden_zone, unauthorized_access, sensor_offline создают происшествия.
- GET incidents/detail возвращает факты, состояние и evidence.
- PATCH status позволяет оператору менять open → acknowledged → closed, не стирая историю.
- Базовый health показывает readiness rules/ML/agent.
- Инструкция запуска проверена QA/A2.

Дубли одинакового события не создают повторную запись/происшествие. Один непрерывный случай нарушения — одно активное происшествие; восстановление отмечаем отдельно. Для нового случая после восстановления можно создать новое.

## Улучшения beta-2

После beta-1 бери маленькие Issues: ошибки и идемпотентность, неправильные id, восстановление связи, фильтры, состояние моделей/агента, журнал lifecycle.

Сохраняй контракт v1. Если меняешь его — согласуй обе пары до изменения, запиши migration. Не включай незаконченный эксперимент в main.

## Подключение F1

B2 передаёт analyze_window и ModelObservation. B1 — agent service/tools. Ты даёшь безопасный интерфейс чтения событий/допусков и сохранения analysis, подключаешь routes.

Мониторинг не вызывает Ollama в POST events. Agent job запускается отдельно от приёма. ML загружается один раз, обучение выполняется отдельно. Ни ожидание модели, ни inference не держит транзакцию SQLite.

Для MVP один uvicorn worker и один scheduler. Долгую CPU-работу выносим из event loop; Ollama — отдельный процесс.

## Ветка и PR

Если клон уже есть, сначала чистый git status:

~~~powershell
git switch main
git pull --ff-only origin main
git switch -c core/backend-skeleton
~~~

После кодирования: git add конкретные файлы → diff --cached → commit → push -u origin core/backend-skeleton. PR base=main. Команды подробно в [TEAM_WORKFLOW](../../TEAM_WORKFLOW.md).

После слияния новая задача начинается новой веткой от свежего main, например core/beta2-validation. Не продолжаешь старую skeleton ветку.

## Самопроверка перед QA

- Нормальное событие принято, записано и видно A2.
- Дубликат не дублирует incident.
- Ошибки возвращают согласованные 422/404/409.
- Событие запрещённой зоны создаёт evidence.
- Разрешённый проход не даёт тревогу, запрещённый даёт.
- После 5 секунд молчания появляется один offline incident.
- Выключенная LLM не останавливает API и правила.
- База сохраняется после перезапуска.

Передай QA Issue/PR, SHA, запуск и входной сценарий. Результат не считается готовым по одному /health.

## Интеграция

После smoke beta-1 ставишь тег. После готовности следующей основы beta-2. Координатор B1 включает main в F1; вместе разбираете несовместимость. После QA объединяешь итоговый PR merge-коммитом и проверяешь main.

Не выполняй merge одновременно с другим оператором. При блокировке расскажи, какой contract/file/Issue нужен, а не просто «жду фронт».
