# A1 — бэкенд: сервер, данные и правила

Ты создаёшь основу приложения: приём показаний, базу данных, точные проверки и ответы для карты. Предварительно ты также интегратор — человек, который объединяет проверенные изменения в общую ветку. Остальные помогают с проверкой и конфликтами.

[План](../TASK_03_PLAN.md), [форматы данных](../CONTRACTS.md), [устройство системы](../ARCHITECTURE.md), [словарь](../GLOSSARY.md).

## Первые действия

1. Согласуй с A2/B1/B2 поля событий, идентификаторы, координаты и время.
2. Создай `requirements.txt` — список библиотек. После проверки закрепи совместимые версии.
3. Создай `src/core/main.py` — точку запуска сервера FastAPI.
4. Подключи SQLite (базу данных в файле).
5. Создай `data/demo/site.json`: здания, зоны, машины, сотрудники, датчики и допуски.
6. Дай A2 получение схемы через `GET /api/site`.
7. Реализуй приём события через `POST /api/events`. POST означает отправку данных серверу.
8. С B2 запусти обычные события симулятора и проверь полный путь: событие → база → карта.

Не жди готовности всей системы. Одного корректного события из контракта достаточно для первого соединения модулей.

## Твои файлы и границы

Ты отвечаешь за `src/core/`, `src/storage/`, `requirements.txt` и `site.json`. Общую схему базы и подключение адресов сервера координируешь ты.

A2 делает интерфейс, B1 — локального агента, B2 — симулятор и нейросеть. Дай им согласованные точки подключения; не переписывай их модули без договорённости. Изменения общего `main.py` вносите по одному небольшому запросу.

## Первая рабочая версия — beta-1

- Сервер отдаёт страницу и принимает события датчиков.
- Проверяются формат, время, координаты и существование объектов.
- События и подтверждающие их данные сохраняются в SQLite.
- Карта получает последние позиции; старое событие не откатывает текущую позицию.
- D1: вход машины в запрещённую зону.
- D2: проход сотрудника без допуска.
- D3: отсутствие heartbeat (сообщения датчика «я работаю») дольше 5 секунд после первого такого сообщения.
- Есть список и карточка происшествия, его история и evidence (ссылки на исходные события).
- Оператор меняет состояние `open → acknowledged → closed`: открыто → увидено диспетчером → закрыто.
- Проверка состояния системы показывает доступность правил, нейросети и агента.
- Команды [запуска](../RUNBOOK.md) повторил другой участник.

Один непрерывный случай — одно происшествие. Повтор одинакового события не обрабатывается заново: это идемпотентность. Восстановление связи и выход из зоны отмечаются отдельно, история остаётся.

## Вторая версия основы — beta-2

После короткой проверки beta-1 QA (тестировщик) начинает её полную проверку. Ты с A2 продолжаете улучшать основу: ошибки, восстановление, фильтры, состояния компонентов.

Сохраняй согласованные форматы. Если нужны изменения, заранее сообщи обеим парам и обнови CONTRACTS. Незаконченную работу держи в личной ветке.

## Как подключить нейросеть и агента

B2 передаёт анализ окна движения и ModelObservation (результат оценки модели). B1 передаёт службу анализа и tools (инструменты чтения данных).

Агент не вызывается при каждой точке транспорта. Его запускает отдельная задача по запросу диспетчера. Нейросеть загружается один раз, обучение запускается отдельной командой.

Не держи транзакцию базы открытой во время ожидания модели. Используйте один процесс сервера и один таймер проверок. Долгие вычисления не должны останавливать приём событий; Ollama работает отдельным процессом.

## Ветка и отправка

При чистом `git status`:

~~~powershell
git switch main
git pull --ff-only origin main
git switch -c core/backend-skeleton
~~~

Так ты получаешь свежий `main` и создаёшь свою ветку. Затем:
1. Проверь код.
2. `git add путь-к-файлу` — подготовь конкретные изменённые файлы.
3. `git diff --cached` — просмотри подготовленные изменения.
4. Сохрани и отправь:

~~~powershell
git commit -m "Добавить сервер и приём событий"
git push -u origin core/backend-skeleton
~~~

5. Создай PR (запрос на объединение): `base=main`, твоя ветка `core/backend-skeleton`.
6. Укажи запуск, пример события и ожидаемый результат. Передай на проверку другому разработчику и QA.

Следующая задача — новая ветка от свежего main, например `core/beta2-validation`. Полный порядок в [Git-инструкции](../../TEAM_WORKFLOW.md).

## Перед передачей

Проверь нормальное событие, повтор, ошибки 422/404/409, разрешённый и запрещённый проход, зону, потерю и возврат связи, перезапуск базы. Выключенная LLM (языковая модель) не должна останавливать правила.

Передай ссылку на задачу и PR, SHA (идентификатор версии: `git rev-parse HEAD`), команду запуска и сценарий. Один успешный ответ о здоровье сервера ещё не доказывает работу всей системы.

## Объединение

Тег beta-1 ставь только после короткой проверки. B1 включает актуальный main в общую ветку функции. Вместе решаете конфликты, QA проверяет совместную версию; затем ты объединяешь итоговый PR с сохранением истории веток.

Один конкретный merge (объединение) выполняет один оператор. Порядок и команды — в [TEAM_WORKFLOW](../../TEAM_WORKFLOW.md).
