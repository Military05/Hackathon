# B1 — full-stack разработчик локального агента

Military05 предварительно B1 и координатор feature/beta1-f1. Ты используешь Codex для конкретных задач своей ветки; команда пишет код самостоятельно.

## Твой результат

Локальная готовая языковая модель исследует выбранное происшествие через разрешённые tools и возвращает объяснение с evidence. Это настройка агента под предприятие, а не обучение новой LLM с нуля.

Читать: [архитектуру](../ARCHITECTURE.md), [контракты](../CONTRACTS.md), [запуск](../RUNBOOK.md), [Codex](../../CODEX_USAGE.md).

## До beta-1: не ждать скелета

1. Проверь Ollama на своей машине и кандидат qwen3:4b, сначала простой ответ, затем реальный tool call.
2. Проверь чтение инструкции установки и размер скачивания. На текущей машине C имеет мало места; веса размещай на E, инструкции в RUNBOOK.
3. Запиши модель, оборудование, время ответа и результат tools в TEAM. Если не проверено — так и напиши.
4. С A1 согласуй tools и JSON ответа, с A2 — панель анализа.
5. Подготовь тестовые tool results и вопросы; реальные пути чтения подключишь после API.
6. Помоги скелету, если он блокируется.

Если tool calling не работает на выбранной модели, сначала меняй настройки/подходящую доступную модель и проверяй. Ограниченный анализатор с готовой сводкой — честный резерв, но не обозначай его как полноценного агента.

## Твои файлы

src/agent/, tests/agent/, конфигурация локальной модели и собственный UI-модуль agent panel по соглашению с A2. Не редактируй одновременно его общий map entrypoint. Schema БД/routes подключаются через A1.

## Что реализовать

- OllamaClient: локальный POST /api/chat, timeout, модель из config.
- Tools: get_incident, get_event_history, get_asset_policy, get_sensor_health.
- Registry с конкретными разрешёнными функциями и проверкой параметров.
- Orchestrator: model → tool_calls → результат → model, bounded loop.
- AgentJob service: queued/running/completed/failed, один активный job.
- Проверка ответа: все event_id существуют и были получены tools.
- Сохранение snapshot, tool trace, model id, длительности.
- Панель для A2: facts/hypotheses/recommendations/evidence.

Модель не выбирает произвольный SQL и не запускает команды компьютера. Tools read-only; изменение status происшествия остаётся обычным действием диспетчера.

## Бюджет обработки

Один job, максимум 3 model requests и 6 tool calls суммарно; цель total deadline 60 секунд на demo-машине. Таймаут и ограничение длины ответа задаёт код. После превышения failed с понятной причиной, без вечного while.

Каждый tool возвращает небольшой ограниченный JSON. Не отправляй модели всю БД или каждый sensor event.

Если facts/evidence не проходят проверку, покажи failed с фактическими данными, не придумывай исправление ответа.

## После beta-1: ветки

Координатор создаёт общую ветку только после тега, один раз:

~~~powershell
git fetch origin --tags
git switch -c feature/beta1-f1 beta-1
git push -u origin feature/beta1-f1
git switch -c feature/f1-agent
~~~

Далее commit/push своей feature/f1-agent → PR **base=feature/beta1-f1**. Не отправляй свою личную реализацию напрямую в main.

B2 создаёт свою ветку от общей. Его данные/ML не зависят от наличия LLM. Согласуйте интерфейс model observations.

## Самопроверка

- Модель действительно выбрала tool, приложение выполнило его и сохранило trace.
- Допуск сотрудника читается из базы, не угадывается.
- Для unknown id инструмент возвращает not_found, агент не выдумывает объект.
- Без evidence нет утверждения «нарушение доказано».
- Текст исходного события не может менять разрешения инструмента.
- Ollama выключена — мониторинг продолжает работать, job корректно завершён ошибкой.
- Новый evidence snapshot не получает устаревший cached analysis.

Покажи QA живые вопросы и валидный/невалидный ответ модели. Обучение собственной MLP — задача B2; агент не должен считать score доказанным нарушением.

## Интеграция

Просматриваешь PR B2 в общую ветку, затем включаешь актуальный main в неё. Для common bug используете общий fix-процесс из PROCESS_IMPROVEMENTS. Перед финальной проверкой фиксируете head, прекращаете его менять. QA проверяет, интегратор main объединяет итоговый PR.

## Где использовать Codex

Лучшие задачи: реализация одного tool, исправление bounded loop, проверка evidence validator, адаптация panel к свежему API, ревью конкретного diff. Передай Issue, ветку, контракт, пример вход/выход и проверку. Git и простые собственные функции не требуют ожидания помощника.

## Готово, когда

Живой локальный агент прошёл набор QA, evidence доступны, trace показывает реальные вызовы, ошибки ограничены, инструкция запуска повторяется. Запуск и качество пока не подтверждены одной лишь документацией Ollama.
