## Обязательные уточнения после аудита — Гаджи

[PREBUILD_FIXES](../PREBUILD_FIXES.md) дополняет v2 по поручению владельца. T36/T37/T39. До обучения большой модели проверь скачанный runtime/API и настоящий tool call. Очередь: 1 running + 2 queued; перед приёмом оценка ожидания строго меньше 120 секунд, выполнение максимум 60. Tools читают один сохранённый as_of/evidence/policy snapshot; корректный event_id не оправдывает неверную фразу. Программные факты отдельно от объяснения. Для отсутствующего первого heartbeat подтверждение идёт через sensor-health snapshot, а не выдуманное событие. UI agent job polling уже подготовлен; работающего агента здесь ещё нет.

Полный критический разбор: [PROJECT_AUDIT](../PROJECT_AUDIT.md). Исключения сохраняются: нет аккаунтов/смен/сложных прав и прогноза столкновений.

## Обновлённая задача B1 — общий локальный агент для трёх рабочих мест

Ты Гаджи, B1, не основной backend A1. Задачи T08/T14–T16/T22/T24. [Согласованная цель](../DISPATCH_OPERATIONS.md), [локальный запуск](../RUNBOOK.md). Одно продолжающееся нарушение не равно одному происшествию на весь завод; одна running LLM job не ограничивает обнаружение тревог.

1. Открой Bionic → Settings → Local Models → Library, выбери уже скачанную Local-модель, запиши имя/вариант/размер. Навигация относится к LM Studio Bionic; установленную версию надо подтвердить. Не выбирай cloud для автономного показа.
2. Проверь доступный программный API. Bionic-чат сам по себе не API для FastAPI. Подтверждённый путь: LM Studio → Developer → Start server; адрес/порт/авторизацию смотри фактически. Проверь /v1/models, обычный ответ, затем настоящий tools call и исполнение тестовой Python-функции.
3. Если выбранная модель/runtime не дают tools или не укладываются во время, зафиксируй ошибку и проверь другой локальный совместимый вариант. Ollama резерв; не требуй его установки, пока Bionic/LM Studio вариант не проверен.
4. Сделай model_client, явный registry четырёх инструментов, schemas/валидацию, provider данных, loop/evidence. На fixtures можно работать без Егора С.; затем его query provider подключается без переписывания loop.
5. Общая очередь для всех профилей: 1 running, 2 queued, FIFO, 120 секунд ожидания, 60 выполнения, максимум 3 model requests/6 tools. Повтор snapshot возвращает существующий результат; автора запроса сохраняй отдельно от владельца происшествия.
6. Сохраняй snapshot, trace, модель/время, проверяй evidence/policy_version. Новые факты → stale. Claim/transfer не делают старый анализ новым и сами по себе не меняют data snapshot. Перезапуск: running failed interrupted, queued восстанавливаются с бюджетом ожидания.
7. С Егором М. подключи панель ответа; с Егором С. — маршруты/jobs/storage; с Гришей — D4 evidence. Анализ не управляет назначением, эскалацией, рацией или машинами.
8. Запиши в TEAM CPU/RAM/GPU/VRAM, модель, runtime/API, версии, время настоящего tool call. На ноутбук переносится проверенная конфигурация и веса; характеристики ноутбука ещё надо подтвердить.

Что согласовать сейчас: Егор С. — query/snapshot/хранение/подключение; Егор М. — отдельный компонент и статусы; Лия — неизвестные tools/id/evidence, очередь и LLM-off. Если query не готовы, продолжай на тестовом provider, блокируется только реальная интеграция. Передача/эскалация — задачи A1/A2, твоя очередь не должна задерживать их.

Прототип до beta-1: prototype/agent-runtime от актуального main. После beta-1 создаёшь общую ветку по инструкции ниже и переносишь проверенные коммиты в личную feature/f1-agent. Не объявляй UI-пример готовым агентом.

Full-stack означает, что ты работаешь и с логикой, и с интерфейсом своей функции. Гаджи (B1) — разработчик агента и координатор общей ветки `feature/beta1-f1`.

Твой результат: готовая локальная языковая модель читает данные через разрешённые инструменты и объясняет выбранное происшествие. Это настройка агента под предприятие; новую большую языковую модель с нуля не обучаем.

## Что написать

- Клиент локальной модели: проверенный /v1/chat/completions с tools либо резервный Ollama /api/chat; конфигурация по RUNBOOK.
- Tools (инструменты): функции чтения карточки, истории, допусков и состояния датчика.
- Registry (явный список разрешённых инструментов) и проверка параметров.
- Цикл агента: модель выбирает инструмент → код выполняет → результат возвращается модели → модель делает вывод.
- Очередь задач: ожидает, выполняется, готово или ошибка.
- Проверку evidence (ссылок на реальные исходные события).
- Сохранение снимка данных, версии модели и tool trace (журнала вызовов).
- Панель с фактами, предположениями и рекомендациями.

Точные имена функций и полей в CONTRACTS. Инструменты только читают. Модель не запускает произвольные команды или SQL и не управляет оборудованием.

## Ограничения

Одна выполняющаяся задача, максимум 3 обращения к модели и 6 вызовов инструментов, общий предел 60 секунд. Это выбранные ограничения, скорость ещё нужно измерить.

Каждый инструмент возвращает короткие данные. Не передавай всю базу и не вызывай модель на каждую точку транспорта. Превышен предел или неверные доказательства — понятная ошибка; мониторинг работает дальше.

Новые исходные события меняют snapshot (снимок данных); старый сохранённый анализ не выдаём за актуальный.

## После beta-1 создаёшь общую ветку

Только после короткой проверки и создания тега, один раз:

~~~powershell
git fetch origin --tags
git switch -c feature/beta1-f1 beta-1
git push -u origin feature/beta1-f1
git switch -c feature/f1-agent
~~~

Ты получил теги, создал общую ветку от beta-1, отправил её на GitHub и создал личную ветку агента. Гриша (B2) создаёт свою личную ветку от общей.

## Отправка кода

1. Проверь свой результат.
2. `git status` — посмотри изменения.
3. `git add путь-к-файлу` — добавь настоящие нужные файлы; `git diff --cached` — просмотри их.
4. Сохрани и отправь личную ветку:

~~~powershell
git commit -m "Добавить анализ происшествия агентом"
git push -u origin feature/f1-agent
~~~

5. Открой PR (запрос на объединение) с `base=feature/beta1-f1` и твоей веткой `feature/f1-agent`.
6. Дай другому разработчику и Лия (QA — тестировщик) (тестировщику) команду, вопрос агенту и ожидаемое поведение.

Твою незавершённую функцию не отправляй напрямую в main. [Подробные команды](../../TEAM_WORKFLOW.md).

## Самопроверка

- Модель действительно выбрала инструмент; код выполнил его.
- Разрешения читаются из базы, не угадываются.
- Неизвестный объект даёт контролируемую ошибку.
- Ссылки на события существуют и получены инструментами.
- Предположения подписаны отдельно.
- Неверный текст/инструмент не расширяет разрешения.
- Выключенный локальный модельный сервер не останавливает карту.
- Старый анализ не подставляется к новым данным.

Покажи тестировщику живой запрос, журнал инструментов и неправильный ответ модели. Передай SHA (номер конкретной версии: `git rev-parse HEAD`).

## Объединение и Codex

Просматривай изменения Гриша (B2) в общей ветке. Затем включи актуальный main в неё по общей инструкции; вместе решите конфликты. Зафиксируйте версию для Лии (QA — тестировщик), после проверки интегратор объединит итоговый запрос в main.

Codex полезен для одной конкретной задачи: написать инструмент, исправить цикл, проверить доказательства или подключить панель. Дай ветку, разрешённые файлы, контракт и проверку. Код и простые действия Git можешь делать сам; команда не ждёт твоих токенов.

Готовность — живой запрос, настоящие инструменты, корректные ссылки, ограниченные ошибки и повторяемый запуск другим участником.
