# A2 — фронтенд: интерфейс и карта предприятия

Ты делаешь то, что видит диспетчер: карту, транспорт, список происшествий, карточки и кнопки. Серверную часть делает A1. Если встретишь незнакомое слово, загляни в [словарь](../GLOSSARY.md).

## С чего начать

1. Прочитай [общий план](../TASK_03_PLAN.md) и [форматы данных](../CONTRACTS.md).
2. Договорись с A1, какие данные сервер возвращает для карты, транспорта и происшествий. Это API — способ общения интерфейса с сервером.
3. Создай страницу в `src/interface/web/`.
4. Возьми здания и зоны из общего `site.json`: не придумывай для карты другую геометрию.
5. Нарисуй SVG (векторную схему территории) с координатами от 0 до 100, `viewBox="0 0 100 100"`.
6. Подключи `GET /api/site` и `GET /api/assets`. GET означает получение данных; пути — адреса операций сервера.
7. Проверь, что событие от симулятора действительно перемещает машину на карте.

Пока сервер не готов, можно временно показывать согласованный пример данных. Это mock (имитация ответа). Явно подпиши его как временный; перед первой рабочей версией подключи настоящий сервер.

## За какие файлы ты отвечаешь

Твоя область — `src/interface/web/` и проверки интерфейса. Главный файл карты меняешь ты. B1 (разработчик агента) и B2 (разработчик нейросети) согласуют с тобой подключение своих панелей.

`site.json` принадлежит A1. Если хочешь передвинуть здание или зону, сначала договорись: рисунок и серверные правила должны совпадать.

## Что должно работать в beta-1 — первой рабочей версии

- Здания W1/W2 (склады), P1/P2 (цеха), O1 (офис), G1 (КПП), дороги и зоны Z1/Z2.
- Машины V1–V3: последняя позиция и время её получения.
- Список происшествий: тип, объект или здание, время, важность, состояние.
- Карточка происшествия с evidence (исходными событиями, подтверждающими вывод).
- Состояние датчиков: связь есть, связь потеряна или ещё неизвестна.
- Кнопки «Увидел происшествие» и «Закрыть». Серверные значения: `acknowledged` и `closed`.
- Понятные состояния: данные загружаются, данных пока нет, произошла ошибка.
- Обновление данных раз в секунду без накопления одновременно выполняющихся запросов.

Нет данных — покажи это. Старая позиция не должна выглядеть свежей. Внешние описания выводи как текст, не исполняй их как HTML.

## Что делать после первой версии

Пока full-stack пара добавляет ИИ-функции, ты улучшаешь основу: фильтры, карточки зданий, сообщения об ошибке и восстановление обновления данных. Это beta-2 — следующая версия основы.

B2 добавит оценку нейросети. Покажи её версию, `score` (числовую оценку), `threshold` (порог срабатывания) и состояние. Число 0.8 не означает «80% вероятности аварии».

B1 добавит агента. Кнопка «Проанализировать» создаёт задачу; показывай очередь, выполнение, готовый ответ или ошибку. Ответ HTTP 202 означает «задача принята», а не «анализ готов». Проверяй состояние существующей задачи, не создавай новую каждую секунду.

Ответ агента раздели на факты, предположения и рекомендации. Дай открыть исходные события и tool trace (журнал вызовов инструментов). Если агент выключен, карта продолжает работать.

## Как начать свою ветку

Ветка — отдельная линия работы, чтобы твои незаконченные изменения не мешали остальным.

~~~powershell
git switch main
git pull --ff-only origin main
git switch -c core/interface-skeleton
~~~

Первая команда переходит в `main` (общую ветку). Вторая получает её свежую версию с GitHub. Третья создаёт твою ветку для интерфейса.

## Как отправить результат

1. Запусти приложение и проверь свою задачу.
2. Посмотри изменённые файлы: `git status`.
3. Добавь нужные файлы: `git add путь-к-файлу`. Подставь настоящий путь; повтори для остальных нужных файлов.
4. Посмотри подготовленные изменения: `git diff --cached`.
5. Сохрани их в истории:

~~~powershell
git commit -m "Добавить карту предприятия"
git push -u origin core/interface-skeleton
~~~

`commit` — сохранение в истории Git. `push` — отправка на GitHub. `origin` — имя подключения к вашему репозиторию.

6. На GitHub открой Pull Request, сокращённо PR (запрос на объединение). Выбери `base=main` — ветку назначения, `compare=core/interface-skeleton` — твою ветку.
7. Напиши, что изменилось, как запустить и что проверить. Попроси другого разработчика посмотреть изменения и передай тестировщику сценарий.
8. После проверки назначенный интегратор объединит запрос.

Следующую задачу начинай новой веткой от свежего `main`, например `core/beta2-interface`. Перед отправкой согласуй с интегратором обновление своей ветки. [Подробные команды](../../TEAM_WORKFLOW.md).

## Самопроверка и передача тестировщику

- Карта совпадает с координатами серверной части.
- Настоящее событие перемещает машину.
- D1 (запрещённая зона), D2 (проход без допуска), D3 (потеря связи) видны в журнале и карточках.
- Нормальная работа не вызывает ложных тревог.
- Повторный клик не отправляет два подтверждения одного происшествия.
- При ошибке связи видна ошибка и время последних данных.
- Перезагрузка страницы не создаёт новые происшествия.
- Время хранится в UTC (мировом времени), а отображение согласовано с командой.

Передай QA (тестировщику): ссылку на запрос, сценарий кликов, ожидаемый результат и SHA (идентификатор версии). Узнать SHA: `git rev-parse HEAD`.
