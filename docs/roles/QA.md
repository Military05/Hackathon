# Q — тестировщик команды

Твоя задача — показать команде, какая версия работает, что уже проверено и какие ошибки мешают сдаче. Не нужно исправлять весь код за разработчиков: нужны понятное воспроизведение и повторная проверка исправления.

Читай [план](../TASK_03_PLAN.md), [форматы](../CONTRACTS.md), [таблицу проверок](../TESTING.md), [запуск](../RUNBOOK.md). Незнакомые слова есть в [словаре](../GLOSSARY.md).

## До первой версии

1. Уточни обязательные требования и допустимость симулятора.
2. Подготовь сценарии и ожидаемые результаты.
3. Проверь обычную работу без нарушений.
4. По готовности небольших PR (запросов на объединение кода) проверяй весь нужный путь.
5. Перед beta-1 проведи smoke (короткую проверку запуска и одного полного основного сценария). Все D1–D3 должны быть доступны для последующей полной проверки.

Агент и нейросеть входят в дополнительную функцию. Не жди их готовности, чтобы начать проверять основу.

## Сразу после beta-1

Обе пары продолжают разработку, а ты полностью проверяешь зафиксированную beta-1. Тег — имя конкретной сохранённой версии; его не передвигаем после найденного бага.

~~~powershell
git clone https://github.com/Military05/Hackathon.git Hackathon-QA
cd Hackathon-QA
git fetch origin --tags
git switch --detach beta-1
git rev-parse HEAD
~~~

Команды создают отдельную копию, получают теги, открывают beta-1 и показывают SHA (идентификатор версии кода). До создания тега переход не сработает.

`--detach` означает просмотр зафиксированной версии без рабочей ветки. Не делай в таком состоянии коммиты; для тестового кода создай именованную ветку по правилам ниже.

## Что проверять

| Сценарий | Ожидаемый результат |
| --- | --- |
| Обычное движение и разрешённый проход | Нет ложных тревог |
| D1: машина вошла в запрещённую зону | Одно происшествие с зоной, машиной и исходным событием |
| D2: сотрудник прошёл без допуска | Происшествие со ссылкой на событие и разрешения |
| D3: датчик перестал посылать heartbeat — сообщение «я работаю» | После порога один случай потери связи; при возврате восстановление |
| До первого heartbeat | Состояние неизвестно, ложного offline нет |
| Некорректный формат или идентификатор | Согласованная ошибка, факты не изменились |
| Повтор одного события | Нет дубля и повторного происшествия |
| Старое событие позиции | Сохранено в истории, текущая позиция не откатилась |
| Точка на границе зоны | Считается внутри |
| Перезапуск сервера | История сохранена, лишнего таймера нет |
| Языковая модель выключена | Карта и правила работают, агент явно недоступен |
| Нейросеть не обучена | Честное «модель не готова», а не «всё нормально» |

Полная таблица Q01–Q32 — в TESTING.

## Проверка собственной нейросети

B2 передаёт сохранённую модель, версии, данные и отчёт. Проверь:
- Модель действительно обучили, а не только нарисовали оценку.
- Обучающие и тестовые эпизоды не пересекаются.
- Готовый правильный ответ не попал среди признаков модели.
- Признаки одинаково вычисляются при обучении и в приложении.
- Сравнение с baseline (простым алгоритмом) сделано на тех же данных.
- Ложные тревоги записаны, результат на синтетике честно подписан.
- Недостаток данных не превращается в ложное «нормально».

D4 — необычное движение. Проверь его на отдельном эпизоде. Score (оценка модели) не равен доказанной вероятности аварии.

## Проверка локального агента

B1 показывает живой запрос. Проверь:
- Tool trace (журнал действий) содержит настоящие вызовы инструментов.
- Evidence (исходные события) существуют в базе и были получены инструментами.
- Факты отделены от предположений.
- Неизвестный объект не превращается в выдуманный.
- Неправильные инструменты и параметры отклоняются.
- Ограничение времени завершает задачу ошибкой без вечного ожидания.
- Текст события не может разрешить модели произвольные команды.
- Новые данные не получают устаревший сохранённый ответ.

Записанный заранее ответ — резерв показа, не доказательство живой работы агента.

## Баги и очередь

P0 — запуск/данные/основной показ сломаны. P1 — неверное обязательное поведение или доказательства. P2 — второстепенное неудобство. P3 — оформление.

Сначала блокирующие ошибки, затем совместная версия и обязательные функции, потом косметика. Полную проверку beta-1 начинай сразу, но найденный P0 имеет приоритет.

Создай Issue (сообщение об ошибке) через шаблон GitHub. Укажи ветку, SHA, запуск, шаги, ожидаемый и фактический результат, данные/seed и затронутые линии main/F1.

После исправления проверь новый SHA и добавь новую запись. Старое PASS (проверено успешно) не относится автоматически к новому коду. Остальные состояния: FAIL — ошибка, BLOCKED — проверка заблокирована, NOT RUN — ещё не запускалась.

## Если добавляешь тесты в репозиторий

- Для основы: `qa/core-scenarios` от main, PR в main.
- Для дополнительной функции: `qa/f1-evidence` от `feature/beta1-f1`, PR в эту общую ветку.

Не меняй ветку автора без договорённости. [Команды Git](../../TEAM_WORKFLOW.md).

## Финал

После включения main в ветку функции фиксируете совместный SHA и временно прекращаете менять его. Проверяешь D1–D4, агента, восстановление и запуск. После объединения ещё раз проверяешь main.

Повтори RUNBOOK с чистой копии проекта без устных подсказок автора. Итоговый тег ставится на проверенный код. Журнал в TESTING сейчас пустой: результаты заполняются после фактических проверок.
