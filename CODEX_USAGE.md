# Люди пишут код: как использовать чат и Codex на хакатоне

Дополнение к [TEAM_WORKFLOW.md](TEAM_WORKFLOW.md) и [PROCESS_IMPROVEMENTS.md](PROCESS_IMPROVEMENTS.md).

**Команда состоит из программистов. Каждый умеет писать код, проектировать структуру, работать с Git и отвечать за результат. Чат и Codex помогают там, где это полезно. Работа не зависит от наличия токенов у одного участника.**

Ты — один из двух full-stack разработчиков. Используешь Codex для своего участка работы и согласованной помощи команде. Остальные продолжают писать код в собственных редакторах и могут обсуждать решения в чате.

Тема, язык и формат неизвестны до задания. Помощнику передаём реальные требования; заранее не заказываем админ-панель, веб-сервер или консольную оболочку.

## 1. Два способа помощи

### Обсуждение в чате

Чат подходит, когда нужен ответ: сравнить идеи, уточнить алгоритм, проверить контракт, объяснить ошибку, составить сценарии. После ответа человек сам меняет код и запускает проверки.

Полезный запрос: «Вот функция и вход, на котором она ошибается. Объясни причину и предложи минимальное изменение». Ответ чата не означает, что файл в репозитории действительно изменён или тесты выполнены.

### Работа Codex с репозиторием

Когда у Codex есть доступ к выбранному клону, он может исследовать код, внести изменения, запускать доступные проверки и подготовить diff/PR в рамках поставленной задачи. Доступ, окружение и допустимые действия зависят от конкретной настройки.

Полезный запрос: «Исправь ошибку в моей ветке, сохрани контракт и покажи выполненные проверки». Человек просматривает diff и понимает изменение; другой участник проводит ревью, QA проверяет поведение.

Не предполагаем, что чат видит незапушенные файлы на чужом компьютере. Передаём конкретный код/ошибку либо открываем Codex в нужном клоне. Ссылка на GitHub указывает опубликованную версию; локальная рабочая папка может быть новее.

## 2. Кто что делает

| Работа | Основной исполнитель | Где полезен чат/Codex |
| --- | --- | --- |
| Разобрать условие, выбрать обязательный сценарий | Все пять, решение руководителя | Обнаружить неоднозначности, сравнить 2–3 простых варианта |
| Выбрать структуру и стек | Разработчики, по своим навыкам | Короткое обсуждение рисков выбранного решения |
| Написать скелет ядра | Разработчик бэкэнда/ядра | Разбор конкретной ошибки либо ревью контракта |
| Написать скелет интерфейса | Разработчик фронтэнда/интерфейса | Проверка ввода/вывода, сценариев пользователя |
| Делать beta-2 | Пара основы | Точечная помощь по багам, без ожидания токенов |
| Делать F1 | Два full-stack | Ты используешь Codex для своего модуля/адаптации; напарник пишет свой участок |
| Тестировать beta-1 и совместную версию | QA, плюс самопроверка авторов | Подсказать крайние случаи, помочь с тестовыми данными |
| Разрешить конфликт и адаптировать версии | Владельцы затронутых файлов | Codex анализирует конкретный конфликт и связанные вызовы |
| Слить PR и выпустить финал | Выбранный оператор с командой | Проверка diff и инструкции, действия по явному поручению |
| Защита | Люди, которые понимают решение | Сократить описание, проверить воспроизводимость запуска |

Не передаём помощнику ответственность «сделай за всех весь проект» при работающей команде. Содержательная задача и ясная граница файлов помогают избежать повторения чужой работы.

## 3. Что выгоднее делать тебе вместе с Codex

### Приоритет 1: сложная воспроизводимая ошибка

Передай шаги, вход, ожидаемый результат, текст ошибки, ветку и SHA. Попроси найти причину и исправить минимально. Это особенно полезно, когда проблема проходит через несколько модулей и руками уже проверили очевидное.

### Приоритет 2: адаптация F1 к обновлённой основе

Дай версию контракта, изменения main и файлы своей функции. Попроси сохранить сценарии обеих версий. Codex помогает найти несовместимые вызовы и форматы, которые текстовый merge не обнаруживает.

### Приоритет 3: твой законченный модуль

Дай задачу и критерии приёмки. Попроси реализовать ограниченный участок, который не занят другим участником, и проверить его. Ты разбираешь diff, уточняешь решение и отправляешь обычный PR.

### Приоритет 4: осмысленные проверки

Попроси тест на найденный баг, важную границу алгоритма или контракт. Для консоли — отрицательный ввод, коды возврата, повтор операций; для других форматов — соответствующие сценарии. Не генерируем десятки тестов, которые только повторяют реализацию.

### Приоритет 5: короткое ревью перед интеграцией

Попроси найти ошибки поведения, несовместимость контрактов и потерю данных в конкретном diff. Результат — список реальных рисков с путями и примерами, затем ты решаешь, что исправлять.

### Приоритет 6: инструкция выпуска

Когда код уже готов, Codex помогает сверить README с реальными командами и собрать сценарий защиты. Успешный текст не заменяет запуск на другом компьютере.

## 4. Что участники делают самостоятельно

Разработчики основы самостоятельно строят скелет, выбирают привычные инструменты, пишут код и проводят самопроверку. Full-stack напарник самостоятельно реализует свой сценарий. QA самостоятельно подтверждает фактическое поведение.

Каждый участник:

1. Берёт Issue и объявляет изменяемые файлы.
2. Создаёт личную ветку от своей базы.
3. Реализует задачу и запускает необходимые проверки.
4. Пишет осмысленное описание PR.
5. Помогает reviewer понять код и исправляет найденное.
6. После слияния обновляет базу.
7. Может объяснить свою часть на защите.

Для знакомой простой функции проще сразу написать код, чем долго формулировать запрос. Git status, commit, push, просмотр diff и обычную настройку редактора команда выполняет без ожидания Codex. При непонятной ошибке из Git обращается к разделу 10 основного руководства.

Чат можно использовать по желанию. Ни подписка, ни доступ к твоему аккаунту не являются условием участия. Не передавай участникам пароль аккаунта или персональный API-ключ; задачи они передают тебе через Issues/PR и код.

## 5. Работа человека и агента без пересечения файлов

Перед началом:

~~~powershell
git status
git branch --show-current
git rev-parse HEAD
~~~

Убедись, что открыта твоя личная ветка и понятны незакоммиченные изменения. Если над файлом уже работает напарник, выбери другую задачу или договорись, кто его меняет.

Для небольшого участка достаточно одного клона: во время изменения Codex не редактируй те же файлы вручную. Если отредактировал/откатил их сам, сообщи это в чат Codex. Перед следующей задачей проверяй состояние.

Для параллельной работы человека и Codex можно использовать отдельный клон или Git worktree с отдельной веткой. Это техническая изоляция файлов, а не обязательная новая командная ветка или дополнительный участник. Ветки потом проходят обычный PR. Не нужно заводить несколько агентов ради одного небольшого исправления.

После изменений:

~~~powershell
git diff
git status
~~~

Проверь, что изменено именно задание, что нет чужих файлов и нежелательных зависимостей. Выполни фактические команды из docs/TEAM.md. Попроси итог: изменённые файлы, поведение, реально выполненные проверки и оставшиеся ограничения.

Codex может подготовить commit/PR по твоему поручению, но не должен считать фразу «посмотри проблему» разрешением на автоматический финальный merge. Для анализа прямо указывай «только анализ». Для реализации — «внеси изменения в моей ветке». Для публикации PR — «отправь ветку и открой PR».

## 6. Универсальный запрос: короткий и достаточный

~~~text
Задача: [один конкретный результат].
Контекст: Issue #..., ветка ..., базовая ветка ..., текущий SHA ...
Вход/ожидаемое поведение: ...
Ошибка/фактическое поведение: ...
Файлы/модуль: ...
Контракт: версия ..., ссылка/путь ...
Ограничения: сохранить ..., не менять чужой модуль ...
Проверка готовности: [команда и ручной сценарий].
Действие: [только анализ / внеси правки / отправь ветку и открой PR].
Итог: краткий diff, выполненные проверки, что осталось непроверенным.
~~~

Все поля не обязательны для каждого вопроса. Для простой ошибки хватит воспроизведения, ожидаемого результата и нужного файла. Для интеграции контекст двух веток обязателен.

Если у агента доступ к репозиторию, укажи путь/ветку и релевантную задачу; не копируй весь проект в сообщение. Если доступа нет, приложи нужный фрагмент и caller. Не проси пересказывать всю архитектуру перед каждой правкой.

## 7. Готовые запросы под этапы хакатона

### Обсуждение задания, без кода

~~~text
Мы команда из пяти: QA, разработчик ядра, разработчик интерфейса,
два full-stack. Два дня. Вот условие: ...
Предложи 2–3 минимальных решения и сравни риски.
Укажи один обязательный сценарий и что отложить.
Не выбирай тему вместо условия и пока не меняй репозиторий.
~~~

### Доработка твоей функции

~~~text
Я full-stack №1. Issue #..., моя ветка feature/f1-logic.
Контракт описан в docs/CONTRACTS.md. Реализуй сценарий ...
Критерии: ...
Напарник сейчас меняет ..., не пересекайся с этим участком.
Сохрани существующие публичные вызовы.
Проверь [конкретное поведение]. Покажи diff и результат проверки.
~~~

Имя `feature/f1-logic` — пример; если делаешь целый сценарий, выбери соответствующее имя личной ветки.

### Воспроизводимый баг

~~~text
На SHA ... в ветке ... сценарий ... выдаёт ...
Ожидалось ... Вход: ... Команда: ... Лог: ...
Найди причину, исправь минимально в моей fix-ветке,
добавь проверку, которая ловит этот баг.
Запусти доступные проверки и укажи непроверенное.
~~~

### Анализ двух веток перед интеграцией

~~~text
Только анализ. Есть main с beta-2 и feature/beta1-f1 с функцией на beta-1.
Сравни изменения, особенно контракт и entrypoint.
Укажи несовместимость поведения и порядок интеграции.
Не выполняй merge/push. Дай конкретные пути и примеры.
~~~

### Работа над конфликтом

~~~text
В моей sync-ветке начат merge актуального main в F1.
Конфликтуют файлы ...; ожидаемый итог: сценарий основы ... плюс F1 ...
Разреши конфликт, сохрани обе возможности и текущий контракт.
Проверь связанные вызовы и [тест/ручной сценарий].
Не объединяй финальный PR самостоятельно.
~~~

### Ревью без правок

~~~text
Проведи ревью diff PR #... / моей ветки.
Нужны ошибки поведения, несовместимость контракта,
потеря данных и пропущенные важные случаи.
Для каждого замечания дай файл, пример и последствия.
Не меняй файлы и не обсуждай стиль без влияния на поведение.
~~~

### Инструкция выпуска

~~~text
Сверь docs/RELEASE.md и README с фактическим состоянием проекта.
Укажи отсутствующие шаги установки/запуска и неверные команды.
Составь короткий сценарий защиты обязательного сценария + F1.
Не утверждай, что запуск проверен, если ты его не запускал.
~~~

## 8. Как распределить ограниченный ресурс Codex

Под «токенами» в разговоре можно иметь в виду доступный ресурс помощника. Подписочные лимиты, токены API и кредиты — разные механизмы; не задаём в этом документе выдуманное число запросов. Актуальный остаток смотрим в доступном интерфейсе usage своего аккаунта. Потребление зависит от модели и задачи. [Официальная справка о лимитах](https://learn.chatgpt.com/docs/pricing).

Для этих двух дней выбери порядок:

1. Блокирующая ошибка.
2. Интеграция и совместимость.
3. Твой сложный модуль.
4. Проверка важного поведения.
5. Документация.
6. Косметические улучшения при оставшемся времени.

Оставь запас на последний день и финальную интеграцию. Не расходуй всё на красивую структуру до получения темы. Команда умеет построить её сама.

Экономия без ухудшения результата:

- Одна ясная задача за запрос; точные ожидания и пример входа.
- Релевантный код/путь/лог вместо большого архива в чате.
- На известную ошибку — короткий воспроизводимый пример.
- После исправления — разумные целевые проверки, перед выпуском — проверка обязательных сценариев.
- Не заказывай повторный общий обзор проекта после каждого commit.
- Проси краткий итог и ссылки на изменённые места.
- Если начался отдельный вопрос, передай компактный актуальный контекст; не считай, что любой новый чат знает все прошлые решения.
- Решения фиксируй в репозитории, чтобы не объяснять их каждый раз.
- Не используй автономные долгие задачи или несколько агентов для маленькой правки.

Это практические рекомендации команды, а не обещание точной экономии или отдельного бесплатного лимита для чата.

## 9. Если ресурс закончился или помощник недоступен

Разработка продолжается по тому же процессу. Ты пишешь код сам, напарник делает свой участок, QA проверяет, оператор выполняет интеграцию.

Чтобы никто не зависел от переписки с помощником, каждый завершённый шаг оставляет:

- Опубликованную личную ветку и PR.
- Контракт и решение в docs.
- Понятные команды проверки.
- Запись результата/ограничения.
- Короткое описание «что осталось».

Важный алгоритм не должен существовать только в ответе чата или незакоммиченном файле на твоём ноутбуке.
