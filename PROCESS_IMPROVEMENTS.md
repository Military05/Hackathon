# Улучшенная система: две пары разработки + непрерывное тестирование

**Кто участвует:** пара A — Егор С. (бэкенд) и Егор М. (фронтенд); пара B — Гаджи (агент) и Гриша (симулятор и нейросеть); тестировщик — Лия. Подробности и роли: [команда](docs/TEAM.md).

Если слово незнакомо, открой [словарь простыми словами](docs/GLOSSARY.md). Команды и названия полей не переводим: в коде они должны остаться точными.

Для команды из пяти человек на 7–8 октября 2026. Основные команды Git и инструкция входа в проект: [TEAM_WORKFLOW.md](TEAM_WORKFLOW.md).

Для выбранного задания №3: Егор С. (A1) — API/БД/правила, Егор М. (A2) — карта/карточки; Гаджи (B1) — локальный агент, Гриша (B2) — симулятор/MLP; Лия (Q) — ранняя проверка. F1 состоит из интеллектуального анализа, не новой копии всей системы. [Роли](docs/TEAM.md), [backlog](docs/BACKLOG.md), [контракты](docs/CONTRACTS.md).

## 1. Ваша идея и её рабочая реализация

Состав команды:

- Один тестировщик.
- Два разработчика основы: бэкэнд/ядро и фронтэнд/интерфейс.
- Два full-stack (разработчик и серверной части, и интерфейса) разработчика дополнительных функций.
- Объединение — общая ответственность четырёх разработчиков при участии Лия (QA — тестировщик). Каждый конкретный merge (объединение веток) выполняет один назначенный человек.

Сохраняем вашу идею: готова бета №1 → сразу ответвляется вторая пара → первая пара делает бету №2 → обе работы соединяются. Добавляем **третий параллельный поток Лия (QA — тестировщик)**, который сразу после готовности скелета проверяет основные функции беты №1. Полная проверка не задерживает начало следующей разработки.

Но перед объявлением беты №1 нужна короткая проверка: программа запускается, один реальный обязательный сценарий проходит, контракт записан. Это smoke-проверка, а не полная регрессия. Если её не проходит, скелет ещё не готов; пары вместе устраняют блокировку.

~~~text
                         Короткая проверка скелета
                                   |
                          beta-1: фиксированный SHA
                   +---------------+---------------+
                   |               |               |
                Пара A          Пара B             QA
            улучшает основу   добавляет F1     проверяет beta-1
            через PR в main   на beta-1        и сообщает баги
                   |               |               |
                   +-------- общие исправления -----+
                   |               |
                 beta-2 -- main → ветка F1
                                   |
                         совместная версия на SHA
                                   |
                         интеграционная проверка QA
                                   |
                          PR F1 → main → beta-3
~~~

Лия (QA — тестировщик) тестирует снимок, а разработчики меняют следующие версии. Поэтому каждый отчёт обязательно указывает **ветку и SHA (идентификатор конкретной версии кода)**. Фраза «я проверил бету» без SHA не позволяет понять, что именно проверено.

## 2. Три потока с самого начала

| Этап | Пара A: основа | Пара B: два full-stack | Лия (QA — тестировщик) |
| --- | --- | --- | --- |
| Первые 30–60 минут | Контракт и точка входа | Примеры, сценарии F1, тестовые данные, заглушки | Сценарии приёмки, подготовка окружения |
| До скелета | Один сценарий от ввода до результата | Независимые задачи по готовому контракту | Проверка небольших PR (запрос на объединение изменений) и запуска |
| Готов beta-1 | Сразу начинает улучшения beta-2 | Сразу создаёт feature/beta1-f1 от beta-1 | Сразу начинает полную проверку основных функций beta-1 |
| Параллельная работа | Маленькие PR; сохраняет совместимость | Маленькие PR в общую ветку функции | Приоритетные баги, перепроверка исправлений |
| Перед интеграцией | Фиксирует проверенную основу | Включает актуальный main, разрешает несовместимости | Проверяет совместный SHA |
| После интеграции | Следующий небольшой шаг либо подготовка сдачи | Новая функция от свежего main либо баги | Регрессия main и подготовка защиты |

Тестировщик не ждёт завершения F1, а full-stack пара не ждёт полной регрессии beta-1. Плохое поведение, найденное Лия (QA — тестировщик), становится конкретной задачей с приоритетом и ответственным.

## 3. Как не превратить одного Лия (QA — тестировщик) в узкое место

Разработчики сами проверяют свой код до передачи. Лия (QA — тестировщик) отвечает за независимую приёмку, ошибки на границах и совместимость. Одна задача не должна превращаться в очередь из нескольких часов непроверяемого кода.

### Что автор обязан передать Лия (QA — тестировщик)

- Ссылка на Issue (задача или сообщение об ошибке) и PR.
- Ветка и точный head (ветка или версия с предлагаемыми изменениями) SHA.
- Команда запуска и подготовка данных.
- Один нормальный и один отрицательный сценарий.
- Ожидаемый результат.
- Что изменилось относительно уже проверенной версии.

Если этих данных нет, автор дополняет описание; Лия (QA — тестировщик) берёт следующую готовую задачу. Понятный PR экономит больше времени, чем сообщение «проверь всё».

### Очередь Лия (QA — тестировщик), по порядку важности

1. P0: запуск, потеря данных, обязательный сценарий.
2. Исправления критических багов и совместная версия перед merge.
3. Обязательная новая функция.
4. Основные функции beta-1 и регрессия изменённых частей.
5. Второстепенные сценарии и внешний вид.

Исходная beta-1 получает обязательную проверку основных функций сразу. Если в это время возникает P0, проверку приостанавливаем ради блокирующей ошибки, после устранения возвращаемся к оставшимся сценариям.

Полный повтор всех сценариев нужен перед финалом и после крупных изменений. Для маленькой правки проверяем затронутое поведение и короткий основной сценарий. Не повторяем всю программу после изменения одной строки документации.

### Статусы проверки

`READY FOR QA → TESTING → PASSED / FAILED`. Вместе со статусом записываем SHA. Новый push (отправка изменений на GitHub), который меняет проверяемый код, требует проверки изменений; старый PASSED не относится автоматически к новому head.

Журнал находится в [docs/TESTING.md](docs/TESTING.md). Он показывает, какой снимок и каким способом проверен. Отдельные обязательные функции отмечаем поштучно, чтобы видеть остаток работы.

## 4. Лия (QA — тестировщик) проверяет beta-1, пока обе пары работают

Лия (QA — тестировщик) может клонировать отдельную папку для проверки снимка:

~~~powershell
git clone https://github.com/Military05/Hackathon.git Hackathon-QA
cd Hackathon-QA
git fetch origin --tags
git switch --detach beta-1
git rev-parse HEAD
~~~

Тег beta-1 появляется только после готовности скелета. Если его ещё нет, сначала нужна контрольная точка из основного руководства.

Detached HEAD здесь специально удерживает одну версию, пока main и функция меняются. Лия (QA — тестировщик) в этой папке не коммитит. Тесты и правки делает в другом клоне либо после возвращения на именованную личную ветку.

Лия (QA — тестировщик) проходит основной сценарий, все основные пункты меню/операции, ошибочный ввод, повтор операции, выход и перезапуск/хранение, если это часть требований. Нормальные и ошибочные наборы сохраняем в fixtures (подготовленные тестовые данные); личные данные и секреты не используем.

После исправления Лия (QA — тестировщик) проверяет **новый SHA ветки с исправлением**. Старый тег beta-1 остаётся неизменным. В журнале старая строка с багом сохраняется, добавляется новая с результатом перепроверки.

## 5. Как чинить общий баг сразу в обеих линиях

Пример: Лия (QA — тестировщик) на beta-1 обнаружил, что пустой ввод ломает приложение. Ошибка есть и в основе beta-2, и в функции на beta-1.

### Обычный способ

Исполнитель делает маленький fix PR в main. После слияния координатор пары B включает актуальный main в общую ветку функции. Это можно делать **до готовности всей beta-2**, если main уже содержит только работающие совместимые изменения. Не ждём следующего тега ради важного исправления.

### Если нужно передать только исправление, без следующих изменений основы

Создаём один небольшой fix от общей исходной beta-1:

~~~powershell
git fetch origin --tags
git switch -c fix/empty-input beta-1
~~~

Исполнитель исправляет ошибку, добавляет проверку, делает commit (сохранение изменений в истории Git) и push:

~~~powershell
git add путь-к-модулю путь-к-тесту
git diff --cached
git commit -m "fix: handle empty input"
git push -u origin fix/empty-input
~~~

Пути заменить реальными файлами. Затем открывает **два PR из одной fix-ветки**:

| PR | base (ветка, в которую объединяем изменения) | head | Проверяет и объединяет |
| --- | --- | --- | --- |
| Исправление основы | main | fix/empty-input | Пара A + Лия (QA — тестировщик), интегратор |
| Исправление функции | feature/beta1-f1 | fix/empty-input | Пара B + Лия (QA — тестировщик), координатор |

Оба слияния — Create a merge commit. Общий fix-коммит попадает в историю обеих линий; позднее main → функция не требует повторно применять отдельную копию исправления.

Перед выбором этого способа убедитесь, что баг воспроизводится на beta-1 и исправление применимо к обеим версиям. Если структура main уже поменялась, адаптируйте её отдельно и проверьте обе цели. Если PR конфликтует, не переписывайте общую fix-ветку изменениями одной цели: создайте отдельную adaptation-ветку для этой цели. Исходный fix остаётся небольшим и общим.

Если проблема относится только к F1, fix делаем от общей ветки функции и направляем туда. Если только к улучшениям beta-2, исправляем main. Лия (QA — тестировщик) указывает затронутые версии в баге.

**Важно:** после обычного push исправление есть лишь на сервере в fix-ветке. Оно считается внедрённым в обе линии только после обоих PR и проверки результатов. Старый beta-1 намеренно остаётся исходным снимком.

## 6. Делим работу full-stack пары без жёсткой специализации

Каждый full-stack может делать логику, интерфейс и тесты. На конкретной F1 выбираем один из вариантов:

- Одна функция, две подзадачи: первый делает алгоритм, второй — вызов и отображение; договариваются о контракте.
- Два независимых сценария одной функции: каждый делает свой сценарий целиком, общие entrypoint (точка запуска приложения) и данные меняет назначенный владелец.

Например, для консольного приложения F1 может включать поиск и экспорт. Один участник делает поиск от команды до результата, второй экспорт от команды до файла. Общую регистрацию команд меняет один из них после согласования.

Перед задачей пишем в Issue: «меняю файлы ..., общий файл ... меняет ...». Если один файл нужен обоим, делим функции либо один участник собирает изменения обоих. Две личные ветки остаются отдельными, PR идут в общую ветку функции.

Не начинаем одновременно две функции, обе требующие полной переделки основного меню. Лучше закончить один пользовательский сценарий и сразу передать его Лия (QA — тестировщик).

## 7. Как объединять всем вместе и не мешать друг другу

Интегратор — оператор текущего слияния, а не единственный человек, который понимает код. Для каждой интеграции назначаем:

| Участник | Действие |
| --- | --- |
| Владелец основы | Объясняет изменение ядра/данных и помогает сохранить старые сценарии |
| Владелец интерфейса | Проверяет меню, команды, параметры и вывод |
| Full-stack №1 | Адаптирует свою часть функции |
| Full-stack №2 | Адаптирует свою часть функции, просматривает итоговые изменения |
| Лия (QA — тестировщик) | Проверяет сценарии на общем SHA и фиксирует результат |
| Выбранный оператор из разработчиков | Выполняет merge и push, открывает/объединяет итоговый PR |

Роли оператора и автора могут совпадать, но одобрение PR даёт другой человек. На следующем слиянии оператор может смениться по явной договорённости.

Перед интеграцией 5–10 минут: сообщаем ветки, готовые PR, изменения контракта, ожидаемую базу. На время финальной проверки останавливаем push в проверяемый head и merge в main. Разработчики могут продолжать независимую работу в новых личных ветках, пока не отправляют её в проверяемую общую версию.

После слияния все обновляют свои базы. Лия (QA — тестировщик) проверяет новый main. Дежурный записывает итоговый SHA и тег. Конкретные команды синхронизации и разрешения конфликтов — разделы 9–10 основного руководства.

## 8. Ограничиваем незавершённую работу

Практические правила для двух дней:

- У каждого разработчика одна активная задача.
- У пары B одна общая функция в интеграции. Следующая начинается после включения текущей в main, если сроки позволяют.
- У Лии (QA — тестировщик) одна активная проверка; следующая готовая задача находится в явной очереди.
- Задача обычно занимает 30–90 минут; если больше, разбиваем на проверяемые части.
- Пара A включает небольшие совместимые изменения в main по мере готовности.
- Общую ветку функции обновляем после значимых изменений main и перед итоговым PR. Не оставляем ветки разойтись на целый день.
- Контракты и общие файлы согласуем до кода, а не после конфликта.
- Незавершённый PR — Draft (черновик запроса, ещё не готовый к объединению); готовый к проверке — Ready.
- Статус BLOCKED содержит причину и вопрос конкретному человеку.

Это ориентиры, а не секундомер. Сложный алгоритм может занять больше; его интерфейс и контрольные примеры согласуем заранее.

## 9. Контрольные точки и критерии перехода

| Точка | Проверка | Что разблокирует |
| --- | --- | --- |
| C0: старт | Доступ, роли, стек, обязательный сценарий | Разработка скелета |
| C1: beta-1 | Запуск + один реальный сценарий + контракт | Одновременный старт beta-2, F1 и полной проверки beta-1 |
| C2: beta-2 | Основные изменения пары A работают | Интеграция улучшенной основы с F1 |
| C3: совместный кандидат | F1 + основные сценарии, нет P0/P1 | PR функции в main |
| C4: финал | Чистый клон, инструкция, демо, SHA | Тег final-v1 и сдача |

Для C1 не требуется проверить всё приложение. Для C3 проверяем изменённые части и обязательные сценарии совместно. Для C4 проверяем весь набор обязательной приёмки.

Если C1 сильно задерживается, оба full-stack помогают закончить обязательный сценарий. Если интеграция не удаётся к заморозке функций, руководитель выбирает уже проверенный объём; неподключённая функция остаётся вне финального результата.

## 10. Коммуникация и быстрые решения

Каждое утро, середина дня и перед завершением — 5–10 минут: готово, следующий шаг, блокировка. Общий контракт меняется — сообщаем сразу обеим парам.

Шаблон сообщения автор → Лия (QA — тестировщик):

~~~text
READY FOR QA: Issue #..., PR #...
Ветка: ...
SHA: ...
Запуск: ...
Проверить: ...
Ожидается: ...
Отличие от прошлой проверки: ...
~~~

Шаблон Лия (QA — тестировщик) → исполнитель:

~~~text
FAILED: сценарий ..., приоритет P...
Ветка / SHA: ...
Шаги: ...
Ожидалось: ...
Получено: ...
Затронутые линии: beta-1 / main / F1.
Баг: ссылка...
~~~

Шаблон перед слиянием:

~~~text
Начинаем интеграцию main → feature/beta1-f1.
Оператор: ...
Владельцы ядра / интерфейса / функции: ...
Проверяемый SHA: появится после merge.
До окончания проверки не меняем head кандидата и main.
QA проверяет основной сценарий + F1; затем итоговый PR в main.
~~~

## 11. Что есть сейчас и что нужно сделать завтра

Сейчас подготовлены документы, логические каталоги и шаблоны. Будущий скелет ещё не написан. Ветка F1, теги beta-1/beta-2 и результаты Лия (QA — тестировщик) не создаются заранее как фиктивные достижения.

Сегодня: доступ → чтение → клон → пробный полезный PR → роли.
Завтра: подтвердить регламент задания №3 → контракт v1 → скелет D1–D3 → C1 → три параллельных потока.
К финалу: совместная версия → независимая проверка → точный тег → инструкция сдачи.

Эта схема использует практики реальных проектов в объёме, подходящем пяти людям и двум дням: небольшие изменения, стабильная общая ветка, явные контракты, проверяемые снимки, быстрые исправления и регулярная интеграция.
