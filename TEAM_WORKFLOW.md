## 2. Пять ролей и ответственность

Руководитель — один из этих пяти человек. Интегратор — тоже один из этих пяти, а не шестой участник. По умолчанию назначаем интегратором разработчика ядра; команда может выбрать другого в `docs/TEAM.md`.

| Роль | Линия | За что отвечает | Что делает до готовности скелета |
| --- | --- | --- | --- |
| Тестировщик (QA) | Обе | Проверка PR, баги, проверка совместной версии, репетиция защиты | Пишет сценарии, готовит данные, проверяет запуск с чистого клона |
| Разработчик ядра / бэкэнда | Пара A | Данные, бизнес-логика, хранение, версия контрактов; по умолчанию интеграция | Создаёт минимальное ядро и точку вызова |
| Разработчик интерфейса / фронтэнда | Пара A | Карта, журнал, карточки и подключение API (способ обмена данными с сервером) | Создаёт интерфейс и соединяет один полный сценарий |
| Full-stack (разработчик и серверной части, и интерфейса) разработчик №1 | Пара B | Локальный агент, tools (инструменты агента), очередь и панель анализа | Проверяет локальную LLM (большая языковая модель) и tool calling (вызов инструментов моделью), согласует tools |
| Full-stack разработчик №2 | Пара B | Симулятор, features (числовые признаки), собственная MLP и evaluation (оценка качества модели) | Готовит normal (обычное поведение) simulator и независимые эпизоды |

После беты №1 пара A улучшает основу до беты №2, а пара B добавляет функцию к снимку беты №1. QA сразу начинает проверять основные функции беты №1 на фиксированном SHA (идентификатор конкретной версии кода), одновременно с разработкой обеих пар, затем проверяет изменения и итог. Перед тегом нужна короткая проверка запуска и обязательного сценария; полное тестирование беты идёт уже параллельно.

Оба участника пары B — full-stack. В текущем F1 B1 делает агентный анализ, B2 — симулятор и нейросеть; каждый подключает собственный законченный сценарий к интерфейсу по соглашению с A2. Все четыре разработчика участвуют в объединении; один выбранный интегратор выполняет конкретное слияние, остальные помогают с контрактами, конфликтами и ревью. Пара B не ждёт без дела первые часы: помогает с требованиями, данными и тестами, берёт независимые задачи. Пока контракта нет, не переписывает чужой каркас.

### Кто принимает решения

- Приоритеты и сокращение объёма: руководитель после короткого обсуждения.
- Формат данных и сигнатуры ядра: разработчик ядра + разработчик интерфейса.
- Изменение общего контракта: согласие обеих пар, запись в `docs/CONTRACTS.md`.
- Проверка поведения: QA; автор PR сообщает, как воспроизвести.
- Слияние в `main`: назначенный интегратор после ревью и проверки.
- Слияние в общую ветку функции: назначенный координатор пары B после ревью второго участника.
- Каждый участник отправляет код в свою ветку. Автор не одобряет собственный PR.

Один reviewer с правом записи достаточен для небольшого PR. Для изменения контрактов нужен просмотр другой пары. QA подтверждает результат проверки, а интегратор объединяет его.

## 3. Как работают ветки и две беты

У нас одна общая история Git. «Основная ветка» — `main`. «Вторая ветка» — временная общая ветка первой функции `feature/beta1-f1`.

| Ветка | Назначение | Кто отправляет изменения | Куда открывать PR |
| --- | --- | --- | --- |
| `main` | Последняя проверенная совместная версия, источник демонстрации | Интегратор через GitHub PR | — |
| `core/backend-skeleton` | Ядро первого скелета | Разработчик ядра | `main` |
| `core/interface-skeleton` | Интерфейс первого скелета | Разработчик интерфейса | `main` |
| `core/beta2-validation`, `core/beta2-interface` | Небольшие улучшения основы | Соответствующий участник пары A | `main` |
| `feature/beta1-f1` | Общий результат пары B, ответвлённый от беты №1 | Координатор пары B через PR; синхронизацию с main делает он | `main` после объединения с бетой №2 |
| `feature/f1-agent` | Логика функции | Первый участник пары B | `feature/beta1-f1` |
| `feature/f1-ml` | Подключение функции | Второй участник пары B | `feature/beta1-f1` |
| `qa/core-scenarios`, `qa/regression` | Тесты, данные и инструкции проверки | QA | `main` или ветка функции, смотря что проверяет |
| `fix/номер-короткое-имя` | Исправление конкретной ошибки | Назначенный исполнитель | Ветка, где исправление нужно |

Имена в таблице — пример и соглашение. Новые имена пишем латиницей без пробелов. Не создаём сразу все ветки: ветку создаёт исполнитель при начале задачи от актуальной базы.

Пара A «работает над main» так: делает небольшой законченный шаг в личной ветке, открывает PR в main, получает проверку, интегратор объединяет. Незаконченный код остаётся в личной ветке или Draft (черновик запроса, ещё не готовый к объединению) PR. `main` должен запускаться после каждого слияния.

Схема истории:

~~~text
main:              скелет → beta-1 → улучшения основы → beta-2 → beta-3 → финал
                              \                         /        ^
feature/beta1-f1:               + функция F1 ← merge main ---------+
                               ^           ^
feature/f1-agent:               + PR        |
feature/f1-ml:                       + PR
~~~

`beta-1`, `beta-2`, `beta-3` — теги проверенных снимков, а не дополнительные постоянные ветки. Тег не двигаем и не переиспользуем. `main` продолжает двигаться вперёд.

**Основное направление изменений:** личная ветка → её база через PR; затем `main → feature/beta1-f1` для адаптации; затем `feature/beta1-f1 → main` через итоговый PR.

Для всех командных PR выбираем **Create a merge (объединение веток) commit (сохранение изменений в истории Git)**. Это сохраняет общую историю при повторной синхронизации веток. В рамках этого процесса не используем squash/rebase для общей ветки функции. Не включаем требование линейной истории, которое запрещает merge-коммиты.

Две пары не отправляют изменения одновременно в одну общую ветку. Общая ветка функции принимает PR от личных веток. Прямую синхронизацию общей ветки с `main` делает только её координатор, предупредив вторую пару.

## 4. Что руководитель делает сегодня

1. Собирает GitHub-ники четырёх остальных участников.
2. Открывает https://github.com/Military05/Hackathon → **Settings → Collaborators → Add people**.
3. Добавляет каждого человека и проверяет, что приглашение принято. Открытая ссылка даёт возможность читать публичный репозиторий; право push (отправка изменений на GitHub) появляется после принятия приглашения.
4. Отправляет команде ссылку на этот файл и готовое сообщение из раздела 14.
5. Вписывает имена в `docs/TEAM.md`, выбирает интегратора и координатора пары B.
6. Создаёт задачи по шаблону **Задача команды** во вкладке Issues (задачи и сообщения об ошибках). Начальный список уже есть в `docs/BACKLOG.md`. Каждая задача получает одного исполнителя.
7. Договаривается о едином чате: там ссылки на Issues/PR и короткие сообщения о блокировках; решения и результат остаются в GitHub.
8. Просит всех сегодня сделать клон и пробный PR с одной строкой в таблице участников. В своём PR человек меняет только свою строку.

### Защита main

При подготовке обнаружено, что `main` не была защищена. Этот документ сам по себе защиту не включает. Настройки доступа и защиты руководитель устанавливает в GitHub отдельно.

Для публичного репозитория защита ветки доступна на GitHub Free. Откройте **Settings → Branches → Add branch protection rule** (или доступную в интерфейсе настройку ruleset) для `main`:

- Require a pull request (запрос на объединение изменений) before merging.
- Один обязательный approving review (проверка изменений другим разработчиком).
- Require conversation resolution before merging.
- Запрет force push и удаления ветки.
- При желании применить правила к администраторам: Do not allow bypassing the above settings.
- **Не включать Require linear history**: наш процесс использует merge-коммиты.
- Проверки CI (автоматические проверки после отправки кода) требовать только после появления настоящего workflow и успешного запуска его job. В этой подготовке workflow не добавлен; автоматическое тестирование на GitHub пока не настроено.

В личном репозитории не обещаем технически ограничить слияние только одним человеком обычными ролями collaborators. «Сливает интегратор» — договорённость команды; защита требует PR и ревью.

Если защиту ещё не настроили, соблюдаем те же правила вручную. Для общей ветки функции можно позднее включить требование PR, но тогда синхронизацию из `main` также проводим отдельным PR, как описано в разделе 9.

## 5. Подготовка компьютера каждого участника

### 5.1. Установить Git и настроить автора

Git: https://git-scm.com/downloads. На Windows подойдут PowerShell, Git Bash или терминал VS Code. Команды ниже совместимы с PowerShell; команды выполняем по одной, после успешного завершения предыдущей.

~~~powershell
git --version
git config --global user.name "Ваше имя"
git config --global user.email "Ваш email из GitHub"
~~~

Вместо строк-примеров укажите свои значения. Для приватности можно взять свой noreply email из GitHub **Settings → Emails**. Эти параметры подписывают коммиты, но не выполняют вход в GitHub.

### 5.2. Скачать репозиторий один раз

Выберите папку с достаточным свободным местом. Не клонируйте проект внутрь другого клона этого же проекта.

~~~powershell
git clone https://github.com/Military05/Hackathon.git
cd Hackathon
git status
git branch --show-current
git remote -v
~~~

Ожидаем чистую рабочую папку, ветку `main`, remote `origin` с адресом Military05/Hackathon. Откройте эту папку в редакторе. ZIP с GitHub не содержит историю Git и для командного push не подходит.

### 5.3. Проверить вход и доступ

При первом push Git может открыть браузер через менеджер учётных данных — войдите под приглашённым аккаунтом. Пароль аккаунта GitHub не используется как пароль HTTPS Git. Если ваш способ входа требует токен/SSH, настройте его по официальной инструкции в конце файла. Не кладите токен в код, remote URL, скриншоты и чат.

Для проверки прав достаточно маленькой полезной правки в своей строке `docs/TEAM.md`:

~~~powershell
git switch main
git pull --ff-only origin main
git switch -c docs/your-login-onboarding
~~~

Замените `your-login` на свой ник, отредактируйте свою строку таблицы, затем:

~~~powershell
git add docs/TEAM.md
git diff --cached
git commit -m "docs: add my team role"
git push -u origin docs/your-login-onboarding
~~~

Откройте PR в `main` по разделу 7. Если таблица уже заполнена, исправьте только контакт или поставьте свою отметку готовности. Пустой коммит для проверки не нужен. Не отправляйте всю папку командой `git add .`, пока не проверили, что в ней нет лишних файлов.

### 5.4. Запуск после выбора языка завтра

Сегодня здесь документация и структура, а не реализованная программа. Готовой команды запуска и тестирования приложения пока нет.

Версии и результат проверки фиксируем в docs/TEAM.md, команды — в [RUNBOOK](docs/RUNBOOK.md). A1 реализует installation/server, B2 simulator/train/evaluate, B1 local LLM. Второй участник повторяет чистый клон. До появления соответствующего кода целевые команды ещё не работают.

Ни формат консоли, ни сервер, ни база данных заранее не обязательны. Выбираем минимальные инструменты, которыми команда уже умеет пользоваться и которые решают задание.

### 5.5. Код и чат

Команда умеет писать код и работает в собственных редакторах. Для обсуждения решений можно использовать чат. Ты как full-stack подключаешь Codex к конкретным задачам своей ветки, сложным ошибкам, проверке diff и интеграции. Работа команды продолжается даже при недоступности помощника или исчерпании лимитов.

### Контракт до параллельной разработки

В `docs/CONTRACTS.md` записываем название операции, вход, выход, ошибки, порядок вызовов и минимальный пример. Для выбранного web MVP контракт включает URL/метод/JSON, локальные query tools и признаки MLP.

Если ядро ещё не готово, интерфейс работает с заглушкой, которая выдаёт **тот же** согласованный формат. Заглушку обозначаем явно; до беты №1 заменяем реальным ядром хотя бы в обязательном сценарии.

Не меняем поле, имя функции или формат ошибки молча. Сначала пишем другой паре и обновляем контракт. Если изменение ломает старую версию, сохраняем совместимость через адаптер либо ставим отдельную задачу адаптации. Это намного дешевле, чем разбирать конфликт в последний час.

### Владелец файлов

Пара A владеет базовыми entrypoint, ядром и основным интерфейсом. Пара B работает прежде всего в своём модуле функции. Подключение функции к общей точке входа — отдельный маленький PR с просмотром владельца интерфейса. QA ведёт тесты и журнал.

Если двое должны изменить один файл, заранее делим функции/участки или выбираем одного исполнителя. Разные ветки не устраняют конфликт автоматически.

## 7. Обычный цикл: задача → код → push → PR

Если с Git пока непривычно, делай по одному шагу. `main` — общая ветка; личная ветка нужна для твоей задачи. PR — просьба проверить и объединить твою работу. Названия кнопок GitHub сохраняем, рядом объясняем смысл.

| Команда или слово | Зачем нужно |
| --- | --- |
| git status | Узнать свою ветку и изменённые файлы |
| git switch | Перейти в ветку; -c создаёт новую |
| git pull --ff-only origin main | Получить свежую общую версию, если нет расхождения истории |
| git add | Выбрать настоящие изменённые файлы для сохранения |
| git diff --cached | Проверить именно подготовленные файлы |
| git commit | Сохранить выбранные изменения в истории |
| git push | Отправить свои коммиты на GitHub |
| origin | Имя подключения к репозиторию GitHub |
| -u | Запомнить, куда отправлять эту ветку дальше |
| PR / Pull Request | Запрос на объединение после проверки |
| base / compare | Куда объединяем / откуда берём изменения |
| git rev-parse HEAD | Узнать точную проверяемую версию кода |

Дальше повторяй команды для своей роли. Не вводи буквально `путь-к-файлу`: подставь файл, который ты изменил. Если появилась ошибка, передай её текст команде и не продолжай остальные шаги вслепую.


### 7.1. Взять задачу

Создайте Issue (задача или сообщение об ошибке) через шаблон **Задача команды** или выберите существующий. У задачи один исполнитель, понятный результат и критерии приёмки. Укажите базовую ветку и файлы, которые планируете менять. Статусы: TODO → IN PROGRESS → IN REVIEW → DONE; BLOCKED сопровождается причиной и тем, кто может помочь.

Одна небольшая задача — одна личная ветка — один PR. Не держите готовый код локально полдня. Отправляйте осмысленные коммиты по мере завершения частей задачи.

### 7.2. Начать личную ветку от main: пример пары A

Сначала убедитесь, что `git status` показывает чистую папку:

~~~powershell
git switch main
git pull --ff-only origin main
git switch -c core/backend-skeleton
~~~

Разработчик интерфейса использует `core/interface-skeleton`. QA — `qa/core-scenarios`. Если ветка уже есть на GitHub, не создавайте ещё одну с тем же именем: используйте `git fetch origin`, затем `git switch --track origin/имя-ветки`; если она уже есть локально — `git switch имя-ветки`.

### 7.3. Закоммитить и отправить

Внесите изменения и выполните команды запуска/тестов из `docs/RUNBOOK.md`. Проверьте:

~~~powershell
git status
git diff
git add src/core/README.md
git diff --cached
git commit -m "Добавить основу сервера"
git push -u origin core/backend-skeleton
~~~

Путь `src/core/README.md` — существующий пример. Добавляйте **свои реально изменённые файлы**, например файл нового модуля и его тест. Не копируйте этот путь вместо своих файлов.

Последующие изменения в той же ветке:

~~~powershell
git add путь-к-файлу
git diff --cached
git commit -m "Исправить пустой ввод"
git push
~~~

`путь-к-файлу` замените реальным путём. `-u` нужен при первой отправке для настройки upstream (связи локальной ветки с её веткой на GitHub); потом достаточно `git push`. Если команда завершилась ошибкой, остановитесь и разберите её, а не запускайте весь блок дальше.

Примеры сообщений: `Добавить поиск`, `Проверить идентификатор записи`, `Проверить неверный ввод`, `Описать запуск`. Пиши понятное сообщение по-русски. Префиксы feat/fix/test/docs необязательны; если используете, они означают новую функцию, исправление, тесты и документацию.

### 7.4. Открыть Pull Request

На GitHub: **Pull requests → New pull request**. Проверьте две стороны:

- **base (ветка, в которую объединяем изменения)** — куда хотите внести результат: для пары A обычно `main`.
- **compare/head** — откуда: например `core/backend-skeleton`.

Для пары B личный PR направляется в `feature/beta1-f1`, а не в `main`. Неправильная base объединяет код в неправильный этап процесса.

Заполните автоматически подставленный шаблон: что изменено, Issue, как запустить, что проверить, какой риск и затронут ли контракт. Незаконченный результат оформляйте как **Draft**; снимите Draft после готовности. Назначьте reviewer, если GitHub позволяет, или передайте ссылку в командный чат.

Используйте `Closes #номер` для задач, которые должны закрыться после попадания в default branch `main`. Для промежуточного PR в ветку функции пишите `Refs #номер`: слияние в такую ветку не означает завершение общей задачи.

### 7.5. Получить проверку и объединить

Reviewer смотрит изменения, QA воспроизводит сценарий и записывает проверенный SHA. Если есть ошибка, автор исправляет её **в этой же ветке**, делает commit и push: PR обновится автоматически.

Интегратор проверяет base/head, отсутствие конфликтов, одобрение, результаты тестов и выбирает **Create a merge commit → Confirm merge**. После слияния QA быстро проверяет новый `main`.

Автор возвращается на общую базу:

~~~powershell
git switch main
git pull --ff-only origin main
~~~

Следующая задача начинается в **новой** ветке от свежей базы. Старую личную ветку можно удалить через GitHub после проверки; общую ветку пары B сохраняем до итоговой интеграции.

## 8. Как получить первую бету и начать вторую линию

### 8.1. Что означает «скелет готов»

До ответвления второй пары обязателен этот набор:

- Проект запускается по написанной инструкции на компьютере QA.
- Есть реальная точка входа, меню/команда/экран и подключённое ядро.
- Один минимальный пользовательский сценарий выполняется от ввода до результата.
- Формат входа, результата и ошибок записан в контракте.
- Есть понятная обработка неверного ввода и способ завершить приложение.
- Тестировщик воспроизвёл основной сценарий и зафиксировал SHA.
- Код пары A объединён в `main`; незакоммиченные локальные файлы не часть беты.
- Учитываем условия хакатона: если они ограничивают использование заранее написанного кода, выбираем допустимый старт вместе с организаторами.

### 8.2. Зафиксировать beta-1

Только интегратор после проверки:

~~~powershell
git switch main
git pull --ff-only origin main
git status
git log -1 --oneline
git tag -a beta-1 -m "First working skeleton checked by QA"
git push origin beta-1
~~~

Тег ставим на действительно проверенный коммит. Если с момента проверки main изменился, сначала QA проверяет новый head (ветка или версия с предлагаемыми изменениями) либо интегратор ставит тег на заранее записанный проверенный SHA. Уже существующий тег не перезаписываем.

### 8.3. Создать общую вторую ветку

Только координатор пары B создаёт её один раз. После появления тега:

~~~powershell
git fetch origin --tags
git switch -c feature/beta1-f1 beta-1
git push -u origin feature/beta1-f1
~~~

Сообщает команде: «Ветка feature/beta1-f1 создана от beta-1, контракт v1, функция F1 = ...».

Теперь full-stack №1, который взял подзадачу логики F1, в своём клоне:

~~~powershell
git fetch origin
git switch -c feature/f1-agent origin/feature/beta1-f1
~~~

Full-stack №2, который взял подключение F1, в своём клоне:

~~~powershell
git fetch origin
git switch -c feature/f1-ml origin/feature/beta1-f1
~~~

Оба отправляют свои личные ветки через `git push -u origin имя-ветки` и открывают PR **base = feature/beta1-f1**. После первого слияния второй участник подтягивает обновлённую общую ветку в свою личную по разделу 9.1.

### 8.4. Что пара A делает одновременно

Пара A начинает улучшения из свежего `main` в новых ветках `core/beta2-validation` и `core/beta2-interface`, направляет PR в `main`. Не меняет согласованный контракт без связи с парой B.

После проверки следующей рабочей основы интегратор ставит тег `beta-2` тем же способом, что `beta-1`. Бета №2 пока может не содержать F1: это улучшенная основа. Первая функция попадёт в следующую совместную бету.

## 9. Как объединить функцию на бете №1 с бетой №2

**Работающие в разных ветках люди не получают изменения друг друга автоматически.** Push отправляет вашу историю; fetch (получение сведений об изменениях с GitHub) получает сведения с сервера; merge включает чужую историю в текущую ветку.

### 9.1. Обновлять личную ветку от её базы

Перед началом работы, перед PR и после заметного изменения базы. Сначала commit своих изменений или stash по разделу 10.1.

Пример для разработчика ядра, текущая ветка `core/beta2-validation`:

~~~powershell
git status
git fetch origin
git switch core/beta2-validation
git merge origin/main
~~~

Пример для разработчика функции, текущая ветка `feature/f1-ml`:

~~~powershell
git status
git fetch origin
git switch feature/f1-ml
git merge origin/feature/beta1-f1
~~~

После merge: разрешить конфликты, выполнить тесты и проверку сценария, затем `git push`. Обычно merge сам создаёт merge-коммит; дополнительный commit нужен, если Git остановился на конфликтах.

Не обновляйте личную ветку функции напрямую от main каждый по-своему. Сначала координатор синхронизирует общую ветку функции с main, затем оба участника включают общую ветку в личные.

### 9.2. Подтянуть beta-2 в общую ветку функции

После того как личные PR функции включены в `feature/beta1-f1`, координатор договаривается с интегратором о коротком окне: не сливать новые PR в main до окончания интеграционной проверки.

Если общая ветка функции не защищена обязательными PR, только её координатор выполняет:

~~~powershell
git fetch origin
git switch feature/beta1-f1
git pull --ff-only origin feature/beta1-f1
git merge origin/main
~~~

Если этой ветки ещё нет в его локальном клоне, вместо первого `git switch` выполнить `git switch --track origin/feature/beta1-f1`.

В этот момент в текущую ветку функции входят улучшения основы. Исправляем не только текстовые конфликты, но и совместимость поведения: новые поля, ошибки, меню, storage. Затем выполняем тесты, ручной сценарий F1 и основной сценарий беты №2.

~~~powershell
git push origin feature/beta1-f1
git log -1 --format=%H
~~~

Вторая пара временно прекращает изменения проверяемой ветки. QA записывает этот SHA, проверяет весь совместный результат и сообщает «готово» либо создаёт конкретный баг.

### 9.3. Если общая ветка функции защищена требованием PR

Вместо прямой отправки результата merge в общую ветку координатор создаёт личную sync-ветку:

~~~powershell
git fetch origin
git switch -c sync/beta2-into-f1 origin/feature/beta1-f1
git merge origin/main
~~~

Разрешает конфликты, запускает проверки, затем:

~~~powershell
git push -u origin sync/beta2-into-f1
~~~

Открывает PR **base = feature/beta1-f1, head = sync/beta2-into-f1**. После ревью объединяет merge-коммитом. QA проверяет уже новый head общей ветки. После этого продолжаем следующим пунктом.

### 9.4. Итоговый PR функции в main

Координатор открывает PR **base = main, head = feature/beta1-f1**. Описание: «Функция F1 + совместимость с beta-2», связанная задача, команды проверки, SHA, результат QA.

Интегратор проверяет:

1. В head включён актуальный main, конфликтов нет.
2. Проверен именно текущий head PR, а не старый коммит.
3. Работают основной сценарий и новая функция вместе.
4. Никакие чужие файлы, функции и настройки не исчезли.
5. Есть одобрение другого участника.

Затем **Create a merge commit** в main. QA запускает новый main повторно; интегратор ставит тег `beta-3` только после успеха.

Если main успел измениться после проверки, повторяем синхронизацию и проверяем затронутые сценарии до слияния. «Нет конфликтов» означает лишь возможность объединить текст, а не корректность программы.

### 9.5. Следующая функция

После интеграции F1 обе пары обновляют main. Для новой функции создают **новую** общую ветку, например `feature/beta3-f2`, от проверенного актуального main или тега beta-3. Не продолжаем бесконечно развивать старый снимок beta-1.

За два дня лучше закончить одну полезную функцию и показать стабильную программу, чем открыть четыре долгие ветки и не успеть их объединить.

## 10. Конфликты, ошибки Git и восстановление

### 10.1. Git не даёт переключить ветку из-за изменений

Сначала `git status`. Если работа готова — добавьте нужные файлы и закоммитьте в своей ветке. Если не готова:

~~~powershell
git stash push -u -m "temporary work before sync"
~~~

После нужного переключения/синхронизации вернитесь в свою ветку и выполните:

~~~powershell
git stash pop
git status
~~~

`-u` включает новые неотслеживаемые файлы, но не игнорируемые. `stash pop` тоже может дать конфликт: разрешите его и проверьте status. Не применяйте stash к чужой ветке случайно. Stash хранится только на вашем компьютере.

### 10.2. Возник конфликт при merge

1. Выполните `git status` и посмотрите список unmerged.
2. Откройте файлы с маркерами:

~~~text
<<<<<<< HEAD
ваш вариант текущей ветки
=======
вариант из присоединяемой ветки
>>>>>>> origin/main
~~~

3. Сохраните итоговый работающий вариант, удалите маркеры. Иногда нужно объединить оба фрагмента и поправить вызовы. «Accept current/incoming» без чтения может потерять работу.
4. Если это общий интерфейс, разбирайте конфликт с владельцем файла.
5. Добавьте каждый исправленный файл, завершите merge и проверьте программу:

~~~powershell
git add путь-к-исправленному-файлу
git commit -m "merge: adapt feature to updated core"
~~~

6. После успешных тестов выполните push своей/координируемой ветки.

Если сейчас не можете решить конфликт, `git merge --abort` отменяет незавершённое слияние. Merge начинаем с чистой рабочей папки, чтобы сохранение своей работы было понятным. Не используем `reset --hard` или `clean -fd` для случайного «исправления Git».

### 10.3. Push rejected / non-fast-forward

Кто-то уже обновил эту удалённую ветку. Не используйте force push. Сохраните работу, затем:

~~~powershell
git fetch origin
git merge origin/имя-текущей-ветки
~~~

Замените имя, решите конфликты, проверьте и повторите push. Если это личная ветка, выясните, кто ещё в неё отправляет изменения. Если общий main — перестаньте отправлять напрямую и откройте личный PR.

### 10.4. Permission denied / 403 / repository not found

Проверьте `git remote -v`, приняты ли приглашения, тот ли аккаунт использует менеджер учётных данных. Имя/email в `git config` не меняют аккаунт входа. Руководитель проверяет доступ collaborators. Не отправляйте пароли и токены в чат.

### 10.5. pull --ff-only отказался работать

В локальной общей ветке есть собственные коммиты либо её история разошлась с удалённой. Не делайте reset. Сначала сохраните локальный head в отдельной ветке:

~~~powershell
git branch backup/my-local-work
git log --oneline --graph --decorate -12
~~~

Покажите историю интегратору. Локальные полезные коммиты переносим в личную ветку и отправляем через PR; сам main держим копией общего main. `--ff-only` специально останавливается вместо скрытого слияния в локальный main.

### 10.6. Ошибочно начали кодить в main

Если изменения ещё не закоммичены, создайте личную ветку сразу:

~~~powershell
git switch -c fix/my-task
~~~

Изменения останутся в рабочей папке этой ветки. Закоммитьте и отправьте её, откройте PR.

Если уже есть локальные коммиты в main, сначала `git branch backup/my-local-work`, затем вместе с интегратором перенесите их. Не отправляйте локальный main напрямую.

### 10.7. Плохой код уже попал в общий main

Исправление — отдельный PR. Если нужно отменить merge, интегратор сначала проверяет SHA и порядок родителей merge-коммита:

~~~powershell
git fetch origin
git switch -c fix/revert-broken-merge origin/main
git show --no-patch --pretty=raw SHA_СЛИЯНИЯ
git revert -m 1 SHA_СЛИЯНИЯ
~~~

`SHA_СЛИЯНИЯ` заменить реальным SHA, первый родитель должен быть предыдущим main. После тестов — push и PR в main. Для обычного коммита используется `git revert SHA` без `-m`. Не копируйте эти команды без проверки конкретного коммита. Revert оставляет общую историю; он не стирает уже опубликованные данные.

После revert merge повторное объединение той же ветки само по себе не вернёт отменённый код. С интегратором выберите новый исправляющий PR либо отмену самого revert, затем протестируйте.

### 10.8. Случайно отправили секрет

Сразу отозвать/заменить токен или пароль у его поставщика и сообщить руководителю. Удаление строки в следующем коммите не удаляет её из истории. Историю чистим отдельным согласованным действием; обычные участники не запускают force push всей команды.

В `.gitignore` должны быть local env, виртуальные окружения, сборки и локальные данные по выбранному стеку. Файл уже отслеживается Git? Добавление в ignore не перестаёт отслеживать его автоматически.

## 11. Инструкция для тестировщика

QA начинает с требований и данных до готовности кода. [docs/TESTING.md](docs/TESTING.md) содержит сценарии и таблицу результатов.

Для каждого PR/беты:

1. Получить ссылку на задачу и PR, точную ветку, команду запуска, ожидаемый результат.
2. Сохранить свою работу перед переключением.
3. Получить нужную ветку:

~~~powershell
git fetch origin
git switch --track origin/core/backend-skeleton
~~~

Команда `--track` нужна только при первом получении ветки. Позже:

~~~powershell
git switch core/backend-skeleton
git pull --ff-only origin core/backend-skeleton
git rev-parse HEAD
~~~

Замените имя на проверяемую ветку. Не коммитите исправления в ветку автора; свои тесты делайте в `qa/...` и направляйте отдельным PR.

4. Выполнить команды установки/сборки/тестов выбранного стека.
5. Пройти сценарии приёмки: нормальный ввод, пустой/неверный ввод, повтор операции, выход; хранение/перезапуск, если предусмотрены требованиями.
6. Проверить интеграцию: основной сценарий беты №2 + функция F1 в одном запуске.
7. Записать SHA, окружение, команды, результат и ссылку на баг.
8. В PR оставить результат и при успехе одобрение, если QA не автор. Если код поменялся после проверки, перепроверить изменённую часть и критический сценарий.
9. После слияния проверить общий main, перед защитой — чистый клон.

Для фиксации конкретного снимка можно проверить `git switch --detach SHA`. В этом режиме не делаем коммиты; возвращаемся `git switch main`. Изменения ветки на сервере не изменяют уже скачанный SHA.

При работе двух линий удобно иметь второй клон в отдельной папке. Не используем одну рабочую папку одновременно для двух запущенных разных версий. У веб-версий могут быть общие localStorage и порты; разделяйте профиль браузера/порт/данные и фиксируйте это.

### Приоритет ошибок

- P0: приложение не запускается, теряет важные данные, невозможен основной показ. Вся команда помогает устранить.
- P1: обязательная функция выдаёт неправильный результат. Исправляем до финального выпуска.
- P2: второстепенный сценарий или оформление. Исправляем, если остаётся время; иначе явно описываем ограничение.

Баг — воспроизводимые шаги, ожидаемое/фактическое поведение, SHA и окружение. Сообщение «не работает» не позволяет быстро исправить проблему.

## 12. Расписание двух дней

План рассчитан на два рабочих дня по ~8 часов. `T0` — фактическое время старта. Отметки относительные: переносим их под программу организаторов. При дедлайне раньше сразу сокращаем объём.

### День 1 — 7 октября

| Интервал | Пара A | Пара B | QA / контрольная точка |
| --- | --- | --- | --- |
| T0–T0+30 мин | Подтвердить регламент, контракт v1 и D1–D3 | Уточнить первую функцию, помочь с требованиями | Критерии успеха; все получили доступ |
| +30 мин–+1 ч | Записать контракт и каркас | Подготовить примеры, сценарии и заглушки | Команды запуска; распределённые Issues |
| +1–+3 ч | Ядро + интерфейс + один полный сценарий через маленькие PR | Независимые задачи, тестовые данные, подготовка модуля функции | Проверить скелет; после успеха тег beta-1 |
| +3–+5 ч | Улучшения основы к beta-2 | Создать feature/beta1-f1 от beta-1, личные ветки, реализовать F1 | Проверять обе линии, не копить баги |
| +5–+7 ч | Закончить и проверить beta-2 | Включить актуальный main в общую ветку, адаптировать F1 | Совместная проверка и PR функции |
| +7–+8 ч | Исправить критические ошибки, объединить | Довести интеграцию | Рабочий main, тег beta-3 при готовности, список на утро |

Если beta-1 не готова к +3 ч, режем обязательный сценарий и помогаем паре A. Не создаём от недоделанного скелета «официальную первую бету» только ради графика.

Перед окончанием дня: каждый делает commit/push полезной работы, оставляет ссылки на Draft PR, пишет «готово / осталось / блокирует». Не считаем незакоммиченные файлы на одном ноутбуке командным результатом.

### День 2 — 8 октября

| Интервал | Все действия | Контроль |
| --- | --- | --- |
| Первые 20 мин | Обновить main, прочитать баги и план, выбрать оставшийся объём | Основной сценарий по-прежнему работает |
| До середины дня | Исправления; ещё одна функция только при устойчивой основе | Новая функция имеет отдельный срок интеграции |
| Середина дня | Объединить оставшиеся функции, остановить новые крупные задачи | Все обязательные возможности в main |
| За 3 ч до сдачи | Заморозить новые функции; только баги, инструкции и демонстрация | Нет открытых обязательных feature PR |
| За 2 ч до сдачи | Чистый клон на другом компьютере, полная проверка | Запуск воспроизводится без автора |
| За 1 ч до сдачи | Репетиция защиты, резервные данные/материалы | Проверенная кандидатная версия |
| Последние 30 мин | Только критические исправления с повторной проверкой | Финальный тег и точная ссылка для сдачи |

Дважды в день и перед интеграцией проводим короткую сверку: каждый за минуту говорит, что готово, что делает и что блокирует. Изменения общего контракта обсуждаем сразу, не ждём следующей встречи.

Если дедлайн близко: оставляем один рабочий сценарий, одну законченную функцию и инструкцию запуска. Некритичную идею переносим в список «после хакатона».

## 13. Готовность задачи, выпуск и демонстрация

### Definition of Done для задачи

- Сделано то, что описано в Issue; критерии приёмки проверены.
- Код в нужной ветке на GitHub; есть PR с понятным описанием.
- Команды запуска/тестов выполняются; ручной сценарий воспроизводится.
- Есть проверки важного поведения, соразмерные изменению.
- Контракт и инструкция обновлены, если изменились.
- Нет секретов, временных файлов, зависимостей/сборок, заглушек вместо обязательной функции.
- Ревью завершено, QA указал проверенный SHA, если задача меняет поведение.
- Результат объединён в нужную общую ветку. Для функции окончательное DONE — после попадания в main и совместной проверки.

### Финальный выпуск

Заполните [docs/RELEASE.md](docs/RELEASE.md): версии инструментов, установка, запуск, примеры команд/данных, результаты проверки, ограничения и сценарий защиты.

QA клонирует проект в новую папку и проходит инструкцию без устных подсказок автора. Проверяет, что необходимые файлы отслеживаются Git. Для нашего web MVP проверяет сервер, карту, D1–D4, сохранение данных, живые tools агента и отключение LLM.

После окончательного успеха интегратор:

~~~powershell
git switch main
git pull --ff-only origin main
git status
git rev-parse HEAD
git tag -a final-v1 -m "Hackathon submission checked by QA"
git push origin final-v1
~~~

Сверьте head с проверенным SHA до создания тега. Если организаторы требуют релиз/архив/бинарник, оформляем их дополнительно по регламенту. Один source-клон не заменяет бинарный выпуск, когда он требуется.

Для сдачи даём ссылку на репозиторий и точный тег `final-v1`, а не обещание «последняя версия всегда в main». После тега финальные изменения — только с повторной проверкой и новым тегом `final-v2`.

Показ на 3–5 минут: проблема → запуск → обязательный сценарий → F1 → результат → ограничения. Сохраняем маленький проверенный набор демоданных и резервный план при отсутствии интернета.

## 15. Краткая памятка и источники

| Нужно | Действие |
| --- | --- |
| Посмотреть текущую ветку и изменения | `git status`, `git branch --show-current` |
| Узнать обновления сервера | `git fetch origin` |
| Обновить чистый локальный main | `git switch main`, `git pull --ff-only origin main` |
| Начать задачу | `git switch -c личная-ветка` от актуальной базы |

| Дальнейшая отправка | `git push` |
| Включить базу в свою ветку | Находясь в своей ветке: `git merge origin/базовая-ветка` |

| Узнать точный снимок | `git rev-parse HEAD` |
| Завершить задачу | PR → ревью/проверка → merge-коммит → проверка общей версии |
